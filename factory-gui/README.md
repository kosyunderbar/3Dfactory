# FLOOR — 셀 기반 제조 통합 관제 GUI v0.2

수정한 기획서의 **독립 작업 셀 + 차체 AGV + 부품 AMR** 컨셉을 반영한 브라우저 샘플입니다. 가상 스마트태그로 차체 상태를 조회하고, 물리적 버퍼의 예약·점유에 따라 배출이 차단되는 흐름을 확인할 수 있습니다.

HTML/CSS/JavaScript로 만든 기존 샘플 형식을 유지했습니다. 본 시스템의 Java 21·Spring Boot·PostgreSQL·Vue 3·Vite·ECharts·Python·TCP/NDJSON·SSE 기술 스택은 변경하지 않았습니다. 이 샘플은 실제 설비·Spring 서버·DB·TCP·SSE에 연결되지 않습니다.

## 실행

`index.html`을 Chrome 또는 Safari로 열면 실행됩니다. 외부 라이브러리, 인터넷 연결, Node.js 설치가 필요하지 않습니다.

로컬 서버를 사용하려면 이 디렉토리에서 다음 명령을 실행합니다.

```sh
python3 -m http.server 5174 --bind 127.0.0.1
```

브라우저에서 <http://127.0.0.1:5174>에 접속합니다. 서버 종료는 터미널에서 `Ctrl+C`입니다.

## 공장 모델

| 대상 | 샘플 설정 |
|---|---|
| 독립 작업 셀 | ASM-01 기초 조립 4초 / ASM-02 모듈 조립 6초 / QC-01 최종 검사 3초 |
| 셀 작업 자리 | 셀당 차체 1대, 진입 버퍼와 별도 |
| Parking Bay | 셀당 물리 슬롯 3칸 |
| 차체 차량 | AGV-001, AGV-002 / 차량당 차체 1대 |
| 부품 차량 | AMR-001 / 부품 도크 인계, 차체 버퍼 슬롯 제외 |
| 차체 경로 | BODY-IN → ASM-01 Bay/셀 → ASM-02 Bay/셀 → QC-01 Bay/셀 → GOOD 또는 HOLD |
| 태그 | 차체 ID와 태그 ID를 실행 내 1:1로 연결한 가상 식별자 |

예약은 배차 승인 시 생성합니다. AGV가 아직 픽업하러 가는 중이어도 목적지 슬롯을 차지하며, 차체는 실제 적재 완료 전까지 앞 셀에 남습니다. Bay에 차체를 내려놓으면 AGV가 복귀합니다. Bay에서 빈 셀로 투입하는 동작은 별도 AGV 없이 가상 인계대로 처리합니다.

## 화면과 조작

- **셀 맵:** 셀 제목/배경을 선택하면 셀 상세, 차체 ID를 선택하면 태그 창, Bay와 차량을 선택하면 해당 상세를 표시합니다. 지도 대상은 Tab과 Enter/Space로도 선택할 수 있습니다.
- **슬롯 카드:** 대기 W, 도착 예약 R, 전체 C, 여유 A를 함께 표시합니다. 상세에서 각 슬롯의 FREE/RESERVED/OCCUPIED와 차체·차량을 확인합니다.
- **태그 창:** 차체/태그 ID, 모델·사양, 현재 위치, 운반 차량, 현재·완료·다음 공정, 검사 결과, 배차와 차체 이력을 표시합니다. 전체 차체 ID 또는 태그 ID로 검색할 수 있습니다. Escape 또는 닫기로 돌아옵니다.
- **셀 강조:** 선택 셀 이외의 작업 구역을 흐리게 표시합니다. 상단 지표는 계속 공장 전체 기준입니다.
- **이벤트:** 작업 완료, 슬롯 예약, 도착, 셀 진입, 부품 인계와 복구를 표시합니다. 상세의 관련 이벤트 버튼으로 필터링하고 전체 기록으로 해제합니다.
- **맵 확대:** 확대 버튼으로 넓게 보고 같은 버튼 또는 Escape로 돌아옵니다.

차체 목록은 현재 공장에 있는 차체 중 최대 6대를 보여 줍니다. 반출된 차체도 ID/태그 검색으로 조회할 수 있습니다.

## 시나리오

**정상 운영:** 같은 차체 모델에서 셀 작업, 배차, 픽업, 이동, Bay 인계, 셀 투입과 최종 검사가 진행됩니다. 최종 검사 결과와 품질 지표는 검사 이력에서 계산합니다. 입력은 실행당 최대 100대이며 모두 반출하면 셀이 대기합니다. 초기화하면 새 실행을 시작합니다.

**버퍼 만석:** 자동 시간을 멈춘 검증 장면입니다. 단계 버튼으로 아래 순서를 확인합니다.

1. ASM-02 Bay의 **대기 2 + 이동 예약 1 = 3 / 3**. ASM-01은 작업을 끝냈지만 차체를 유지하며, 빈 AGV-002가 있어도 배출하지 않습니다.
2. ‘예약 차량 도착시키기’: **대기 3 + 예약 0 = 3 / 3**. 차량이 도착해도 가용 슬롯이 생기지 않으므로 차단은 유지됩니다.
3. ‘차체를 셀로 투입 · 배차 재개’: 대기 차체 1대가 ASM-02에 진입해 1칸을 반환합니다. 그 칸을 AGV-002가 새로 예약하면 **대기 2 + 예약 1 = 3 / 3**으로 돌아갑니다. 새 배차는 승인됐지만 ASM-01 차체는 픽업 전이므로 셀에 남습니다.

‘검증 완료 · 다시 보기’로 장면을 반복할 수 있습니다. 이 장면의 자동 셀 진입은 설명을 위해 보류합니다. 정상 운영에는 이런 보류가 없습니다.

**셀 정지:** ASM-02 작업과 셀 진입이 멈추고 고장 알람이 발생합니다. 이미 예약한 차량은 Bay에 도착할 수 있으며, 이후 버퍼가 차면 ASM-01의 배출도 막힙니다. 알람 확인은 고장을 복구하지 않습니다. 셀 상세의 ‘ASM-02 복구’ 버튼으로 복구하고 확인·복구 이력을 각각 살펴봅니다. 버퍼 만석/가용 차량 대기는 고장 알람으로 집계하지 않습니다.

**품질 이상:** 최근 5분 이력 샘플 **검사 100대 / 불량 20대**를 주입합니다. 과거 표본과 새 검사 모두 차체별 결과를 보관하고 동일한 시간 구간에서 집계합니다. 이후 새 검사와 시간 경과로 수치가 바뀝니다. 즉시 일시정지하면 초기 20.0%를 확인할 수 있습니다.

**통신 단절 / 재연결:** 브라우저의 상태 수신만 중단합니다. 시뮬레이터는 계속 동작하고, 화면은 마지막 차체·슬롯·예약·좌표를 유지합니다. 현재 가동/이동 수는 ‘—’, 나머지 값은 마지막 수신값으로 표시합니다. 태그 창도 마지막 스냅샷을 따릅니다. ‘재연결’을 누르면 최신 전체 상태를 받습니다. 기존 셀 정지 알람을 임의로 복구하지 않습니다.

**일시정지:** 시뮬레이터 자체를 멈추므로 작업과 이동 모두 중단됩니다. 만석 안내에서는 단계 버튼을 사용합니다.

정상·만석·정지·품질 장면 전환과 초기화는 실행/이력을 새로 만듭니다. 통신 단절과 재연결은 현재 실행을 유지합니다. 새로고침하면 저장되지 않은 데모 상태가 초기화됩니다.

## 검증

모델 검증에서 만석 배출 거절, 도착 시 슬롯 유지, 셀 진입 시 반환, 픽업 전 차체 유지, 중복 배차 거절, 출발 전 취소와 중복 취소 방지, 출발 후 취소 거절, 정지 전파, 태그 고유성과 차체 소유 위치를 확인했습니다. 100대 정상 실행을 20,000번의 100ms 단계로 진행하며 2,008개 상태를 검사했고, 모든 차체가 한 번씩 검사되고 반출됐습니다. 부품 AMR은 차체 슬롯을 소비하지 않습니다.

`verify-model.js`는 실패하면 예외를 던지는 독립 검증 스크립트입니다. Node.js가 있는 개발 환경에서는 이 폴더에서 다음과 같이 재실행할 수 있습니다. Node.js는 GUI 실행의 필수 조건이 아닙니다.

```sh
node -e "require('./model.js'); require('./verify-model.js')"
```

Chrome에서 만석 3단계, 차체/태그 검색과 상세, 키보드 셀 선택, 정지 알람 확인/복구, 통신 단절 시 좌표 고정과 재연결, 초기 품질 표본을 확인했습니다. 약 1440px 데스크톱과 390px 모바일에서 배치와 태그 창을 확인했습니다. 작은 화면의 가로 스크롤은 맵 내부에서 처리합니다.

## 구현 범위와 후속 연결

100ms 모델 단계와 500ms 화면 스냅샷을 분리했습니다. 표시용 위치 보간은 슬롯 계산에 사용하지 않으며 일시정지/통신 단절/단계 안내에서는 멈춥니다. 애니메이션 감소 설정에서는 스냅샷 위치만 표시합니다. 차트는 이 독립 샘플에서 SVG로 그립니다.

이 검증은 **브라우저 내부 모델**의 결과입니다. 서버의 동시 요청 처리, DB 트랜잭션, 로그 재전송, TCP/SSE 복구, 실제 태그 측위, 충돌 회피와 수백 대 부하 시험을 검증한 결과가 아닙니다. 본 구현에서는 상태 공급부를 서버 API/SSE로 교체하고 Vue 컴포넌트와 ECharts를 적용합니다. 부품 재고는 충분하다고 가정하며, 경로는 순환하지 않는 고정 순서입니다. 모든 형태의 교착 상태를 해결했다고 주장하지 않습니다.

화면 색상은 사용자 지정 기준인 **흰색 바탕·네이비 글씨·네이비~파란색 강조**를 따른다. 상태는 색과 함께 이름/테두리/점선으로 구분한다. [색상 기준](<../docs/development/UI 색상 기준.md>)

## S09 완료와 재실행

[실제 측정/P0 완료표](<../docs/development/S09 측정·완료 기록.md>) · [처음 실행/기존 데이터/복구/시연](<../docs/development/초기 실행·재실행·복구·시연.md>) · [새 실제 시연 캡처/단계 재생](<../docs/development/s09-demo/index.html>).

S09-01~04를 완료했습니다. 측정은 별도 네이티브 검증 DB/임의 loopback 포트를 사용하며 개발 Compose DB/볼륨은 유지했습니다. 정상25.63~25.72건/s·작은 화면 반영 p95 약98ms, 높은 입력 목표 미생성·업무 전달 지연을 구분합니다. SQL 병목이 확인되지 않아 새 index/DDL/의존성은 추가하지 않았습니다. 수집 Flyway1/2·관제1 그대로이며 같은 기존 data 재시작의 선택8개 표 지문이 일치했습니다. 일반 기동은 자동 생산하지 않습니다.

이 디렉터리는 독립 UI 샘플입니다. S09 시연은 `services/factory-console`과 실제 Python→TCP→수집 DB→HTTP→관제 DB→REST/SSE 경로에서 캡처했습니다. 샘플 자체를 실제 데이터 연결 근거로 쓰지 않습니다.
