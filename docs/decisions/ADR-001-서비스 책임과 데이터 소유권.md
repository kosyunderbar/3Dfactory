> 범위: 실행 단위·책임·데이터 소유·상태 변경 권한  
> 구현 상태: 설계 결정 완료. 2026-10-05 S01-01~04에서 두 앱·독립 DB/계정/Flyway·Compose/readiness·Python/Vue 실행 기반 및 실제 검증 완료. S02-01에서 Python 공장 설정·차체/태그·단일 위치 기초도 완료. 작업/예약/운송·네트워크 본 기능은 미구현.

## 1. 배경과 목적

[단계별 개발 계획](<../../가상 제조공장 실시간 통합 관제 시스템 - 단계별 개발 계획.md>)에 따라 기존 기술 스택으로 소규모 MSA를 만든다. 서비스별 독립 실행과 작업 단위별 검증을 가능하게 하고, 같은 차체·슬롯을 여러 프로그램이 독립적으로 변경하지 않도록 책임을 확정한다.

공장은 독립 셀 3개, 차체 AGV 2대, 부품 AMR 1대에서 시작한다. P0에서는 Python 공장 모델이 실제 물리 규칙을 결정하고, Spring 서비스는 수집과 관제를 맡는다. 가상 스마트태그는 차체 식별·조회 기능이며 별도 하드웨어나 태그 서비스가 아니다.

## 2. 확정한 실행 단위

| 실행 단위 | 언어/기반 | 핵심 책임 | 담당하지 않는 책임 |
|---|---|---|---|
| `factory-simulator` | Python 3 | 셀 공정·차체/태그·차량·검사·배차·예약/반환·시나리오·사건 송신 | GUI용 SQL 집계, 알람 확인 기록 |
| `ingestion-service` | Java 21 / Spring Boot | TCP 프레임·입력 검증, 수신 중복 판정, 원본/outbox 저장, 저장 확인 응답, 관제에 전달/재시도 | 슬롯 승인, 등록 차체/공정의 업무 판정, 품질 집계, GUI용 현재 상태 생성 |
| `operations-service` | Java 21 / Spring Boot | 업무 검증·반영, 관측 상태·이력·집계·알람, REST 조회/알람 확인, SSE | 원본 TCP 접수, 실제 공장 배차·예약·셀 작업 결정 |
| `factory-console` | Vue 3 / JavaScript | 지도·태그·버퍼·품질·알람 표시, 조회 요청, 선택/필터 유지 | 차체 위치·예약·검사 실적 결정, 서비스 DB 직접 접근 |

두 Spring 앱은 각각 빌드·실행·재시작한다. 하나의 저장소에서 관리하며, 서비스 내부의 수집/처리/조회/전송 코드를 책임별 모듈로 나눈다. 모듈마다 별도 서버를 만들지는 않는다. 실제 앱 생성·Wrapper·골격 설정은 S01-01에서 준비했다. [작업 5 해설](<../work-notes/작업 5. 두 Spring 앱의 실행 기반.md>)과 [실행 안내](../../services/README.md)를 따른다. DB·Compose·Python/Vue 기반은 S01-02~04에서 완료했다. [전체 실행 안내](../../infrastructure/README.md)를 따른다.

## 3. 상태 변경 권한

### 3.1 공장의 물리 상태는 Python만 결정한다

Python의 단일 상태 변경 루프가 다음을 결정한다.

- 차체와 태그의 생성·연결, 현재 물리 위치, 공정 시작/완료와 검사 결과.
- 목적지의 슬롯과 가용 AGV 확인, 예약 승인·픽업·인계·반환·출발 전 취소.
- W(대기)+R(유효 예약)≥C(전체 슬롯)일 때 신규 배출 차단.
- 예약 후 실제 픽업 전 차체 유지, 도착 R→W, Bay→셀 투입 시 슬롯 반환.
- 차체/부품 운송 구분, 셀 정지·복구 등의 시뮬레이션 조건.

서버나 화면이 빈 슬롯을 보고 별도로 배차하지 않는다. 통신 단절이나 서버 재시작만으로 예약을 해제하지 않는다. 부품 AMR은 차체 버퍼 슬롯을 사용하지 않는다.

### 3.2 관제 DB는 마지막으로 검증·반영한 관측 상태를 제공한다

`factory_snapshot`은 Python 모델의 복제본이다. 관제 서비스는 차체 단일 위치, 슬롯 소유자, 예약/운송 관계와 용량을 검증한 뒤 최신 보고를 저장한다. 잘못된 보고를 받아 임의로 차체 위치나 슬롯 수를 수정해 정상 상태로 만들지 않는다.

관제 서비스는 검사 fact로 실적·불량률을 계산하고 고장 알람을 판단한다. 운영자의 알람 확인/메모는 관제 데이터의 변경이다. **알람 확인은 Python 셀 복구나 예약 반환이 아니다.** P0 공장 조건 변경은 시뮬레이터 CLI/시나리오로 수행한다. 실제 GUI의 공장 제어 기능을 이번 결정에 추가하지 않는다.

### 3.3 식별자와 구성의 원본

Python은 run과 사건, 차체/태그 등 공장 모델 식별자의 생성 주체다. 셀·Bay·차량·경로·슬롯 수는 시뮬레이터 실행 구성에서 정한다. 관제 DB의 구성/메타데이터 표는 그 정보를 관제에 사용할 수 있도록 등록한 사본이다. 수집 서비스는 run/source ID를 사건 식별자로 보관하되 관제 DB 등록 정보를 직접 조회하지 않는다.

알람 등 관제 자체 기록의 ID는 관제 서비스가 생성한다. ID 형식·등록 사건·참조 순서·버전 호환성은 S00-02~03에서 확정한다. 이 결정은 식별자 생성/관리 책임을 정하며 구체적인 메시지 필드를 미리 확정하지 않는다.

## 4. 데이터 소유권

‘소유’는 해당 서비스가 자기 DB의 데이터를 읽고 쓰며, 마이그레이션·제약·조회와 복구 책임을 가진다는 뜻이다. 데이터의 원본 발생 주체와 DB 사본의 관리 주체는 구분한다.

| 데이터/표 | 관리 주체 | 의미와 공급 경로 |
|---|---|---|
| 공장 모델·예약·차체 위치 | Python 메모리 모델 | 물리 상태의 기준. 사건과 전체 보고로 송신 |
| 송신 미확인 목록 | Python | 수집 저장 확인 전 재전송 책임. P0는 메모리 기반 |
| `raw_event` | 수집 서비스 / `ingestion_db` | 받은 사건 원문과 ID/내용 중복 판정 |
| `event_outbox` | 수집 서비스 / `ingestion_db` | 원본과 함께 저장하는 전달 대기·재시도·전달 결과 |
| `delivery_stream` | 수집 서비스 / `ingestion_db` | S00-03에서 추가한 run/source별 다음 전달 순번·중단/공백 대기 근거 |
| `delivery_action` | 수집 서비스 / `ingestion_db` | S05 V2의 현재 head 명시적 재개: 이전 보류 상태·순번·운영자·이유·시각 |
| `processed_event` | 관제 서비스 / `operations_db` | 업무 반영/거절과 중복 처리 방지 기록 |
| `event_projection` | 관제 서비스 / `operations_db` | 전달받은 사건을 정규화한 화면 조회용 이력 |
| `simulation_run` | 관제 서비스 / `operations_db` | Python 실행 정보를 등록한 관제용 기록 |
| `equipment`, `factory_buffer`, `vehicle` | 관제 서비스 / `operations_db` | 실행 구성에서 받은 셀·Bay·차량 메타데이터 |
| `body` | 관제 서비스 / `operations_db` | Python에서 받은 차체/태그 1:1 메타데이터 |
| `factory_snapshot` | 관제 서비스 / `operations_db` | 같은 보고 시점의 셀·차체·슬롯·차량·활성 운송 |
| `inspection_result` | 관제 서비스 / `operations_db` | 전달받은 검사 사실. 품질 집계의 기준 |
| `operation_history`, `transport_history` | 관제 서비스 / `operations_db` | 작업·차체/부품 운송 사실과 결과 |
| `alarm` | 관제 서비스 / `operations_db` | 관측 고장·신선도에 따른 발생/복구, 운영자의 확인 |
| `alarm_note` | 관제 서비스 / `operations_db` | 운영자 조치 메모. P1이며 P0 구현 필수 아님 |
| 선택·검색·필터·화면 보간 | Vue 브라우저 상태 | 표현을 위한 상태. 업무 상태를 덮어쓰지 않음 |

원본을 수집 DB에 보관하고 관제용 기록을 관제 DB에 만들 수 있다. 이 복제는 서로 다른 목적의 기록이며, 같은 사건을 두 번 생산·검사한 것으로 집계하지 않는다. 관제 이력 조회는 자기 `event_projection`/업무 표를 사용한다.

**2026-10-05 S00-03 보완:** 전달 재개를 DB 행 번호의 최댓값에 의존하지 않도록 delivery_stream의 수집 DB 소유권을 추가했다. raw_event/processed_event에는 동일 원본 비교를 위한 raw_json_text를 보관한다. 서버 수·물리 상태 변경 권한은 그대로다. 상세 저장 경계와 상태값은 [v1 전달 계약](../../contracts/v1/delivery.md)을 따른다.

## 5. DB 접근과 저장 경계

개발 환경은 PostgreSQL 17 인스턴스 하나에서 `ingestion_db`와 `operations_db`를 분리한다. DB 접속 계정도 각각 분리하고 자신의 DB에만 접근하도록 구성한다. 권한·Flyway·실제 연결 검증은 S01-02에서 완료했다. 각 서비스의 일반 앱 계정과 별도 마이그레이션 계정을 두고 상대 DB/관리 DB 접속과 앱 DDL을 금지했다. [DB 실행 안내](../../infrastructure/postgresql/README.md) · [작업 6](<../work-notes/작업 6. 두 DB와 서비스별 저장 구조.md>)를 따른다.

- 수집 서비스만 `ingestion_db`를 읽고 쓴다.
- 관제 서비스만 `operations_db`를 읽고 쓴다.
- Python과 Vue는 두 DB에 직접 접속하지 않는다.
- 다른 서비스의 표를 직접 조회하거나 DB 간 외래키·JOIN을 만들지 않는다. 필요한 정보는 계약된 API/사건으로 교환한다.
- 수집 DB의 원본+outbox는 하나의 저장 단위로 처리한다.
- 관제 DB의 처리 기록+조회용 사건+해당 업무 이력/현재 값은 하나의 저장 단위로 처리한다. 영구 거절은 업무 반영을 취소한 뒤 추적 가능한 기록으로 남긴다.
- 두 DB에 걸친 저장을 하나의 로컬 트랜잭션으로 취급하지 않는다. 재전달과 관제의 중복 처리 방지로 이어 붙인다.

공유 PostgreSQL 인스턴스가 중단되면 두 서비스 DB 모두 영향을 받을 수 있다. 독립 서비스 실행과 별도 DB 소유권은 인스턴스 장애까지 완전히 분리했다는 뜻이 아니다. 별도 DB 서버·다중 인스턴스 운영은 이번 P0 결정에 포함하지 않는다.

## 6. 통신 경계의 소유자

| 경계 | 보내는 쪽 / 받는 쪽 | 책임과 완료 의미 |
|---|---|---|
| TCP/NDJSON | Python → 수집 서비스 | 사건 전송·프레임 검증·원본/outbox 커밋. 수집 응답은 이 저장을 확인 |
| 내부 REST | 수집 서비스 → 관제 서비스 | 영속 전달 대기를 보내고 처리 결과를 기록. 관제 응답은 업무 반영 또는 거절을 확인 |
| 조회 REST | Vue → 관제 서비스 | 차체/태그·셀·Bay·차량 현재 값과 이력 조회 |
| 알람 확인 REST | Vue → 관제 서비스 | 운영자 확인 기록 변경. 공장 물리 상태 변경 아님 |
| SSE | 관제 서비스 → Vue | 한 묶음의 관측 상태·지표·알람과 기준 시각 전달 |
| 시나리오 CLI | 운영자 → Python | 데모 공장 조건 변경 후 새 사건/상태 송신 |

수집 서비스는 저장 확인 이후 관제 전달 책임을 가진다. 관제 서비스가 멈췄다고 Python이 이미 수집 확인을 받은 사건을 다시 보내게 만들지 않는다. 수집 서비스는 남은 outbox를 재전달하고, 관제는 같은 사건의 업무를 다시 적용하지 않는다.

정확한 API 경로, 요청/응답 필드, ACK 상태 이름, 전달 순서·timeout/backoff·상한·오류/격리 정책은 S00-02~04의 계약 작업이다. 수집 완료와 관제 반영 완료가 다르다는 **의미와 책임**은 이 결정에서 확정한다.

## 7. 선택 이유와 영향

수집과 관제를 나누면 TCP 접수/저장과 업무 처리/화면 제공을 각각 실행·검증할 수 있다. 대신 두 서비스 사이에서 전달 실패·중복·반영 지연을 다뤄야 하므로 outbox와 업무 처리 기록을 별도로 관리한다.

차체·태그·슬롯마다 서버를 나누면 같은 물리 상태를 여러 경계에서 맞춰야 한다. 현재 P0는 Python 모델과 관제의 전체 스냅샷 검증 안에서 이 관계를 함께 다룬다. 서버 수를 늘리기보다 두 서비스의 소유권과 실패 동작을 명확히 한다.

기존 Java·Spring·PostgreSQL·Vue·Python·TCP/NDJSON·REST/SSE·Compose를 유지한다. 새 메시지 브로커나 실제 태그 플랫폼을 추가하지 않는다. 실행 기반 코드·이미지 digest·구체 버전은 S01에서 준비했다. 이 ADR 작성 당시 업무 코드와 데이터 연결은 후속 단계였으며 S02~S06에서 최소 실제 흐름을 구현했다.

## 8. 완료 판단과 남은 작업

S00-01의 완료 조건은 다음과 같다.

- 실행 단위와 서비스 내부 모듈을 구분했다.
- 각 영속 표의 소유 DB와 관리 서비스를 하나씩 정했다.
- 공장 상태 변경·예약 권한을 Python 한 곳에 두었다.
- GUI 조회, 알람 확인, 원본 수집, 업무 반영의 경계를 정했다.
- 서비스 DB 직접 공유와 두 DB의 단일 로컬 트랜잭션 가정을 배제했다.

이번 산출물은 설계 문서다. 서비스 기동·DB 권한·중복/장애 동작의 실제 성공은 후속 구현과 검증으로 확인한다. ACK/API의 세부 계약은 아직 미완료이며 S00 전체를 완료로 표시하지 않는다.

이 ADR을 처음 작성한 직후의 작업은 **S00-02: 식별자·시각·순번·이벤트 규격과 예제 정의**다. 처음 읽는 사람을 위한 설명과 이번 작업 기록은 [작업 1 해설](<../work-notes/작업 1. 서비스 책임과 데이터 소유권.md>)에 있다.

**2026-10-05 S05 보완:** 자동 HTTP 전달·진단·재시작 복구를 구현했고 수집 V2의 누적 시도/재개 기록을 추가했다. 기존 표/서비스 소유권과 Python의 물리 변경 권한은 유지한다. 관제는 수집 진단을 HTTP로만 조회한다. 원본 내용 변경·순번 건너뛰기·격리 자동 해제는 제공하지 않는다. [S05 수집 안내](../../services/ingestion-service/README.md).


**2026-10-05 S06 보완:** Python의 명시적 한 차체 시나리오를 기존 송신/수집/자동 전달과 연결했다. 관제 SSE는 REST와 같은 ViewPublisher 묶음을 제공하며 Vue는 셀/버퍼·차체/태그를 관측만 한다. 물리 상태·예약·AGV 배출의 권위는 계속 Python 한 곳에 있다. 새 공유 DB/표/브로커/의존성을 도입하지 않았다. [S06 설명](<../work-notes/작업 27. S06-02 REST와 SSE 전체 상태 연결.md>).


## S07 적용 확인

지도·태그 상세는 같은 전체 관제 묶음을 읽고, 별도 이력/품질/알람 확인 응답은 현재 물리 상태를 변경하지 않는다. Python만 배차·적재·고장/정상화·슬롯 반환을 결정한다. 실제 알람 확인 후에도 고장과 예약이 유지되는 것을 확인했다. 기존 서비스/DB 경계를 유지하고 기획된 ECharts6.1.0을 Vue에 추가했다. [작업31](<../work-notes/작업 31. S07-03 품질 차트와 알람 확인·기록 조회.md>).
