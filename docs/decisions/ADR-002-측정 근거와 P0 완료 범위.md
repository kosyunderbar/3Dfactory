# ADR-002: 측정 근거와 P0 완료 범위

> 결정일: 2026-10-05 · S09 · 기존 스택·서비스 경계 유지

## 결정

물리 모델과 데이터 전달 규칙을 바꾸지 않고 실제 처리 구간을 관측한다. Java 측정은 명시적인 JVM 파일 옵션, 브라우저 측정은 개발 모드의 명시적인 환경 변수로만 켠다. 일반 실행과 프로덕션 UI에 측정 버튼·내부 구간·검증 제어를 추가하지 않는다.

측정 도구는 사용자 DB와 분리된 PostgreSQL·Java·Vue 프로세스를 소유한다. 성공한 측정 UUID의 원본 바이트·해시와 두 DB를 대조한 뒤 자기 run 행만 정리해 반복 조건을 맞춘다. 실패 데이터, 원본 NDJSON, 실행 계획·측정 파일과 로그는 보존한다. 자격 정보는 공유 산출물에서 제외한다.

## 유지한 규칙

| 규칙 | 이유와 의미 |
|---|---|
| 두 Spring 서비스·두 소유 DB | 수집 저장과 관제 업무 반영·조회 책임을 분리한다. 공통 PostgreSQL 인스턴스의 장애까지 분리한 것은 아니다 |
| TCP 저장 ACK와 HTTP 업무 결과 구분 | ACK는 수집 commit 확인이며 화면 완료나 관제 commit을 대신하지 않는다 |
| Python 단일 writer·원본 한 건 in-flight | 공장 전환·순번·재전송 원본을 유지한다. 처리량을 높이기 위해 동시 writer를 추가하지 않는다 |
| 목적지 예약 R은 배차 승인부터 차지 | 픽업 전과 이동 중의 예약도 가용 슬롯을 소모한다. `W+R≥C`이면 신규 배출을 막고 이미 예약한 AGV는 도착한다 |
| 현재 상태는 전체 snapshot, 품질은 고유 검사 fact | 최신 관측값과 누적 실적의 책임을 분리한다. 늦은 고유 사실과 중복 입력을 구분한다 |
| 가상 tagId는 차체 조회 식별자 | 차체 상태를 GUI로 조회한다. 무선 태그·센서·현장 위치 측정 장비를 구현하지 않는다 |
| 흰 바탕·네이비 글씨·파랑 계열 표현 | 사용자 지정 UI 기준을 그대로 유지한다. 텍스트 상태와 접근 가능한 상세도 유지한다 |

서비스 책임의 상세 근거는 [ADR-001](<ADR-001-서비스 책임과 데이터 소유권.md>)에 있다.

## 측정 결과의 해석

고유 commit 수를 실제 처리량으로 기록한다. 요청 빈도·전송 시도·재전송 수를 생산 실적으로 쓰지 않는다. 100·300·500 events/s 목표를 실제 입력기로 만들지 못했다면 해당 입력량의 서버 처리 능력은 미검증으로 남긴다.

SSE는 최신 전체 상태를 묶으므로 모든 입력 사건을 화면 프레임으로 대응시키지 않는다. 실제 화면에서 관측한 sourceSeq를 원본의 수신 시각과 연결한다. 내부 구간은 같은 프로세스의 monotonic clock, 종단 구간은 단일 호스트 시계 차이를 포함한 추정치다. `nextTick`과 다음 렌더 프레임은 물리 디스플레이 표시 완료의 직접 측정이 아니다.

실제 Chrome의 전경 표본과 해상도를 기록한다. 충족하지 못한 기준 화면 크기나 부족한 전경 표본을 목표 달성으로 표시하지 않는다. 실제 부하의 예열·활성·배출 시간을 구분하고 p95를 단순 합산하지 않는다.

SQL의 10만 합성 로그와 품질의 실제 검사 사실을 구분한다. 실제 실행 계획과 동일 조건 비교에 의미 있는 병목이 있을 때만 인덱스 변경을 채택한다. 검증 전용 임시 인덱스를 운영 마이그레이션이라고 설명하지 않는다. 예열 결과를 cold cache 결과라고 부르지 않는다.

## 후속 조건

P0는 3셀·AGV 2대·AMR 1대의 실제 연결과 예약·차체·검사·복구를 다룬다. 100대 차체 정확성 결과는 수백 대 차량 성능이 아니다. 교통 경로 충돌·복잡한 자원 순환 전체의 교착 상태 부재 증명, 실장비 통신, Python 비정상 종료 후 물리 상태 영속 복원, 고가용성·다중 인스턴스·운영 인증은 이번 완료 범위에 포함하지 않는다.

실제 값·최적화 채택 여부·P0 근거와 시연은 [S09 측정·완료 기록](<../development/S09 측정·완료 기록.md>)에서 확인한다. 성능 목표는 결과와 분리해서 남기며 실패하거나 미측정인 목표를 완료 숫자로 바꾸지 않는다.

## S09에서 확인한 최종 결정

검증 전용 fence index의 warm SQL 개선은0.016ms이며7.41MiB 추가 공간과 삽입 갱신 비용이 있어 채택하지 않았다. 기존 설비/시간순 로그 첫 페이지 API p95는12.77/3.92ms로500ms 목표 안이다. 순차 API 전후 값에는 cache/JIT 영향도 포함되므로 index 인과 효과로 확정하지 않는다. 새 DDL·운영 마이그레이션·의존성을 추가하지 않고 수집V1/V2·관제V1을 유지했다.

높은 입력 목표는 단일 ACK 대기 생성기가 만들지 못했고 관제 전달 대기/SSE 지연도 관측했다. 이번 단계에서는 측정 결과와 한계를 남겼다. 높은 부하 개선은 원본 보존·순번·멱등 규칙을 유지하면서 생성기와 전달 transaction을 따로 평가하는 후속 작업으로 둔다. 같은 호스트/설정의 완료 반복8+4회에는 새 JVM/PG와 물리 cache/uptime 차이가 있음을 남겼다.

선택8개 표의 같은 data 재시작 지문·이력과 새 실제5대 시연을 확인했다. 21초 단계 영상은 실제7장 캡처 재생이며 연속 녹화와 구분한다. 기본 비활성 계측은 업무 책임을 바꾸지 않고 개발/검증 시에만 켠다. Python의 메모리 물리 상태 자동 영속 복원과 수백 대 차량/기준 해상도 GPU 성능은 이 결정으로 보장되지 않는다.
