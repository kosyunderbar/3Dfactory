# 작업 6. 두 DB와 서비스별 저장 구조

> 작업 ID: S01-02 · 완료일: 2026-10-05  
> 결과: 실제 PostgreSQL 17.11에서 두 DB·계정 권한·서비스별 Flyway V1 마이그레이션 확인 완료. Compose와 공장 업무 기능은 이후 작업이다.

## 1. 이번 작업은 무엇인가

작업 5에서 프로그램 두 개를 만들었다. 이번에는 **각 프로그램이 자료를 저장할 공간과 그 공간의 출입 권한**을 준비했다.

수집 앱은 공장 보고서의 원문과 아직 전달하지 못한 목록을 ingestion_db에 보관한다. 관제 앱은 차체/태그 등록, 마지막 확인 상태, 검사/작업/운송 이력과 알람을 operations_db에 보관한다. 같은 PostgreSQL 서버에 있어도 서로 다른 DB다. 각 앱이 상대 DB를 직접 읽고 쓰지 않고 정해진 사건/API로 자료를 주고받게 만드는 기반이다.

이번에는 DB 구조가 실제로 만들어지고 권한이 작동하는지 확인했다. Python 차체를 생성하거나 보고서를 실제 수집·처리하는 기능은 아직 없다.

## 2. DB와 계정은 각각 무슨 역할인가

DB는 저장 공간이고, 표는 그 안에서 종류별로 자료를 담는 칸이다. 계정은 그 공간에 들어올 때 사용하는 이름이다. 비밀번호가 맞아도 그 계정에 허용하지 않은 DB에는 들어갈 수 없다.

| 공간 | 데이터를 사용하는 계정 | 구조를 바꾸는 계정 |
|---|---|---|
| ingestion_db | ingestion_app | ingestion_migrator |
| operations_db | operations_app | operations_migrator |

앱 계정은 자기 DB의 자료를 읽고 추가·수정·삭제할 수 있다. 표 자체를 새로 만들거나 지우는 권한은 없다. 구조 변경은 Flyway용 계정이 맡는다. 관리자 권한, 새 DB/계정 생성 권한도 이 네 계정에 주지 않았다.

자료 한 행을 삭제하는 것과 표 전체를 없애는 것은 다르다. 앱은 업무에 필요한 행 변경만 수행하고, 표 구조는 검토된 마이그레이션으로 변경한다. 서로 다른 서비스의 DB와 관리용 postgres DB 접속도 차단했다.

## 3. Flyway는 무엇인가

Flyway는 ‘DB 구조를 어떤 순서로 만들고 바꿨는지’를 관리한다. 이번에는 각 앱에 **V1** SQL 파일을 하나씩 만들었다.

앱이 일반 모드로 시작하면 Flyway는 자신의 DB에서 적용 이력을 확인한다. V1이 없으면 적용하고, 이미 적용했다면 다시 실행하지 않는다. 이후 변경은 V2, V3로 추가한다. 적용한 파일을 수정하면 체크섬이 달라져 검증 오류로 드러난다.

‘앱을 껐다 켰다’는 이유로 DB를 초기화하지 않는다. 이번 SQL에는 기존 표/데이터를 지우는 DROP/TRUNCATE나 가짜 생산 실적이 없다. clean도 금지했다. 앱 계정이 Flyway 이력의 내용을 바꾸는 권한도 제거했다.

초기 DB/계정 준비와 Flyway 재실행은 다른 작업이다. 초기 준비는 새 전용 인스턴스에서 한 번만 실행하고, 이미 역할/DB가 있으면 덮어쓰지 않고 거절한다. Flyway는 같은 DB에서 반복 시작해도 적용된 버전을 유지한다.

## 4. 어떤 자료를 저장하나

수집 DB는 표 3개다.

| 표 | 쉬운 뜻 |
|---|---|
| raw_event | 공장 보고서 원문과 ID·순번·수신 시각·원문 해시 |
| event_outbox | 관제에 전달할 보고서, 시도 횟수·다음 시각·전달/격리 결과 |
| delivery_stream | 실행별 다음 전달 순번과 중단/공백 대기 상태 |

관제 DB는 기존 소유권 문서의 표 13개다. run/설비/Bay/차량/차체 등록, 처리 사건/조회 이력/현재 스냅샷, 검사/작업/운송 fact, 알람과 P1 메모 공간이다. 메모 표가 있다고 메모 API까지 만든 것은 아니다. 각각의 Flyway 이력 표는 이 16개 업무 표와 별도다.

태그가 같은 실행의 서로 다른 차체를 가리키지 못하는 고유 조건, 같은 검사/사건의 중복 방지 조건, 참조 관계와 기본 수량/상태 조건을 준비했다. 보고서 원문의 SHA-256도 원문 바이트에서 계산한 값과 일치해야 한다.

Bay의 실제 대기·예약·슬롯 소유는 **한 공장 스냅샷 JSON**에 함께 보관한다. DB 이력을 보며 W/R을 따로 더하거나 통신 단절로 예약을 해제하지 않는다. W+R≥C의 물리 배차 규칙은 이후 Python 모델과 관제 검증 코드에서 구현한다.

저장할 수 있게 표를 만든 것과 그 자료를 올바르게 처리하는 코드를 만든 것은 다르다. 상세 JSON 검증, 동일 원본 비교·ACK, 예약/차체 보존, 늦은 사실 반영 등은 S02~S05에서 구현하고 해당 변경 때 필요한 사례만 확인한다.

## 5. 앱 설정도 어떻게 달라졌나

일반 실행에는 서비스마다 DB URL과 두 계정의 사용자/암호, 총 **5개 설정**이 필요하다. 예를 들어 수집 앱은 다음 이름을 사용한다.

```text
INGESTION_DB_URL
INGESTION_DB_USERNAME
INGESTION_DB_PASSWORD
INGESTION_MIGRATION_USERNAME
INGESTION_MIGRATION_PASSWORD
```

관제 앱은 OPERATIONS_로 시작한다. 기본 DataSource는 앱 계정, Flyway는 구조 변경 계정을 사용하지만 같은 서비스 DB URL을 바라본다. 설정이 없거나 비어 있으면 필요한 이름을 알려주고 종료한다. 실제 암호를 문서/코드/명령줄에 넣지 않았다.

작업 5의 bootstrap은 계속 DB 없는 골격 확인용이다. 일반 실행에서 자동으로 선택하지 않는다. Docker/Compose와 readiness는 다음 작업에서 준비하므로 이번 결과를 ‘전체 관제가 실행된다’고 쓰지 않는다.

## 6. 실제 검증과 결과

환경에 Docker/기존 PostgreSQL이 없어서 공식 PostgreSQL **17.11** 소스와 SHA-256을 확인한 뒤 /tmp 전용 경로에 빌드했다. 사용자 전역 설치나 다른 DB는 건드리지 않았다. 검증은 새 프로젝트 전용 클러스터에서 했으며, SQLite/가짜 메모리 DB를 사용하지 않았다.

실제 실행 명령:

```sh
FACTORY_PG_BIN=/tmp/factory-pg-17.11/bin python3 scripts/verify-databases.py
```

스크립트 안에서 두 앱은 각각 다음 최소 사례만 실행했다. 플래그/DB 접속값은 새 검증 클러스터용으로 스크립트가 환경 변수로 전달한다.

```sh
scripts/service-maven.sh ingestion-service --offline --batch-mode --no-transfer-progress -Dtest=DatabaseMigrationTests verify
scripts/service-maven.sh operations-service --offline --batch-mode --no-transfer-progress -Dtest=DatabaseMigrationTests verify
```

| 확인 | 실제 결과 |
|---|---|
| 수집 Flyway V1 + 자기 DB 쓰기 | BUILD SUCCESS, Tests run: 1 / Failures: 0 / Errors: 0 |
| 관제 Flyway V1 + 자기 DB 쓰기 | BUILD SUCCESS, Tests run: 1 / Failures: 0 / Errors: 0 |
| Flyway 재실행 | 새 적용 0건, 이미 넣은 확인용 행 유지 |
| 상대 서비스 DB와 postgres 접속 | 두 앱 모두 SQLSTATE 42501로 거절 |
| 앱 계정의 표 생성 | 두 앱 모두 SQLSTATE 42501로 거절 |
| 앱의 Flyway 이력 UPDATE 권한 | 두 앱 모두 없음 |
| 생성된 업무 표 | 수집 3개 + 관제 13개 = 16개 |
| 기존 DB 초기 준비 재요청 | 덮어쓰기 없이 거절 |
| 문서·진행 상태 | 로컬 링크 182개 연결 확인, S01-02 완료/S01-03 미착수 |
| 검증 서버 정리 | 이 검증 인스턴스만 종료, 데이터·로그 보존 |

첫 기동에서 긴 프로젝트 경로가 macOS Unix 소켓의 103바이트 제한을 넘었다. 데이터는 계속 workspace에 두고 소켓만 짧은 /tmp 디렉토리로 바꿔 해결했다. 같은 실패 조건을 해결한 뒤 다시 실행했고, 통과 후 전체 테스트나 기존 bootstrap/사건/GUI 검증으로 확대하지 않았다.

증거는 `.build-cache/database-verification/20261004T163640Z-bbc5e89a/`에 있다. UTC 실행번호라 한국 날짜와 하루 다르게 보일 수 있다. result.json에는 표 수·실행 결과·종료 여부가 남고 각 서비스 로그/테스트 결과에는 Flyway 성공과 최소 테스트 통과가 남는다. 자동 생성한 서로 다른 암호는 해당 비공개 폴더의 0600 파일에만 보관하며 출력하지 않았다.

검증용 행은 정확한 ID로만 정리했고 구조/이력을 초기화하지 않았다. 상시 DB가 계속 켜져 있는 상태는 아니다. 새로운 검증을 요청하면 새로운 클러스터를 만들며 이전 데이터를 자동 삭제하지 않는다.

소스 빌드/검증 도구를 다시 준비하는 방법, 초기 SQL·권한·마이그레이션 경계는 [PostgreSQL 실행 안내](../../infrastructure/postgresql/README.md)에 있다. 실제 입력 처리·DB 업무 제약의 전체 사례·운영 복구/성능·Compose·GUI는 이번에 검증하지 않았다.
