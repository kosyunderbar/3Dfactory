# 작업 38. S09-02 SQL과 실제 화면 비용 확인

> 작업 ID: S09-02 · 2026-10-05 · 완료 · 결과: [S09 측정·완료 기록](<../development/S09 측정·완료 기록.md>)

이번 작업은 조회와 화면 갱신에서 시간이 어디에 쓰이는지 확인합니다. 느릴 것 같은 곳을 미리 바꾸는 대신 실제 실행 계획과 시간을 확인합니다.

## SQL과 인덱스의 역할

SQL은 DB에서 원하는 행을 찾는 요청입니다. 인덱스는 원하는 기록을 빠르게 찾는 색인입니다. 색인을 추가하면 읽기가 빨라질 수 있지만 디스크를 더 쓰고 새 기록을 저장할 때도 색인을 갱신해야 합니다.

로그 조회에는 기간·실행·설비 필터, 최신순 정렬과 페이지 경계가 있습니다. 페이지 조회 중 새 사건이 들어와도 다음 페이지에 갑자기 끼어들지 않도록 최초 페이지에서 기록 번호의 상한인 commit fence를 고정합니다. 이 번호의 최댓값을 찾는 비용도 실제 조회 비용에 포함됩니다.

## 두 종류의 데이터

[SQL·시연 도구](../../scripts/measure-sql-demo.py)는 별도 DB에 고정 규칙의 합성 로그 10만 건을 만듭니다. 특정 설비의 기간 로그와 전체 시간순 로그를 같은 조건으로 조회합니다. 품질은 S08의 실제 100대 원본을 재생한 검사 사실 100건으로 집계합니다.

합성 로그는 SQL 조회용이며 TCP로 수용한 실제 생산 이벤트 수가 아닙니다. 검사 100건의 결과를 “10만 건 품질 집계 성능”으로 표현하지 않습니다.

## 개선을 판단하는 방법

`EXPLAIN (ANALYZE, BUFFERS)`는 DB가 어떤 방식으로 행을 찾았고 얼마나 걸렸는지 보여 줍니다. 최초 관측과 예열 후 값을 분리하고, 5회 예열 뒤 50회 실제 API 시간을 기록합니다. OS 캐시를 비우지 않으므로 cold cache 성능이라고 주장하지 않습니다.

임시 인덱스는 검증 전용 DB에만 만들어 같은 데이터·기간·설비·페이지 크기로 비교합니다. 실제로 의미 있는 병목이 확인됐을 때만 추가 마이그레이션을 반영합니다. 읽기 시간뿐 아니라 인덱스 크기와 동일한 롤백 삽입 비용도 기록합니다. 최종 판단과 수치는 통합 기록에 있습니다.

## 화면 비용

실제 Chrome에서 SSE 수신 후 Vue `nextTick`과 다음 렌더 프레임까지의 시간을 기록합니다. 지도·슬롯·태그는 같은 관측 묶음을 사용합니다. 개발 측정 모드에서는 ECharts의 `setOption` 호출 비용도 관측합니다.

프레임 간격은 브라우저의 `requestAnimationFrame` 관측값입니다. 디스플레이 표시 완료나 GPU 프레임을 직접 측정한 값이 아닙니다. 숨겨진 탭·비활성 창·실제 해상도 조건을 분리하고, 부족한 표본이나 목표 미달을 통과로 표시하지 않습니다.

## 이번 실제 결과

로그10만 건의 기존 API p95는 설비12.770ms·전체 시간순3.916ms, 실제 검사100건 품질은1.000ms였습니다(5회 예열 후50회). 기간·run·설비·첫20건을 고정하고 임시 index 전/후의 페이지 식별자도 같았습니다.

**운영 인덱스를 추가하지 않았습니다.** fence SQL의 개선은0.016ms이고 index는 약7.41MiB를 차지했습니다. 동일1,000행 rollback 삽입 p50은34.276→35.130ms였습니다. API 감소에는 cache/JIT의 순차 진행 영향도 있어 모두 index 효과라고 설명하지 않습니다. 임시 index만 삭제하고 관제 Flyway V1을 유지했습니다.

새 실제 화면의 Vue→프레임463표본 p95는6.10ms, ECharts13회 호출 p95는22.80ms였습니다. 작은 화면·일시정지/상세 전환의 조건부 관측이며 기준 해상도 전체 지도 성능으로 확대하지 않습니다. 구체적인 화면 병목이 확인되지 않아 화면 동작/색상과 기존 차트 구성을 유지했습니다.
