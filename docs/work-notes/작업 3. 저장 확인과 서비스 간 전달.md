# 작업 3. 저장 확인과 서비스 간 전달

> 상태: 완료 — 전달 계약·기본값·예제와 필요한 자료 확인  
> 선행 작업: [작업 2](<작업 2. 식별자와 사건 데이터 규격.md>)

## 1. 이번 작업의 의미

작업 2에서는 보고서에 적을 항목을 정했다. 이번에는 **보고서를 보낸 뒤 무엇을 확인해야 하고, 실패하면 어떻게 이어가는지**를 정했다. 기준은 [v1 전달 계약](../../contracts/v1/delivery.md)에 기록했다. 이번 산출물은 규칙·요청/응답 예제·기본 설정값이며 실제 서버가 실행되는 단계는 아니다.

차체 검사 보고를 예로 들면, Python이 보냈다는 사실만으로 DB에 남았다고 할 수 없다. 또 수집 서비스가 저장했다고 해서 관제 화면에 검사 결과가 반영된 것도 아니다. 이 두 확인을 구분해야 보고서를 잃거나 같은 검사를 두 번 세는 문제를 다룰 수 있다.

## 2. 두 가지 답장은 무엇인가

| 답장 | 누가 보내나 | 확인한 내용 |
|---|---|---|
| 수집 ACK: RECEIVED | 수집 → Python | 원본 보고서와 전달 대기를 수집 DB에 저장함 |
| 관제 결과: APPLIED | 관제 → 수집 | 검사/작업/상태 기록과 처리 확인을 관제 DB에 반영함 |
| DUPLICATE_RECEIVED | 수집 → Python | 같은 원본이 이미 저장돼 있음 |
| DUPLICATE_APPLIED | 관제 → 수집 | 같은 보고서의 업무가 이미 반영돼 있음 |
| RETRY_LATER | 두 경계 모두 | 지금 성공으로 확정할 수 없으므로 원본을 유지함 |
| REJECTED | 두 경계 모두 | 형식·ID·업무 규칙 등의 문제가 있어 그대로 성공 처리할 수 없음 |

ACK는 ‘처리 결과를 알려주는 답장’이다. 같은 REJECTED라도 어느 경계에서 받았는지에 따라 기록과 대응이 다르다. 응답에 kind와 버전을 넣어 그 의미를 구분한다.

Python은 수집 저장 성공을 확인한 보고서부터 자기 송신 목록에서 제거한다. 이제 전달할 책임은 수집 서비스의 outbox에 있다. 관제가 잠시 꺼져 있다고 이미 저장한 검사를 Python에서 다시 발생시키는 것은 아니다.

## 3. 저장했는데 답장만 끊기면 어떻게 되나

1. 수집 서비스가 검사 보고서와 outbox를 저장한다.
2. 그 직후 연결이 끊겨 Python이 답장을 못 받는다.
3. Python은 **같은 번호·같은 원본**으로 다시 보낸다.
4. 수집은 저장된 원본을 확인하고 DUPLICATE_RECEIVED를 응답한다. outbox를 하나 더 만들지 않는다.

관제에서도 같다. 관제가 검사 기록을 저장한 뒤 답장만 끊기면, 수집은 같은 원본을 다시 전달한다. 관제는 DUPLICATE_APPLIED를 응답하고 생산량을 다시 올리지 않는다.

반대로 DB 저장이 실패했는데 RECEIVED라고 답하면 Python은 자기 원본을 지워 버릴 수 있다. 그래서 성공 답장은 **커밋이 끝난 뒤** 보낸다는 약속이 필요하다. 실제로 지켜지는지는 후속 DB/통신 구현에서 확인한다.

## 4. 같은 원본은 어떻게 구분하나

ID가 같고 내용도 같아야 같은 보고서다. 같은 검사 번호인데 FAIL을 PASS로 바꾸면 정상 재전송이 아니다.

원본에는 SHA-256이라는 방식으로 만든 64자리 해시를 붙인다. 해시는 내용 확인을 돕는 값이고 보고서 ID를 대신하지 않는다. ID·해시·원본 바이트를 함께 비교한다.

이번 P0에서는 Python이 보고서를 한 번 글자로 만들고 그 글자를 그대로 다시 보내도록 정했다. 읽기 좋게 공백을 추가하거나 항목 순서를 바꾸는 것도 원본 변경이다. 내부 REST에서도 그 원본을 문자열로 담아 전달한다. 서로 다른 언어가 보고서를 다시 써서 달라지는 일을 피하기 위해서다.

## 5. 왜 ‘다음 전달 순번’을 DB에 남기나

전달 worker는 outbox에서 보고서를 꺼내 관제로 보내는 반복 작업이다. 수집 서버를 다시 시작하면 worker의 기억도 사라진다. 그래서 `delivery_stream` 표에 ‘이 run에서 다음으로 보낼 순번’을 저장하기로 했다. 소유자는 수집 서비스이며 다른 서비스가 이 DB에 직접 들어가지 않는다.

예를 들어 다음 전달 순번이 35인데 36만 보이면, 36부터 보내지 않는다. 35가 도착할 때까지 기다리고 오래 비어 있으면 누락 대기로 표시한다. DB 행 번호가 가장 크다는 이유로 앞의 사건을 모두 처리했다고 가정하지 않는다.

관제의 성공 응답을 확인하면 outbox의 완료 표시와 다음 순번 증가를 한 번의 DB 저장 묶음으로 처리한다. 이 저장이 실패하면 같은 35번을 다시 보내고 관제의 중복 확인을 받는다.

예약 이력과 전체 상태도 구분한다. SLOT_RESERVED를 받았다고 예약 수를 더한 뒤 스냅샷의 예약 수를 또 더하지 않는다. 물리 예약은 계속 Python이 결정한다.

## 6. 일시 장애와 잘못된 보고서는 다르게 다룬다

| 상황 | 이번에 정한 대응 |
|---|---|
| 관제 서버가 잠시 꺼짐 | 원본을 유지하고 간격을 늘려 재전달 |
| 반복 실패가 정한 횟수를 넘음 | 재시도 보류로 표시. 원본을 남기고 원인 해결 후 명시적 재개 |
| 차체 등록이 아직 안 보임 | 등록 정보를 가정하지 않고 기다림. 오래 해결되지 않으면 의존성 대기로 보류 |
| 슬롯/차체 관계가 모순됨 | 거절 근거와 원본을 남기고 해당 run의 전달 중단 |
| 같은 ID의 내용이 바뀜 | 정상 기록을 덮어쓰지 않고 충돌로 기록 |
| 요청 경로나 버전이 잘못됨 | 프로그램/설정 문제로 보류. 사건을 성공으로 넘기지 않음 |

격리(QUARANTINED)는 잘못된 보고서를 반영하지 않고 원본과 오류 근거를 보존하는 것이다. **차체를 실제 Parking Bay로 옮긴다는 뜻이 아니다.** 뒤 보고서도 자동으로 건너뛰지 않는다. 그렇지 않으면 검사 결과가 빠진 run을 정상 완료처럼 보여 줄 수 있다.

영구 업무 오류가 있는 run은 원인 수정 후 새 run으로 다시 검증한다. 통신 장애처럼 원본 자체가 정상인 경우는 같은 원본으로 재개할 수 있다. 다른 run의 처리는 계속할 수 있도록 경계를 둔다.

오래된 검사 사실이 나중에 도착하는 것과 모순된 입력도 다르다. 참조와 내용이 유효한 미반영 검사 사실은 보관하고, 과거 스냅샷으로 현재 차체 위치를 되돌리지 않는다.

## 7. 소프트웨어 대기장과 차체 Bay는 다르다

| 대기 공간 | 담는 것 | 가득 찼을 때 |
|---|---|---|
| 물리 Bay | 차체의 실제 대기와 도착 예약 | W+R≥C이면 신규 배출 차단 |
| Python 송신 목록 | 아직 수집 저장 확인을 못 받은 보고서 | 물리 계산을 일시 정지하고 원본을 배출 |
| 수집 outbox | 수집 저장 후 관제 전달 책임이 남은 보고서 | 새 보고서 접수를 제한하고 이미 받은 원본 유지 |

둘 다 무한히 늘릴 수 없지만 계산 대상이 다르다. 서버 대기장이 가득 찼다고 차체 예약을 취소하거나 Bay의 R을 0으로 만들지 않는다.

기본값은 [전달 기본값 JSON](../../contracts/v1/delivery-policy.json)에 기록했다. Python은 미확인 1건씩 전송하고, 한 보고서의 자동 시도는 10회, 수집의 내부 전달은 20회로 제한한다. 재시도 간격은 0.5초부터 늘어나 최대 30초다. 횟수가 끝나도 원본을 삭제하지 않는다.

Python 대기가 한도에 가까워지면 물리 상태를 먼저 바꾸고 보고서를 버리지 않도록 **tick 확정 전에** 멈춘다. 이 자동 정지가 해소되면 재개할 수 있지만 운영자가 일부러 멈춘 공장은 자동으로 켜지 않는다.

## 8. 시간 필드와 버전의 주의점

committedAt은 수집이 ‘저장된 것을 확인했다’는 응답 시각이다. 중복 답장에서는 달라질 수 있다. 관제의 appliedAt은 처리 기록에 보관한 시각이고 중복 답장은 기존 값을 돌려준다. 응답은 실제 커밋 뒤에 보내며, 이 기록 시각을 DB 커밋 순간을 정밀하게 측정한 값으로 설명하지 않는다.

HTTP의 Retry-After는 **초**, 응답 본문의 retryAfterMs는 **밀리초**다. 예제에서는 500ms를 본문에 넣으면 헤더에는 올림해 1초를 적는다. 수집은 더 긴 안내 시간을 지킨다.

schemaVersion은 보고서의 항목 양식, protocolVersion은 전달 요청/답장 양식의 버전이다. 현재는 모두 1만 지원한다. 나중에 바뀌면 받는 쪽부터 준비하고 Python은 새 run으로 전환한다. DB에 보관한 옛 보고서의 버전만 바꿔 재사용하지 않는다.

이번 확인은 예제의 형식·의미만 확인한다. 네트워크/DB 동작을 흉내 낸 테스트로 저장 보장이 구현됐다고 쓰지 않는다. 실제 구현 단계에서 필요한 실패 사례만 확인한다.

Python 표준 라이브러리만 사용했고 새 패키지를 설치하지 않았다. 실제 출력은 다음과 같다.

```text
PASS: raw byte/hash correlation; 5 TCP ACKs, 7 HTTP results; seconds/ms and bounded retries; source/outbox attempts=10/20; failure ACK cannot promise commit.
```

통과 뒤 같은 예제 확인을 반복하거나 GUI/전체 테스트로 확대하지 않았다. 관련 문서의 링크·완료 상태와 추가된 표의 단일 소유권만 Python의 일회성 문서 확인 명령으로 별도 확인했다. S00은 진행 중이며 다음 작업은 S00-04다.
