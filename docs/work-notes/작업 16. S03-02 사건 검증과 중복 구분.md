# 작업 16. S03-02 사건 검증과 중복 구분

> 작업 ID: S03-02 · 완료일: 2026-10-05 · 상태: 완료  
> 기준: [사건 계약 v1](../../contracts/v1/events.md) · [전달 계약 v1](../../contracts/v1/delivery.md)

수집 서버가 받은 보고서의 양식과 식별 번호를 검사하고, 다시 들어온 원본과 번호 충돌을 구분하도록 구현했다. 통신이 끊겼다가 같은 보고서를 다시 보내는 일은 정상적인 복구 과정이다. 반면 기존 번호에 다른 내용을 넣으면 저장 이력이 모순되므로 거절해야 한다.

## 양식과 번호의 역할

schemaVersion은 보고서 양식의 버전이다. runId는 공장 실행 번호, sourceId는 송신 프로그램 번호, eventId는 사건 자체의 UUID, sourceSeq는 같은 송신원이 만든 사건의 순번이다. 네 번호가 같은 원본을 식별하는 기준이 된다.

[Protocol.java](../../services/ingestion-service/src/main/java/dev/factory/ingestion/receiver/Protocol.java)는 UTF-8·JSON 문법과 v1 봉투·17종 payload를 검사한다. 잘못된 UTF-8, BOM/CRLF/빈 줄, 중복 JSON 키, NaN/Infinity와 뒤에 붙은 또 다른 JSON을 거절한다. 필수 항목 누락·정의하지 않은 키·숫자 대신 boolean/문자열·범위를 넘는 순번·실제로 없는 날짜·잘못된 ID·상태값도 거절한다.

공장 구성과 전체 스냅샷은 내부 객체까지 필수 키·자료형·열거값·숫자 범위를 확인한다. 설정은 speed=1, 슬롯 capacity=2~4 등 기존 규격을 유지한다. 검사 설비 ID는 QC-01로 제한한다. nullable 항목은 값이 null일 수 있다는 뜻이며 키 생략을 뜻하지 않는다. 미지원 정수 버전은 UNSUPPORTED_SCHEMA다.

이는 수집 단계의 형태/값 검사다. “이 차체가 앞서 등록되었나”, “이 예약과 차량의 실제 소유 관계가 맞나”, “스냅샷의 대기+예약 합계가 물리 목록과 같은가” 같은 사건 사이의 업무 관계는 S04 관제 서비스에서 검사한다. 수집 성공을 물리 모델 검증 완료라고 해석하지 않는다.

## 다시 보낸 원본을 판정하는 방법

[EventStore.java](../../services/ingestion-service/src/main/java/dev/factory/ingestion/receiver/EventStore.java)는 이미 커밋된 원본에서 다음을 확인한다.

| 입력 | 결과 |
|---|---|
| 같은 run/eventId, 같은 run/source/순번, 같은 원본 바이트·SHA-256 | DUPLICATE_RECEIVED, 추가 저장 없음 |
| 같은 eventId인데 순번이나 원본이 다름 | ID_CONFLICT |
| 같은 sourceSeq인데 eventId가 다름 | SEQUENCE_CONFLICT |
| 기존 run에서 sourceId가 바뀜 | SOURCE_CONFLICT |

SHA-256은 원본 바이트를 비교하는 요약값이다. LF를 제외한 실제 UTF-8 원본으로 계산하며 해시와 원본 자체를 모두 비교한다. JSON을 새로 직렬화해서 비교하지 않는다. 내용이 같은 JSON이어도 공백이 추가되어 원본이 달라지면 기존 ID의 다른 원본이다. 기존 정상 기록을 덮어쓰거나 새 번호를 만들어 우회하지 않는다.

식별자를 모두 검증할 수 있으면 ACK에 네 번호와 해시를 연결한다. 하나라도 읽을 수 없으면 네 번호를 전부 null로 둔다. 불완전한 프레임은 해시도 null이다. Python이 다른 사건을 잘못 확인 처리하지 않도록 하기 위한 규칙이다.

## 최소 확인 결과

S03의 공통 명령은 다음과 같다.

```sh
python3 scripts/verify-databases.py --suite ingestion
```

최종 Java 7개가 통과했다. 이번 검증에서는 17종 계약 예제의 형태를 실제 Java 검증기로 확인하고, 대표 문법/필수 필드/자료형/날짜/버전 오류를 거절했다. 실제 PostgreSQL에서는 같은 원본 재전송은 1건을 유지하고, 원본 공백 변경·순번 변경·다른 eventId·source 변경은 각 충돌 코드로 구분했다. 거절/상한 초과 입력이 기존 원본과 outbox를 바꾸지 않는 것도 확인했다.

오류 사례를 무한히 나열하는 방식으로 테스트를 늘리지 않았다. 핵심 문법과 번호 충돌 경계를 세 개의 단위 테스트 및 실제 저장 시나리오에 묶었다. 최종 증거는 작업 15와 같은 S03 검증 기록이다. 이후 QC-01 고정값과 내부 숫자 범위/자료형을 추가 점검한 변경은 ReceiverUnitTests 3개만 재확인했으며 모두 통과했다. 추가 단위 증거는 `.build-cache/s03-final-schema-tests.log`다.

다음 S03-03은 “검증을 통과했다”와 “실제로 저장됐다” 사이를 연결한다. 검증만 끝났다고 성공 ACK를 보내면 DB 장애 때 보고서가 사라질 수 있다.
