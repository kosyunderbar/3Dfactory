# 작업 37. S09-01 실제 입력 부하와 구간별 지연 측정

> 작업 ID: S09-01 · 2026-10-05 · 완료 · 결과: [S09 측정·완료 기록](<../development/S09 측정·완료 기록.md>)

이번 작업은 “데이터가 제대로 전달되는가”에 이어 “어느 정도의 입력에서 얼마나 늦게 전달되는가”를 확인하는 작업입니다. 운영 기능을 추가하는 작업은 아닙니다.

## 각 프로그램이 하는 일

Python은 공장 상태를 결정하고 보고서를 만듭니다. 수집 서버는 TCP로 보고서를 받아 DB에 저장한 뒤 ACK를 보냅니다. 전달 worker는 영속 outbox의 보고서를 관제 서버에 HTTP로 보냅니다. 관제 서버는 업무 기록과 최신 상태를 저장합니다. Vue 화면은 REST와 SSE로 관측값을 받습니다.

ACK는 수집 DB에 저장됐다는 답입니다. 화면에 표시됐다는 답이 아닙니다. 따라서 ACK 왕복, 수집 대기/저장, 서버 간 전달, 업무 저장, SSE 수신, Vue 반영을 구분해 측정합니다.

## p95는 무엇인가

100개의 지연값을 작은 순서로 정렬했을 때 약 95번째 값입니다. 대부분의 요청이 어느 정도 안에 끝나는지 보여 줍니다. 이 프로젝트는 표본을 정렬해 `ceil(표본 수 × 0.95)` 위치를 사용합니다. 각 구간의 p95를 더해 종단 지연을 만들지 않습니다.

## 입력 목표와 실제 처리량

정상 입력은 초당 25건 목표로 5분씩 3회, 스트레스 입력은 100·300·500건 목표로 각각 2분씩 3회 측정합니다. 동일 seed와 기본 공장 설정을 사용하며 전체 보고 빈도를 늘립니다. 검사 결과를 대량 생성해 실적을 부풀리지 않습니다.

Python은 기존 규칙대로 원본 한 건의 저장 확인을 받은 뒤 다음 원본을 보냅니다. 서버가 느리면 목표 빈도를 못 맞출 수 있습니다. **목표 500건/s를 설정했다는 사실을 실제 500건/s 수신·처리 성공으로 쓰지 않습니다.** 원본, 전송 시도, 저장, 반영, 중복, 거절, 미확인, 전달 대기를 각각 남깁니다.

## 데이터와 측정의 경계

[측정 도구](../../scripts/measure-performance.py)는 별도 PostgreSQL과 Java·Vue 프로세스를 사용합니다. 성공한 자기 run의 원본 바이트와 해시를 양 DB와 대조한 뒤 그 run의 DB 행만 정리해 다음 반복의 조건을 맞춥니다. 원본·결과·로그·측정 파일은 보존하고 실패 기록은 지우지 않습니다.

Java 기록은 JVM 옵션을 지정했을 때만 켜집니다. 브라우저 기록은 개발 모드의 명시적인 측정 옵션이 있어야 켜집니다. 평소 API·이벤트 규격·공장 계산·화면 색상은 바뀌지 않습니다. 같은 프로세스의 구간은 monotonic clock, 서로 다른 프로세스의 종단값은 단일 호스트 시계의 추정치입니다.

SSE는 최신 전체 상태를 묶어서 전달합니다. 모든 입력 이벤트가 각각 화면 프레임으로 전달되지는 않습니다. 화면 지연은 실제 관측된 sourceSeq의 수신 시각과 연결해서 계산합니다. 전경·실제 해상도·표본 수와 한계는 통합 기록에서 확인합니다.

## 꼭 필요한 검증

기존 Java 관련 메서드 2개, Vue 빌드와 수신 순서 검증 2개, 실제 측정 원본의 양 DB 대조를 사용합니다. 전체 테스트를 다시 돌리거나 측정 수치를 검증하는 새 단위 테스트를 늘리지 않습니다. 실제 결과와 재실행 명령은 통합 기록에 둡니다.

## 이번 실제 결과

정상300초×3와 스트레스120초×3×3의12개 반복을 완료했습니다. 원본151,073건이 수집/관제 DB에서 같은 순번·바이트·해시였고 종료 미확인/outbox는0입니다. 정상 입력25.63~25.72건/s, 실제 작은 전경 화면의 반영 p95는98.20~98.50ms였습니다. 100/300/500 목표 입력량을 만들지 못했고 관제 반영 대기·관측 SSE 최대 약54초가 나타났습니다.

브라우저 시간 원점과 wall clock의 약2초 차이를 발견해 렌더 표본마다 보정했으며 보정 전 값도 보존했습니다. 기준1440×900·GPU FPS·수백 대 차량 성능은 미검증입니다. 준비 단계 도구 오류와 새 JVM/PG에서 나머지4회를 수행한 사실도 통합 기록에 남겼습니다. 기본 비활성인 계측만 추가하고 원본/업무 규칙은 유지했습니다.
