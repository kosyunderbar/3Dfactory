# 작업 28. S06-03 Vue 셀 관측과 차체·태그 상세

> 작업 ID: S06-03 · 완료일: 2026-10-05 · 상태: 완료

## 이번 작업은 무엇인가

실제 Vue 화면을 “연결 준비 중”에서 **실제 공장 상태를 관측하는 최소 화면**으로 바꿨다. HTML 샘플의 JavaScript 모델이나 임의 숫자를 데이터 공급부로 쓰지 않는다. 관제 REST의 실행 목록과 SSE의 전체 묶음만 사용한다.

실행을 선택하면 셀 상태/차체·Bay 대기W/예약R/여유A/전체C를 보여 준다. 차체의 태그 버튼을 누르면 현재 위치·공정·운송/차량·검사·관측 시각의 상세 창이 열린다. 셀 카드와 상세 창은 동일한 전체 상태 묶음의 값을 읽으므로 서로 다른 조회 시점의 현재값을 섞지 않는다.

## 기술의 역할

| 구성 | 쉬운 역할 |
|---|---|
| Vue ref/computed | 새 묶음을 받으면 관련 표시를 함께 바꾸기 |
| ConsoleFeed | 실행/연결별 수신 순서와 REST/SSE 교체 판단 |
| EventSource | 이름 있는 factory-snapshot 이벤트 수신/기본 재접속 |
| performance.now | 브라우저가 마지막 유효 묶음을 받은 뒤의 경과 시간 |
| HTML dialog | 선택한 차체의 상세 창, 닫기/Escape와 기본 포커스 처리 |
| CSS | 흰색 배경·네이비 글씨·파란 강조와 이름/점선으로 상태 구분 |

## 화면을 뒤로 돌리는 늦은 응답을 막는 방법

실행 선택이나 새 연결을 만들 때 local generation을 바꾸고 이전 EventSource/REST 요청을 닫거나 취소한다. 연결의 첫 유효 SSE 묶음이 epoch 기준을 정한다. 그보다 늦게 온 REST가 예전 서버/실행의 답장이라면 버린다. 같은 epoch에서는 더 높은 revision만 적용하며, sourceSeq가 감소하면 기존 상태를 유지하고 다시 연결한다. 같은 sourceSeq의 새 revision은 신선도 변경일 수 있어 허용한다.

중복 묶음과 heartbeat는 새 관측으로 세지 않는다. 새 유효 전체 묶음이3초 동안 없으면 “마지막 확인값”,10초면 “화면 연결 확인 필요”를 표시한다. 서버에서 받은 sourceAgeMs에 브라우저 수신 후 경과를 더한 나이가3초를 넘겨도 LIVE 표시를 중지한다. 종료 확인된 ARCHIVED는 공장 나이 증가와 별도로 보관값으로 표시한다. 서버 DTO의 dataStatus나 물리 좌표 자체를 수정하지 않는다.

화면의 연결 표시는 공장 데이터의 신선도와 별개다. SSE가 열려 있어도 Python 보고가 끊기면 STALE/DISCONNECTED가 된다. 전송 자체가 끊기면 마지막 상태를 보존하고 한 재연결 타이머로2초 뒤 다시 연결한다. 관측 부재는0대/0칸으로 추정하지 않는다.

## 실제 브라우저 확인

Chrome에서 실제 새 run을 열어 ASM-01 작업과 body-00001/tag-00001의 동일 위치를 확인하고 상세 창을 열었다. 검증이 시작한 Python 프로세스만 SIGSTOP으로 잠시 멈췄다. 연결이 살아 있어도 새 보고가 없자 관제/화면은 소스 연결 확인과 마지막 확인값을 표시했다. 같은 sourceSeq/차체/셀 상태를 유지했고 재개 뒤 새 보고로 진행했다. 최종 GOOD/PASS와 FINISHED/ARCHIVED도 같은 run의 화면과 REST/두 DB 결과로 확인했다.

Java3개와 별도로 `scripts/console.sh test`의 **Node2개**가 통과했다. 예전 REST/epoch/실행의 응답과 감소 순번이 최신 상태를 덮지 않는지, 중복/연결/heartbeat가 타이머를 갱신하지 않는지와3초/10초 경계를 묶었다. 새 UI 테스트 프레임워크를 추가하지 않았다. Vue 빌드와 실제 화면은 별도 실제 증거이며 Node 결과만으로 브라우저 표시가 성공했다고 쓰지 않는다.

최종 실행의 screenshot/AX 상태·DB/REST/SSE 결과는 [공유 검증 기록](<../validation/최소 검증 시나리오와 도구.md>)에 있다. 소스 중단과 SSE 단절을 같은 장애라고 설명하지 않는다. 이번 실제 중단은 Python 프로세스이며, 모든 서비스/DB/네트워크 장애 조합은 S08이다.
