# 작업 4. 화면 조회와 실시간 상태 전달

> 작업 ID: S00-04 · 완료일: 2026-10-05  
> 결과: 화면 조회·SSE·신선도·반영 지연과 최소 검증 도구의 **설계 완료**. 서버/DB/Vue 연결 구현은 이후 작업이다.

## 1. 이번 작업은 무엇인가

작업 2에서는 공장이 보내는 보고서 양식을, 작업 3에서는 그 보고서를 저장하고 전달하는 방법을 정했다. 이번에는 **그 자료를 화면이 어떻게 받아 보여줄지** 정했다.

화면을 만든다고 해서 차량을 화면 코드에서 직접 움직이는 것은 아니다. Python이 공장의 실제 상태를 결정하고, 관제 서버가 확인한 자료를 묶어 주면 화면은 그것을 보여준다. 이 경계를 지켜야 지도·태그 창·버퍼 숫자가 서로 다른 상황을 말하지 않는다.

이 작업으로 S00의 네 설계 작업이 끝났다. 다음은 S01-01, 두 Spring 앱의 실행 기반을 준비하는 작업이다. 이번에는 그 작업을 시작하지 않았다.

## 2. REST와 SSE는 각각 어떤 역할인가

**REST**는 필요할 때 묻고 답을 받는 방식이다. ‘tag-00042는 어떤 차체인가?’, ‘지난 5분 검사 결과는?’처럼 조회하거나, 알람 확인 버튼을 눌렀을 때 사용한다.

**SSE**는 연결을 열어 두고 서버가 화면의 새 상태를 보내는 방식이다. 현재 지도·차량·슬롯·숫자를 한 묶음으로 받는다. 메시지 하나를 놓쳐도 재접속 때 최신 전체 묶음을 받으면 현재 화면을 다시 구성할 수 있다. 지난 이력 전체를 SSE로 재생할 필요는 없다.

이를 위한 새 프레임워크나 메시지 브로커를 추가하지 않았다. 기존 Spring REST/SSE와 Vue 계획을 유지했다. [정확한 화면 계약](../../contracts/v1/monitoring.md)에 경로·필드·크기·오류를 적었다.

## 3. 태그 창과 지도를 같은 장면으로 맞춘다

예제의 BAY-ASM-02는 대기 2대, 예약 1대, 전체 3칸이다. 여유는 0칸이다. 예약된 body-00042는 아직 픽업 전이므로 ASM-01 셀에 남아 있다. 태그 창에도 ‘ASM-01 / 배출 대기 / 예약 있음’이 표시되어야 한다.

이때 보고서 대기가 밀리거나 통신이 끊겨도 화면이 임의로 예약을 없애거나 차체를 AGV로 옮기면 안 된다. 마지막 확인값을 유지하고 오래됐다는 표시를 붙인다. 이미 예약된 운송은 Python의 기존 규칙대로 계속 진행할 수 있고, 여유가 0이라는 이유로 그 예약까지 취소하지 않는다.

현재 화면에는 세 가지 번호가 있다.

| 번호 | 쉬운 뜻 |
|---|---|
| runId | 어느 공장 실행인가 |
| sourceSeq | 공장이 보낸 몇 번째 상태 보고서인가 |
| serverEpoch + revision | 어느 관제 서버 실행에서 만든 몇 번째 화면 묶음인가 |

같은 공장 보고서를 보면서도 알람을 확인하거나 시간이 지나 ‘오래된 상태’가 되면 새 화면 묶음이 필요하다. 그래서 sourceSeq와 revision을 따로 둔다. 늦게 도착한 태그 조회가 최신 지도를 과거로 돌리지 못하도록 run·epoch·revision과 요청 세대를 확인한다.

## 4. 연결됐다는 것과 최신이라는 것은 다르다

인터넷 통로가 열려 있어도 새 공장 보고서가 없을 수 있다. 수집 서버가 저장 답장을 했어도 관제 서버가 아직 반영하지 못할 수 있다. 다음 두 문제를 따로 본다.

| 상황 | 표시와 의미 |
|---|---|
| 새 공장 보고가 3초 이상 없음 | STALE: 마지막 상태가 오래됨 |
| 10초 이상 없음 또는 생산자 연결 끊김 | DISCONNECTED: 소스 연결/상태 보고 확인 필요 |
| 보고서가 1초 이상 반영 대기 | CATCHING_UP: 서버가 밀린 자료를 반영 중 |
| 관제 서버 재시작 후 저장값만 읽음 | RESTORING: 새 상태 보고를 기다림 |
| 수집 진단 조회 실패 | UNKNOWN: 전달 상태를 확인할 수 없음 |
| 재시도 소진·영구 거절 등으로 처리 중단 | BLOCKED: 순번과 원인을 보고 복구해야 함 |
| 의도적으로 공장만 일시정지 | PAUSED: 이동은 정지, 상태 보고는 계속 가능 |
| 아직 첫 상태 보고가 없음 | WAITING: 0대가 아니라 아직 모름 |
| 종료 보고와 전달 완료까지 확인 | FINISHED: 보관된 마지막 확인값 |

정상적인 짧은 전달 대기는 허용하므로 LIVE가 ‘지연이 전혀 없다’는 뜻은 아니다. 1초 안의 대기 수라도 진단에서 볼 수 있다. 상태가 겹칠 때는 계약의 우선순위를 사용하고, 마지막 관측 시각과 진단 표본 시각도 함께 보여준다.

브라우저와 관제 사이의 연결 표시도 별도로 둔다. SSE가 끊겼는데 화면에 마지막 LIVE 문자열만 남기는 일을 막고, 오래된 상태에서는 이동 애니메이션을 멈춘다. 화면 연결 문제를 공장 AGV의 실제 고장으로 바꾸지 않는다.

## 5. 두 종류의 대기를 혼동하지 않는다

**차체 버퍼**는 물리적인 Parking Bay다. 대기 차체 W와 유효 예약 R을 세어 W+R≥C이면 새 배출을 막는다.

**보고서 대기**는 서버가 아직 전달/반영하지 못한 사건 목록이다. 이것은 pendingCount/pendingBytes로 표시한다. 보고서가 10개 밀렸다고 Bay에 차체가 10대 있다는 뜻이 아니다.

수집 서버의 진단은 HTTP로 물어본다. 관제 서버가 수집 DB를 직접 뒤져 읽지 않으므로 서비스별 데이터 소유권도 유지한다. 진단은 별도 시점에 읽은 표본이라 그 시각과 성공 여부를 함께 전달한다.

## 6. 품질·이력·알람도 기준을 정했다

검사 0건이면 불량률은 0%가 아니라 ‘—’로 표시한다. 아직 검사하지 않은 차체를 합격으로 세지 않는다. 최근 5분은 서버가 정한 하나의 UTC 구간이며 지연 검사 결과는 원래 발생 시간에 반영한다. 페이지를 넘기며 들어온 새 사실은 새 조회에서 볼 수 있게 기준을 고정한다.

이력은 기본 50개, 최대 200개씩 조회한다. 한 번에 최대 24시간을 요청하고 차트는 최대 300개 버킷만 보낸다. 지도용 묶음에도 무제한 과거 이력을 넣지 않는다.

알람 확인은 ‘운영자가 읽었다’는 기록이다. 설비 고장을 고치거나 예약을 해제하는 기능이 아니다. 같은 확인 요청이 다시 오면 최초 확인 기록을 그대로 돌려준다.

## 7. 무엇을 확인했나

Python 3.12.1의 기본 도구만 사용했다. 추가 패키지는 설치하지 않았다.

```sh
python3 scripts/check_monitoring_examples.py
```

결과:

```text
PASS: REST/tag/SSE share one snapshot; 16 status boundaries; 4 invalid examples rejected; 6 late-response decisions; empty quality stays null. Contract examples only.
```

완전한 화면/태그 응답과 실제 SSE 텍스트가 같은 공장 스냅샷을 담는지 확인했다. 관측 없는 값이 0으로 바뀌지 않는지, 진단 실패가 예약을 없애지 않는지도 확인했다. 잘못된 필드 누락·순번·슬롯·불량률 예제는 거절됐다. 문서의 로컬 링크 129개도 모두 실제 파일로 연결되는지 확인했다.

이 결과는 **자료와 판정 예제의 확인**이다. 실제 DB 트랜잭션·SSE 접속·자동 재연결·Vue 화면을 실행한 결과가 아니다. 기존 사건/전달 자료는 바꾸지 않아 그 검증을 반복하지 않았다. [최소 검증 시나리오와 도구](<../validation/최소 검증 시나리오와 도구.md>)에는 해당 구현 작업에서 꼭 필요한 실제 검증만 골라 실행하도록 적었다.
