# 작업 22. S04-04 데이터 신선도와 알람 확인·복구

> 작업 ID: S04-04 · 완료일: 2026-10-05 · 상태: 완료  
> 마지막 확인값 보존 · 진단 실패 UNKNOWN · 확인과 복구 분리

공장 보고가 얼마나 오래됐는지, 업무 반영이 뒤처졌는지 판단하는 관제 규칙과 알람의 발생·확인·복구를 구현했다. 연결을 확인할 수 없다고 차체 위치나 슬롯 예약을 임의로 바꾸지 않는다.

## 오래된 사진을 현재 공장으로 오해하지 않도록

스냅샷의 capturedAt은 공장을 관측한 시각이다. 관제는 조회 시각과 비교해 freshness를 계산한다. [Observation.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/Observation.java)에 시간 경계와 상태 우선순위를 분리했다.

| 보고 나이/상황 | freshness |
|---|---|
| 스냅샷 없음 | NO_DATA |
| 3초 미만 | FRESH |
| 3초 이상, 10초 미만 | STALE |
| 10초 이상 | EXPIRED |
| 소스 시각이 관제보다 5초 초과 미래 | UNKNOWN |
| 종료 사실과 전달 완료를 함께 확인 | ARCHIVED |

보고가 오래돼도 마지막 물리 위치를 보관한다. 조회가 됐다는 이유만으로 최신이라고 판단하지 않는다. 서버를 재시작하면 새로운 serverEpoch를 만들고 DB에 저장된 스냅샷을 복원한다. 이때는 RESTORING이며 복원 시점보다 큰 sourceSeq의 새 스냅샷을 실제로 반영해야 observedAfterEpoch=true다.

## 전달 지연을 알아야 LIVE라고 말할 수 있다

수집기가 원본을 저장했더라도 관제에 전달하지 못한 보고서가 있을 수 있다. [DeliveryDiagnostics.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/DeliveryDiagnostics.java)는 수집기의 내부 delivery-status API를 조회해 pending 수·다음 순번·연결·대기 시각을 확인한다. 상대 DB를 직접 조회하지 않는다.

진단은 run별 1초 간격으로 합치고, 연결 500ms/전체 응답 1초/몸체 8KiB로 제한한다. 실패 또는 오래된 표본은 diagnosticState=UNAVAILABLE이다. 마지막 성공 값을 남기더라도 확인 실패 사실을 숨기지 않는다. 전달 진단을 한 번도 받지 못하면 run/source 이외 미확인 값은 null이다.

**수집기의 이 진단 제공 경로와 자동 outbox 전달은 S05에서 구현한다.** S04는 소비·검증·상태 판정 쪽을 준비했다. 따라서 지금 실제 관제는 최신 스냅샷을 받았어도 UNKNOWN으로 표시한다. 임의의 pending=0을 만들어 LIVE라고 하지 않는다. 물리 runState=FINISHED와 관제 dataStatus=FINISHED도 구분한다. 후자는 종료 사건 커밋과 AVAILABLE 진단의 pending=0/전달 커서 통과가 모두 필요하다.

판정 순서는 BLOCKED → FINISHED → WAITING → RESTORING → UNKNOWN → DISCONNECTED → STALE → CATCHING_UP → PAUSED → LIVE다. 진단이 유효한 상태에서 보고 대기가 1초 이상이거나 재시도/순번 대기 중이면 CATCHING_UP이다. 이는 차체 Parking Bay의 W/R과 다른 보고서 대기다.

## 알람의 확인과 복구는 다른 행동이다

[AlarmService.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/AlarmService.java)가 다음 P0 조건을 관리한다.

| 알람 | 근거 |
|---|---|
| EQUIPMENT_DOWN | 검증된 최신 스냅샷의 셀 DOWN |
| BUFFER_FULL | 같은 스냅샷의 A=C-W-R=0 |
| SOURCE_STALE | 진행 실행의 보고 나이 3초 이상 |
| SOURCE_DISCONNECTED | 유효 진단의 연결 끊김 또는 보고 나이 10초 이상 |
| PROCESSING_BLOCKED | 관제 업무 중단 또는 알려진 전달 보류/중단 |

같은 조건이 계속 참이면 활성 알람 하나를 유지한다. 정상 상태를 실제 확인하면 resolvedAt을 기록한다. 이후 다시 발생하면 새 알람 ID를 만든다. 고장/만석은 오래된 스냅샷이나 진단 실패만으로 해소하지 않는다. QUALITY_WARNING 생성은 P1이며 이번에는 추가하지 않았다.

운영자가 `POST /api/v1/alarms/{alarmId}/acknowledge`에 operatorId를 보내면 최초 확인자/시각을 저장한다. 다른 이름으로 다시 요청해도 최초 값을 유지한다. “봤다”는 기록이며 conditionActive를 false로 만들거나 고장을 고치거나 슬롯을 반환하지 않는다. operatorId는 학습용 이름이지 인증된 사용자 신원은 아니다.

예를 들어 ASM-01이 DOWN일 때 확인 버튼을 눌러도 차체와 남은 작업 시간이 그대로다. Python에서 복구한 뒤 새 유효 스냅샷이 오면 해당 알람이 해소된다. 이 흐름을 실제 HTTP와 PostgreSQL로 확인했다.

## 검증 결과와 남은 연결

S04 공통 7개 중 순수 판정 2개는 2,999/3,000/9,999/10,000ms, 시계 선행, 상태 우선순위와 999/1,000ms 반영 지연을 확인했다. 실제 DB/HTTP 시나리오에서는 고장 알람 확인·최초 확인자 보존·정상 복구, 진단 실패 UNKNOWN, 서버 복원 RESTORING을 확인했다. Compose의 사건 60건에서도 알람 확인 후 조건 유지와 실제 복구를 확인했다.

```sh
python3 scripts/verify-databases.py --suite operations

```
