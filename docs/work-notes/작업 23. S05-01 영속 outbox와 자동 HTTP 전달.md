# 작업 23. S05-01 영속 outbox와 자동 HTTP 전달

> 작업 ID: S05-01 · 완료일: 2026-10-05 · 상태: 완료

## 이번 작업은 무엇인가

수집기가 받아 둔 보고서를 관제에 자동으로 전달하는 담당자를 만들었다. 이전에는 Python이 보고서를 보내면 수집 DB에 저장하는 데까지 연결됐고, 관제 API는 별도로 호출해야 했다. 이제 수집 저장 뒤 전달 작업(worker)이 DB의 대기 목록을 읽어 관제 API를 호출한다.

outbox는 보낼 보고서의 목록이다. 차체가 기다리는 Parking Bay와는 다르다. 이 목록이 밀려도 이미 확보한 물리 슬롯을 반환하지 않는다. Python은 수집 성공 ACK를 받으면 자기 송신 목록에서 해당 보고서를 제거하고, 이후 전달 책임은 수집기가 맡는다.

## 기술이 맡는 역할

| 구성 | 쉬운 설명 | 이번 역할 |
|---|---|---|
| PostgreSQL outbox | 재시작해도 남는 발송 장부 | 원본 번호·상태·시도 횟수·다음 시도 시각 보존 |
| delivery_stream | 실행별 책갈피 | 다음에 전달할 sourceSeq를 기억 |
| Java worker | 장부를 읽는 전달 담당자 | 한 건씩 HTTP 요청, 실행별 순환 선택 |
| REST/HTTP | 프로그램 사이의 요청과 답장 | 관제 업무 반영 결과 확인 |
| 트랜잭션 | 모두 저장하거나 모두 취소하는 단위 | 완료 표시와 책갈피 증가를 함께 저장 |
| Flyway V2 | DB 구조의 추가 변경 기록 | 누적 시도·최근 시도 시각·재개 기록 추가 |

기존 Java 21·Spring Boot·JDBC·PostgreSQL·Maven·TCP/REST·Compose를 유지했다. Java 기본 HTTP 클라이언트를 사용하며 브로커나 다른 프레임워크를 추가하지 않았다.

## 실제 흐름

1. TCP 수집이 원본과 outbox를 같은 수집 DB 트랜잭션에 저장하고 ACK한다.
2. worker가 해당 실행의 다음 순번만 고른다. HTTP 전에 시도 횟수와 다음 재시도 가능 시각을 먼저 저장한다.
3. DB 트랜잭션을 끝낸 뒤 원본 문자열·해시·최초 수신 시각을 그대로 HTTP로 보낸다.
4. 관제 성공 또는 중복 성공을 확인하면 DELIVERED 표시와 책갈피 증가를 같은 트랜잭션으로 저장한다.
5. 통신 결과가 불명확하면 같은 원본을 다시 보낸다. 새 번호를 붙이거나 JSON을 다시 구성하지 않는다.

HTTP 연결은 1초, 전체 요청/응답 대기는 최대 5초다. 응답은 8KiB, 요청은 512KiB로 제한한다. 첫 실패 뒤 500ms부터 간격을 늘려 최대 30초에 제한하며 0~10%의 양의 jitter를 더한다. 서버가 더 긴 대기를 요구하면 30초 안에서는 그 값을 지킨다. 30초를 넘는 요구는 설정 확인을 위해 보류한다. 최초 포함 20회 뒤에는 자동 발송을 멈춘다.

시도 기록을 먼저 커밋하므로 그 직후 프로세스가 종료되면 실제 HTTP 시작 여부는 모를 수 있다. 횟수는 보수적으로 유지하며 재시작만으로 시도 예산을 다시 주지 않는다. 두 DB를 동시에 커밋한 것으로 표현하지 않는다.

## 변경 파일

`services/ingestion-service/.../delivery/`의 DeliveryWorker·DeliveryStore·OperationsClient·DeliveryWire·LimitedBody가 전달과 응답 판정을 나눠 맡는다. 설정은 ingestion application.yml과 compose.yaml에 추가했다. 기존 수집 V1은 수정하지 않고 V2로 event_outbox의 누적 횟수/최근 시도 시각과 delivery_action을 추가했다.

## 꼭 필요한 검증 결과

S05 세 작업이 같은 최소 검증을 공유했다. `python3 scripts/verify-databases.py --suite delivery`에서 총 **8개**가 통과했다. 새 전달 판정 1개·실제 두 DB/TCP/HTTP 통합 3개·영향받은 기존 저장 경계 3개·bootstrap 1개다. 정상 60건, 원본/해시 일치, 완료와 책갈피 동시 저장, 관제 응답 유실과 수집 완료 저장 rollback을 확인했다. 상세 장애 분류는 작업 24에서 설명한다.

기존 Compose에서는 `python3 scripts/verify-delivery.py --with-restarts`로 **Python TCP ACK 60건 → 자동 HTTP → 관제 저장 60건**을 확인했다. 업무 이력은 작업 3·운송 6·검사 1건으로 남았다. 관제 중단/수집 재시작 복구까지 한 실행에 묶었고 기존 DB/볼륨을 보존했다. 성공한 새 검증 UUID의 기록만 정리했다.

## 남은 작업

현재는 수집 한 인스턴스·worker 하나다. 여러 worker의 분산 조정은 P0에 포함하지 않는다. 일반 Python 기동은 여전히 자동 생산을 시작하지 않는다. 실제 화면의 SSE/Vue 연결과 실시간 성능 측정은 S06 이후다.
