# 작업 49. 통로 기반 경로와 구간 예약

2026-10-10 · 경로의 급격한 변경을 줄이고 공정 관찰에 필요한 기본 주행 제약 적용

## 결정과 변경

사용자 승인: A* 통로망 + 구간 예약 + 기본 차량 운동 제약을 구현하고, 시뮬레이션 검증 후 바로 적용한다. 작업 기록을 계속 남긴다.

- 정책 3을 새 실행 기본값으로 설정했다. 기존 정책 1·2의 배치·기록 재생과 운반 규칙은 보존한다.
- 기존 자유 공간 탐색은 타 차량의 남은 경로 전체를 큰 사각형들로 차단하여 우회가 커졌다. 새 정책은 방향성 통로망에서 A*로 경로를 정한다. 구간 거리, 정차 비용, 현재 점유에 따른 예상 대기 비용을 반영한다.
- 처음에는 기존 좁은 배치에 통로망을 넣었으나, 접안 차량이 주행선까지 막아 양보 이동이 잦았다. CELL 접안 y=100, 동행 통로 y=180, 서행 통로 y=260, BAY 접안 y=340으로 분리했다. 부품 구역과 경계도 뒤로 옮겼다. 주차는 통로 밖 전용 지점에 배치했다.
- 다음 한 구간의 적재물 포함 안전 영역을 예약한 뒤 출발한다. 구간 끝은 정지 가능한 위치이며, 타 차량의 현재 위치와 승인 구간 모두 검사한다. 지나간 예약은 해제하되 같은 tick의 차량 갱신이 모두 끝나기 전에는 진입시키지 않는다.
- 주행 중 경로는 유지한다. 3초 이상 막힌 경우 정차 노드에서만 대체 경로를 찾는다. 대체 경로에는 최대 속도 2초에 해당하는 변경 비용을 더해 작은 이득 때문에 경로를 바꾸지 않는다. 통행이 모두 멈추면 지정 대기 노드로 양보한다. 오래 기다린 요청부터 통행 예약을 시도하며, 교착 양보는 후순위 요청부터 검토한다.
- 빈 복귀 차량의 재배차와 우선 픽업 전환은 다음 정차 노드에서 한다. 이동 중 새 경로로 즉시 꺾지 않는다. 명시적 취소도 정차 지점에서만 허용한다.
- 차동구동형으로 가정했다. 옆으로 미끄러지는 이동 없이 정차→제자리 회전→가속→정속→감속한다. 속도 37.5 모델 좌표/s, 가속도 75 모델 좌표/s², 회전 120°/s 상한을 적용한다. 적재물까지 포함한 반경 30 원형 영역, 차량 간 최소 간격 63을 유지한다.
- 스냅샷에 회전·가감속 시간 곡선을 기록하고 브라우저에서도 같은 곡선을 보간한다. 정지 시 방향이 초기화되지 않는다. 회색 통로/방향 표시를 추가하고 현재 작업 경로는 파란색으로 유지했다.
- P0 실시간 실행 제한은 실제 정차·회전과 확대된 통로의 운반 시간을 반영하여 1,200초로 늘렸다.

## 검증

- Python 42개 통과. 정책 1·2 회귀 검사와 새 정책의 일반 1/3대, 부품 AMR 동시 운행, 고장·BAY 포화/복구, 용량 2/4와 100/500ms tick, 일시정지, 정차 전 취소 거부, 주차 위치 교환, 잘못된 통로 설정을 검증한다.
- 매 tick의 이동 선분으로 차량 상호 충돌과 장애물 통과를 검사한다. 회전 속도·가감속 상한과 경로 변경 시 정지 상태도 검사한다.
- Node 12개 통과, Vite 빌드 성공. 두 Java 서비스 테스트 및 패키징 성공(ingestion 6개, operations 7개 실행 통과; 별도 DB 환경 변수가 필요한 통합 테스트 7개/6개는 생략하고 실제 연결 실행으로 확인). 정책 3 대표 사건의 엄격한 구조 검사를 추가했다.
- 오프라인 일반 3대와 P0 5대 모두 완료. 두 실행의 최소 연속 이동 중심 간격은 80이었다. [원본 시뮬레이션 결과](../development/3d-review/lane-simulation-verification.json).
- 일반 3대: 346.5초, 지정 위치로 양보 2회. P0 5대: 806.0초, 양보 9회. 이는 가감속·정차와 확대된 동선을 포함한 모델 시간이다. 이전 정책과 같은 물리 조건의 처리량 비교는 아니다.
- 브라우저 보간 표본: 일반 4,865개, P0 11,298개 차량군 표본에서 장애물 관통과 차량 중첩 없음. 최소 간격 80.

## 범위

현재 공장 배치에 맞춘 통로망과 원형 적재 안전 영역을 사용하는 운동학적 시뮬레이션이다. 실제 센서 인식·위치 추정, 바퀴 접지/마찰, 충격, 연속 곡선 주행은 구현 범위에 포함하지 않는다. 각 통로 구간 끝에서 정지하는 보수적인 방식이다. 임의의 공장 배치나 무제한 차량 수에 대한 교착 해소 보장은 아니다.

## 실제 관제 적용

- 수집·관제 서비스에 새 계약을 배포하고, 개발 콘솔에서 실제 3대 실행을 시작했다. 실행 ID: `run-20261010-66facd07e492493a9aa513fbddad86cb`.
- 3대 모두 GOOD/PASS, 차량 전부 IDLE, 활성 운송 없음, FINISHED. 원본 사건 806개의 원문·순번·SHA-256이 수집 DB와 관제 DB에서 모두 일치하고 전달 대기 0건이다. [연결 검증](../development/3d-review/lane-connected-verification.json).
- 실제 실행의 snapshot 695개, 보간 차량군 표본 4,865개에서 충돌 없음, 최소 중심 간격 80. 브라우저의 계산 위치와 원본 위치도 일치한다. [실제 이동 검증](../development/3d-review/lane-connected-motion-verification.json).
- Chrome에서 실시간 운반과 완료 상태를 확인했고 콘솔 오류가 없다. [운행 화면](../development/3d-review/lane-live.jpg), [완료 화면](../development/3d-review/lane-finished.jpg).
- 실행 중 마지막 정리에서 재계획/양보에도 설정된 운송 속도와 지연을 유지하도록 보완했고, 작은 우회 이득을 거르는 경로 변경 비용을 명시했다. 최종 코드는 Python 42개와 오프라인 전체 시나리오를 다시 통과했다. 실제 연결 실행 346.4초, 최종 오프라인 동일 3대 조건 346.5초다.
- 새 실행부터 정책 3이 적용된다. 기존 실행 기록과 DB는 삭제하지 않았다.
- 개발 콘솔(5174)과 기존 콘솔 컨테이너(5173)에 화면을 반영했다. 컨테이너 빌드에 필요한 `simulation-launcher.js` 복사를 보완했고 새 이미지의 healthcheck도 통과했다.
