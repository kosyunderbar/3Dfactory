# 작업 19. S04-01 내부 사건 수신과 업무 처리 기록

> 작업 ID: S04-01 · 완료일: 2026-10-05 · 상태: 완료  
> Java 21 · Spring Boot 4.1.1 · Spring JDBC · 실제 PostgreSQL 17.11

관제 서비스가 보고서를 받아 업무 규칙을 확인하고, 반영 결과를 DB에 남기는 내부 API를 구현했다. 수집 서비스는 보고서를 안전하게 맡는 역할이고, 관제 서비스는 그 보고서가 차체·검사·운송 기록에 어떤 의미인지 판단하는 역할이다.

## 이번 작업을 이해하는 사례

“차체 1번의 QC 검사가 FAIL이었다”는 보고가 온다고 생각해 보자. 관제는 먼저 해당 공장 실행이 등록됐는지, 차체 1번이 있는지, 검사 설비가 QC-01인지 확인한다. 유효하면 검사 결과와 처리 기록을 함께 저장하고 APPLIED로 답한다.

답장이 유실되어 같은 보고서가 다시 와도 검사 수를 또 늘리지 않는다. DB에 저장된 사건 번호·송신원·순번·원본 문자열·SHA-256이 모두 같으면 DUPLICATE_APPLIED와 최초 처리 시각을 반환한다. 서버를 다시 켜도 DB 기록으로 이 판단을 유지할 수 있다.

## 코드와 기술의 역할

| 파일 | 역할 |
|---|---|
| [OperationsController.java](../../services/operations-service/src/main/java/dev/factory/operations/api/OperationsController.java) | HTTP 요청의 양식·크기·해시를 검사하고 결과를 답함 |
| [EventSyntax.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/EventSyntax.java) | v1 사건 17종의 필드·식별자·시각·숫자 양식 검증 |
| [ModelRules.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/ModelRules.java) | 공장 구성, 차체 소유, 슬롯·운송 등의 업무 관계 검증 |
| [EventApplication.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/EventApplication.java) | 실제 SQL, 사건 중복 판단, 트랜잭션과 성공/거절 기록 |

API는 프로그램이 다른 프로그램에 요청하는 창구다. 이번 창구는 `POST /internal/v1/events/apply`이며 브라우저용 조회와 구분한다. 몸체는 protocolVersion=1, rawEvent, eventSha256, receivedAt 네 필드다. rawEvent는 LF를 제외한 원본 문자열이다. 원본을 새 양식으로 다시 조립하지 않는다.

전체 요청 상한은 512KiB, 원본은 65,535바이트다. UTF-8 JSON만 받으며 중복 JSON 키·추가 필드·잘못된 해시는 입력 오류로 응답한다. 수집 앱의 Java 코드를 관제 앱에서 가져다 쓰지 않고 독립 검증기를 두었다. 두 앱을 각자 빌드하고, 동일한 문서 계약으로 통신하는 MSA 경계를 유지한다.

## 저장을 함께 확정하는 이유

트랜잭션은 여러 DB 변경을 하나로 확정하거나 함께 취소하는 단위다. 성공 처리 기록인 processed_event만 남고 검사 저장이 실패하면 재요청을 잘못 성공으로 판단할 수 있다. 따라서 업무 기록·처리 기록·조회용 사건 투영을 같은 관제 DB 트랜잭션에 묶었다. run별 DB 잠금으로 같은 실행의 쓰기를 직렬화한다. 업무 요청은 최대 4개가 처리 자리를 사용한다.

| 결과 | 의미 |
|---|---|
| 200 APPLIED | 업무와 처리 기록이 COMMIT된 뒤 답함 |
| 200 DUPLICATE_APPLIED | 이미 처리한 같은 원본. 업무 재적용 없음 |
| 409 RETRY_LATER | 실행/차체 등 선행 참조가 없거나 run 처리가 중단됨. 성공 기록 없음 |
| 422 REJECTED | 업무 변경을 rollback한 뒤 별도 트랜잭션에 거절 근거를 저장하고 run을 BLOCKED로 기록 |
| 409 REJECTED | 사건 번호·순번·송신원 충돌. 기존 정상 기록 유지 |
| 429 / 503 RETRY_LATER | 처리 자리 부족 또는 DB 성공 미확인. 재전달 책임 유지 |

COMMIT은 DB 변경 확정이고 rollback은 중간 변경 취소다. 422 근거를 저장하는 데도 실패하면 거절을 확정하지 않고 503으로 답한다. appliedAt/recordedAt은 DB 행에 쓴 시각이며 실제 COMMIT 순간과 동일한 측정값은 아니다. 성공 응답은 TransactionTemplate의 COMMIT 반환 뒤에만 보낸다.

## 필요한 최소 검증과 결과

```sh
python3 scripts/verify-databases.py --suite operations
python3 scripts/verify-operations.py
```

첫 명령은 별도 임시 PostgreSQL을 만들고 종료한다. S04 전체가 공유하는 7개 검증 중 실제 DB/HTTP 시나리오는 4개다. 같은 원본의 반복 처리, 태그 충돌의 영속 거절, 미등록 참조의 재시도, 실제 PostgreSQL 제약 위반에 따른 업무·처리 기록 rollback을 확인했다. 잘못된 JSON이 503으로 분류되던 문제를 고쳐 400 입력 오류로 응답하도록 검증했다.

두 번째 명령은 실행 중인 Compose에 명시적 검증 호출로 사건 60건을 반영한다. DB 원본 문자열·해시·순번 일치와 중복 응답을 확인했다. 검증 전용 UUID를 새로 생성하고 기존 행 0건을 확인한 뒤 해당 run만 정리한다. 자동 승인 검토가 정리 대상 충돌 가능성을 지적하여 이 사전 확인을 추가했고, 보완된 검증은 통과했다. 기존 DB·볼륨은 보존했다.

공통 증거는 [S04 검증 안내](<../validation/최소 검증 시나리오와 도구.md>)에 있다. 자동 outbox 전달은 S05이다. 이번 내부 API가 준비됐다는 사실은 수집된 모든 보고서의 자동 반영이나 GUI LIVE 연결 완료를 뜻하지 않는다.
