## 이번 작업은 무엇인가

앞에서는 서버 두 개와 DB를 준비했다. 이번에는 **공장의 상태를 결정할 Python 프로그램**과 **그 상태를 보여 줄 Vue 앱**의 시작 구조를 만들었다. 네 프로그램이 각자의 폴더에서 독립 실행되고 Compose에서도 함께 켜지게 했다.

공장에 비유하면 Python은 작업 셀·차체·운송 차량의 움직임을 결정할 모형 공장이고, Vue는 그 공장을 바라보는 관제 창이다. 지금은 모형 공장의 전원과 관제 창의 틀을 만든 단계다. 실제 움직임과 보고서 연결은 다음 작업에서 채운다.

## Python은 어떤 역할인가

Python은 향후 차체가 어디에 있는지, 어떤 셀이 작업 중인지, 어느 슬롯이 예약됐는지 결정하는 유일한 물리 상태 소유자가 된다. 서버나 화면에서 같은 차체를 별도로 배출 승인하지 않는다.

이번 `services/factory-simulator/`에는 다음 실행 기반을 넣었다.

- **설정 검사:** 향후 수집 TCP의 host/port가 필요하다. 누락되거나 포트가 범위를 벗어나면 시작을 거절한다.
- **기동:** `python -m factory_simulator`로 자기 프로그램을 시작한다. `SCAFFOLD_IDLE`이라는 대기 로그를 남긴다.
- **종료:** Ctrl+C 또는 컨테이너 종료 신호를 받으면 기본 루프를 끝내고 heartbeat 파일을 정리한다.
- **실행 확인:** 기본 루프가 갱신하는 heartbeat를 확인한다. 이 검사는 공장 운전이나 TCP 전달 성공을 뜻하지 않는다.

`factoryRunStarted`는 false다. 아직 차체·태그·예약·사건을 만들거나 TCP에 연결하지 않는다. 연결 대상 설정이 유효한 것과 실제 송신 성공은 서로 다른 조건이다.

Python 3.12 가상환경은 프로젝트 `.build-cache/simulator-venv/`에 있다. 가상환경은 이 프로젝트가 사용할 실행 도구를 분리하는 폴더다. 현재 제삼자 패키지가 없어 pip 설치나 새 테스트 라이브러리가 필요 없다. 표준 unittest를 사용한다.

```sh
scripts/simulator.sh setup
scripts/simulator.sh test
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run --check-config
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run
```

마지막 명령은 대기 상태를 유지하며 Ctrl+C로 종료한다. 자세한 설명은 [Python 실행 안내](../../services/factory-simulator/README.md)에 있다.

## Vue·Vite·Node는 어떤 역할인가

| 기술 | 쉬운 설명 | 이번 사용 |
|---|---|---|
| Vue 3 | 화면 구성과 바뀌는 값을 연결하는 도구 | 준비 상태, 확인 버튼, 안내 화면 |
| JavaScript | 브라우저가 실행하는 화면 동작 코드 | 실제 HTTP 요청과 상태 표시 |
| Vite | 개발 서버와 배포용 파일 빌드 도구 | dev / build / preview |
| Node / npm | 개발·빌드 도구를 실행하고 의존성을 설치 | Node 24.21.0, npm 11.19.0 |
| package-lock.json | 의존성의 정확한 버전·무결성을 기록한 설치 목록 | npm ci로 같은 구성 설치 |
| Nginx | Compose에서 빌드된 화면 파일을 제공하는 서버 | 화면 파일, 관제 서버 경로 중계 |

기존의 Vue 3·JavaScript·Vite 스택을 유지했다. 구체 버전은 Vue 3.5.43 / Vite 8.3.2 / plugin-vue 6.0.9로 고정했다. TypeScript로 바꾸지 않았다. 지도/애니메이션과 ECharts 업무 화면은 해당 기능을 만들 때 연결한다.

개발 중에는 Vite가 Vue 코드를 읽어 화면을 제공한다. Compose에서는 Node가 배포용 HTML/JS/CSS를 만들고 Nginx가 그 결과를 제공한다. Node 빌드 도구가 실제 브라우저 안에서 실행되는 것은 아니다.

```sh
scripts/console.sh install
scripts/console.sh dev
scripts/console.sh build
scripts/console.sh preview
```

`install`은 npm ci이며 package-lock.json을 기준으로 설치한다. dev는 5173, preview는 4173을 사용한다. [Vue 실행 안내](../../services/factory-console/README.md)를 따른다. Compose의 화면 주소도 5173이므로 같은 포트의 dev 서버를 동시에 켜지 않는다.

## 첫 화면은 무엇을 보여 주는가

현재 화면은 서로 다른 두 상태를 보여 준다.

1. **관제 서버 실행 상태:** `/readyz`를 실제로 요청한다. 서버/DB가 준비됐으면 “실행 준비됨”, 준비되지 않았으면 “준비되지 않음”, 연결 자체를 확인할 수 없으면 “연결 확인 불가”다. “다시 확인” 버튼은 요청을 다시 보낸다.
2. **공장 데이터 연결 전:** 사건·스냅샷의 수신 기능이 아직 없음을 표시한다. 차체·버퍼 값은 `—`다. 준비 상태가 정상이라고 실적 0이나 가짜 차체 위치를 만들지 않는다.

브라우저는 자기 화면 서버로 요청하고, Vite/Nginx가 operations-service로 중계한다. 이를 proxy라고 한다. 사용자는 같은 화면 주소를 사용하고 브라우저에 DB 계정/암호를 넣을 필요가 없다. 화면이 ingestion DB나 operations DB를 직접 읽지 않는다.

독립 셀, 가상 스마트태그, **W + R ≥ C의 신규 배출 차단**이라는 개발 방향을 첫 화면의 안내에도 반영했다. 아직 GUI에서 예약을 승인하거나 실제 태그 상태를 계산하는 것은 아니다.

기존 `factory-gui/`의 상세 디자인/시나리오는 계속 독립 샘플이다. 그 JS 모델을 실제 Python 데이터 공급부로 사용하지 않는다. 후속 S06/S07에서 실제 관제 데이터로 지도·태그 창을 연결한다.

## 필요한 최소 검증과 실제 결과

| 검증 | 실제 결과 |
|---|---|
| Python `unittest` | 설정 정상/누락/포트 범위 오류를 묶은 테스트 1개 통과 |
| Python `--check-config` | 정상 설정 인정, TCP 미구현임을 명시 |
| Vue `npm run build` | Vite 배포 빌드 성공 |
| 실제 Compose의 Python/Vue 기동 | 두 컨테이너 healthy; 전체 결과는 작업 7에 기록 |
| 실제 Chrome에서 Vue 화면/확인 버튼 | 준비 상태 정상, 확인 시각 갱신, 공장 데이터는 연결 전/— 유지 |

Vue에 별도 테스트 프레임워크를 추가하지 않았다. 이 작은 실행 화면은 빌드와 실제 브라우저 확인으로 충분하다. Python 설정 검사도 테스트 수를 늘리는 대신 필요한 시작 경계만 확인했다. 기존 계약/샘플 테스트를 전체 재실행하지 않았다.

브라우저 확인 화면은 [기본 화면 캡처](../../services/factory-console/preview-foundation.jpg)에 남겼다. 로컬 Python은 3.12.1, 컨테이너 Python은 3.12.15이며 같은 3.12 계열이다. Node 공식 바이너리와 기반 이미지는 각각 checksum/digest로 고정했다.
