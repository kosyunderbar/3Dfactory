# 작업 46. 완료 차량 우선 픽업과 통행 예약 해제

2026-10-10 · ASM-01 완료 후 빈 AGV가 Bay 앞에서 대기하다 신규 차체로 이동하는 문제 수정

## 재현과 원인

3대 정상 생산을 기존 모델로 실행했다. AGV-001은 10.3초에 첫 차체를 BAY-ASM-01에 내려놓자마자 body-00003의 INPUT 픽업에 배정됐다. ASM-01 작업은 14.3초에 완료됐으나, 모든 AGV가 이미 배차된 상태여서 완료 차체의 우선순위가 적용되지 않았다. AGV-001은 BODY-IN 접안 경합으로 제자리에서 대기했고, 결국 AGV-002가 36.9초에 완료 차체를 적재했다.

다른 차량이 이미 지난 구간도 이동이 끝날 때까지 예약되어 있어 불필요한 대기가 더 길어졌다.

## 수정

- 교통 적용 실행에서 완료된 CELL의 배출을 신규 INPUT 픽업보다 우선한다. 빈 AGV가 없으면 아직 TO_PICKUP인 INPUT 배차 중 완료 셀에 가장 가까운 차량을 전환한다. 목적지 Bay가 만석이면 전환하지 않는다.
- 기존 운송과 슬롯 예약은 정상 취소·해제 사건으로 남기고, 완료 차체에는 새 운송 ID를 배정한다. 사유는 PRIORITY_REDISPATCH다. INPUT 차체는 자동 배차 대기열에 남아 이후 처리된다.
- LOADING, 적재 운반, 양보 지점으로 이동 중인 차량은 전환하지 않는다. 사용자가 시나리오로 취소한 차체의 재배차 보류도 유지한다.
- 통행 예약은 실제 현재 위치 이후의 남은 경로만 유지한다. 같은 tick의 이동 전 구간은 모든 차량의 갱신이 끝날 때까지 보존해 갱신 순서로 인한 관통을 막는다. 속도·안전 반경·장애물 회피는 유지한다.
- 수신 스키마와 관제 모델 검증에 PRIORITY_REDISPATCH를 추가했다. traffic 구성의 INPUT 출발 전 취소만 허용한다. 실제 관제 서비스 두 개를 재빌드·재시작했고 DB는 유지했다.

- Java 두 서비스 테스트·패키징 성공. ingestion 6개 및 operations 6개 실행 통과. DB 환경 변수에 의존하는 테스트는 각각 7개·6개 생략되어 실제 연결 실행으로 별도 검증했다.
