# 작업 15. S03-01 TCP 입력 조립과 수신 제한

> 작업 ID: S03-01 · 완료일: 2026-10-05 · 상태: 완료  
> 함께 진행한 단계: S03-01~04 · 기술 스택 유지 · 필요한 경계 테스트만 수행

Python이 만든 사건을 수집 서버가 한 건씩 읽을 수 있도록 TCP 입구를 만들었다. 공장의 차체 이동이나 버퍼 계산을 이 서버로 옮기는 작업은 아니다. 공장 상태는 Python이 결정하고, 수집 서버는 그 결과 보고서를 받는다.

TCP는 통신 통로다. Python이 보고서 한 장을 보냈더라도 서버에서는 두 조각으로 읽을 수 있고, 보고서 두 장이 한 조각으로 들어올 수도 있다. 그래서 “한 번 읽은 데이터 = 보고서 한 장”이라고 판단하면 내용이 잘리거나 서로 섞인다. 이번에는 LF 줄바꿈을 보고서의 끝으로 사용한다. 이 형식을 NDJSON이라고 한다.

## 무엇을 구현했나

[FrameDecoder.java](../../services/ingestion-service/src/main/java/dev/factory/ingestion/receiver/FrameDecoder.java)는 바이트를 모아 LF에서 한 사건을 완성한다. 한글의 UTF-8 바이트 중간이 잘려 들어와도, 완전한 사건을 조립한 다음 문자를 해석한다. 한 read에 여러 사건이 있어도 순서대로 넘긴다.

한 프레임은 LF 포함 65,536바이트까지 받는다. 끝나지 않은 원본이 65,535바이트를 넘으면 FRAME_TOO_LARGE로 닫는다. 첫 바이트부터 3초 안에 LF가 없으면 FRAME_TIMEOUT이다. 조금씩 바이트를 보내도 그 시간을 연장하지 않는다. 연결이 끊겼을 때 LF 없는 마지막 조각은 저장하지 않고, 앞서 완성해 저장한 사건은 유지한다.

[TcpReceiver.java](../../services/ingestion-service/src/main/java/dev/factory/ingestion/receiver/TcpReceiver.java)는 최대 8개 연결을 읽는다. 넘는 연결은 닫으므로 Python은 원본을 보존하고 제한된 재접속을 한다. [AdmissionQueue.java](../../services/ingestion-service/src/main/java/dev/factory/ingestion/receiver/AdmissionQueue.java)는 저장을 기다리는 입력을 최대 128프레임·8MiB로 제한한다. 둘 중 하나라도 넘는 새 입력은 INGESTION_BUSY이며 성공으로 처리하지 않는다. 각 연결은 앞 사건의 저장 결과를 기다리므로, 뒤 입력도 자연스럽게 읽기 대기한다.

저장을 결정하는 worker는 하나다. 여러 연결이 동시에 들어와도 DB 접수 판단을 한 줄로 처리한다. 이는 목적지 슬롯을 예약하는 Python 작업과 다른 종류의 대기다.

입력 오류는 원본/outbox 대신 [RejectionLog.java](../../services/ingestion-service/src/main/java/dev/factory/ingestion/receiver/RejectionLog.java)의 별도 NDJSON 로그에 남긴다. 시각·코드·식별자·해시·최대 1KiB의 Base64 미리보기를 기록하며 파일은 10MiB씩 최대 3개다. 이 파일 기록도 실패하면 DIAGNOSTIC_UNAVAILABLE로 재시도 요청을 보낸다. 읽을 수 없는 식별자를 추측해서 정상 ACK로 답하지 않는다.

## 어떻게 확인했나

S03 전체에서 아래 명령을 한 번의 최종 검증으로 사용했다. PostgreSQL 17.11 도구가 준비된 환경에서 새 검증 클러스터를 만들고 종료하며, 기존 개발 DB를 초기화하지 않는다.

```sh
python3 scripts/verify-databases.py --suite ingestion
```

결과는 Java 7개 통과다. 조립·검증·입력 큐 테스트 3개, 실제 DB/TCP 테스트 3개, 기존 bootstrap 확인 1개를 묶었다. TCP 조각/다중 프레임·한글 중간 분할·최대 크기·고정 시간 제한·큐의 건수/바이트 제한을 확인했다. 실제 소켓에서는 부분 입력 종료, 3초 시간 초과, 8개 연결 이후 9번째 거절, 정상 사건 뒤 과대 입력에서 앞 저장 보존도 확인했다. 큐 상한은 worker를 잠시 붙잡는 결정적 테스트로 검증했다.

최종 증거: `.build-cache/database-verification/20261005T073615Z-f5a5b580/result.json`과 `ingestion-s03.log`. 최종 컨테이너에서도 잘못된 JSON의 REJECTED/INVALID_JSON 응답과 UID 10001의 보존 로그 쓰기를 확인했다. 이 실행 설정 확인은 `.build-cache/s03-container-diagnostics.json`에 기록했다.

## 실행과 다음 범위

일반 수집 앱의 기본 TCP 주소는 `127.0.0.1:9090`이다. `INGESTION_TCP_ADDRESS/PORT`로 바꿀 수 있고 Compose는 컨테이너 내부 0.0.0.0, 호스트 공개는 127.0.0.1만 사용한다. bootstrap 모드는 TCP/DB를 만들지 않는다. 일반 `/readyz`는 DB와 TCP 입구 준비를 확인한다.

S03-02는 보고서 양식과 번호를 검사하고, S03-03은 원본과 전달 대기를 함께 저장한다. S03 네 작업을 함께 완료했으므로 TCP 입구는 이 저장 경로까지 연결되어 있다. 관제 업무 처리·서버 간 전달·GUI LIVE는 S04 이후 범위다.
