## 이번 작업은 무엇인가

지금까지는 Python 프로그램을 켜고 끄는 방법을 만들었다. 이번에는 그 프로그램 안에 **공장의 배치 설정**, **실행의 식별자**, **차체와 가상 태그의 등록부**, **현재 위치를 한 곳에만 보관하는 규칙**을 만들었다.

공장에 비유하면 셀·주차면·차량·경로의 배치도를 확정하고, 들어온 차체에 이름표를 붙여 등록한 단계다. 아직 작업 셀이 조립하거나 AGV가 운송하는 단계는 아니다.

이 모델은 Python 메모리에 있다. DB에 저장하거나 서버/화면에 보내지 않는다. 서버와 GUI 없이 실행해 규칙을 확인할 수 있다.

## 실행 설정은 어떤 역할인가

`default-run.json`에는 seed, sourceId와 공장 config를 넣었다. 공장 config는 기존 v1 RUN_STARTED의 구성 규격과 같다. 기본 파일은 계약 예제에서 출발했지만 실행 시 contracts 예제를 읽거나 기존 JS 샘플 모델에 의존하지 않는다.

| 설정 | 기본값 / 의미 |
|---|---|
| tickMs | 100ms. 후속 물리 모델이 한 번 진행할 시간 |
| snapshotIntervalMs | 500ms. 후속 상태 보고 간격, tick의 배수 |
| speed | 1배속 |
| maxBodies | 100대. 실행에서 등록할 차체의 전체 상한 |
| seed / failProbability | 42 / 0.01. 후속 검사 결과 생성의 기준; 현재 검사는 미구현 |
| 셀 | ASM-01·ASM-02·QC-01, 작업 시간 4/6/3초 |
| Bay | 각 셀 3칸, 구성 허용 범위 2~4칸 |
| 차량 | 차체 AGV 2대, 부품 AMR 1대 |
| 경로 | 투입→3셀→GOOD/HOLD의 고정 비순환 경로와 별도 부품 경로 |

설정 파일을 읽을 때 잘못된 범위, 빠진 셀, 잘못된 참조, 슬롯 수 불일치, 경로 좌표 불일치 등을 거절한다. 숫자 자리에 true를 넣거나 JSON 키를 중복한 것도 허용하지 않는다. 설정이 틀린 상태로 공장을 켜지 않는다.

읽은 설정은 실행 동안 변경할 수 없도록 고정한다. 예를 들어 실행 중 외부 코드가 원래 설정 사전의 버퍼 용량을 바꾸더라도 이미 만든 모델의 용량은 바뀌지 않는다. 다른 설정으로 실행하려면 새 모델/run을 만든다.

`configuration.py`는 기존 TCP 연결 대상 설정, `run_configuration.py`는 새 공장 설정이다. **공장 배치 설정과 네트워크 접속 설정은 서로 다른 역할**이다.

## runId와 차체·태그 번호는 왜 필요한가

새 모델마다 UTC 시작 날짜와 UUID v4로 runId를 만든다. 같은 seed와 같은 설정으로 다시 시작해도 runId는 다르다. 두 실행의 `body-00001`을 같은 차체로 취급하지 않도록 한다.

일반 등록은 다음처럼 시작한다.

| bodyId | tagId | 초기 위치 |
|---|---|---|
| body-00001 | tag-00001 | INPUT / BODY-IN |
| body-00002 | tag-00002 | INPUT / BODY-IN |
| body-00003 | tag-00003 | INPUT / BODY-IN |

등록부는 bodyId와 tagId가 각각 실행 안에서 고유한지 확인한다. 태그 ID를 조회하면 연결된 차체 하나를 찾는다. 같은 번호를 자동 생성하는 기본값과 별도로, 명시적으로 `body-00001 ↔ tag-00009`처럼 등록할 수도 있다. **숫자 부분이 같아서 연결되는 것이 아니라 실제 등록 관계가 기준**이다.

중복 ID·잘못된 모델 코드·상한 초과는 거절한다. 실패한 등록은 기존 차체를 바꾸거나 자동 번호를 소모하지 않는다. 같은 run에서 등록 차체를 삭제해 번호를 재사용하는 기능도 없다.

이는 가상 이름표 등록이다. 실제 무선 태그 리더나 위치 측정 장치를 구현한 것은 아니다.

## 차체가 한 곳에만 있다는 것은 어떻게 보장하는가

차체마다 변경 불가능한 `Body` 객체가 하나 있고, 그 안에 현재 `Location` 하나만 둔다. 셀·Bay·AGV에 별도의 변경 가능한 차체 목록을 동시에 저장하지 않는다. “이 셀의 차체”는 차체 등록부의 현재 위치를 읽어 얻는다.

| 위치 | 보유 규칙 |
|---|---|
| INPUT / BODY-IN | 등록 상한 안에서 여러 차체 대기 가능 |
| CELL / 셀 ID | 작업 자리당 차체 최대 1대 |
| BUFFER / Bay ID + slot ID | 실제 면당 차체 최대 1대; 구성에 있는 면만 허용 |
| VEHICLE / AGV ID | 차체 AGV당 최대 1대; 부품 AMR은 차체를 보유할 수 없음 |
| RESULT / GOOD 또는 HOLD | 여러 반출 차체의 기록 보존 가능 |

현재 위치 변경의 내부 기초 함수는 **기대하는 출발 위치가 맞는지 → 목적지가 등록돼 있고 비었는지 → 차체 객체 한 번 교체** 순서로 처리한다. 교체할 때 기존 위치 소유가 사라지고 새 위치 소유가 생긴다. 실패하면 기존 차체와 모든 조회 결과가 유지된다. 모델을 만든 스레드에서만 변경 명령을 받는다.

이 함수는 앞으로 작업/운송 코드가 사용할 내부 부품이다. **현재 공개 CLI에 차체 이동 명령을 추가한 것은 아니다.** 경로 순서·공정 완료·예약·픽업 같은 업무 조건은 S02-02~04에서 상위 동작이 검사해야 한다. 이 기초 함수를 검사한 것을 실제 AGV 운송 성공으로 기록하지 않는다.

테스트용 초기 배치는 별도의 명시적 fixture 모드에서만 CELL/BUFFER에 등록할 수 있다. 일반 기동/일반 등록에는 이 우회 모드가 켜지지 않는다. 초기 배치도 자리 중복과 슬롯 유효성 검사를 통과해야 한다. 완전한 작업 상태 fixture는 후속 상태 모델과 함께 구성한다.

## 서버 없이 직접 확인하기

프로젝트 루트에서 실행한다. S01의 가상환경을 사용하며 필요하면 setup을 한 번 수행한다.

```sh
scripts/simulator.sh setup
scripts/simulator.sh run --inspect-model --initial-bodies 3
```

`--inspect-model`은 TCP 주소 설정이나 서버 기동이 필요 없다. 새 run과 차체 3대를 만들고 로컬 설명 JSON을 출력한 뒤 종료한다. 출력에는 다음 구분이 있다.

```json
{
  "modelPreview": true,
  "modelState": "INITIALIZED",
  "factoryRunStarted": false
}
```

차체 3대는 모두 BODY-IN에 있다. 이는 로컬 등록 결과이며 v1 사건 봉투나 완전한 FACTORY_SNAPSHOT이 아니다. sourceSeq·eventId를 발급하거나 TCP로 송신하지 않는다. 조립/물리 시간도 진행하지 않는다.

설정을 바꾸려면 기본 JSON을 복사해 수정한 뒤 `--config /절대/경로/run.json`을 지정한다. 잘못된 파일은 시작을 거절한다. 실제 장기 실행은 기존 TCP 대상 환경 변수를 요구하며, 모델 초기화 후 기본 heartbeat 루프를 유지한다. 현재 생산을 시작하지는 않는다.

## 필요한 최소 검증과 실제 결과

새 모델 테스트는 3개로 묶었다. 기존 접속 설정 테스트 1개를 포함한 Python 테스트는 총 **4개 통과**했다.

| 테스트 | 핵심 확인 |
|---|---|
| 공장 설정 | 버퍼 2/4칸 허용; 용량/슬롯/보고 간격/seed/경로/셀 오류 거절; 설정 고정 |
| 등록·실행 격리 | UTC runId, run마다 새 ID, 태그 매핑, 중복/상한 거절, 실패 시 번호 보존, 등록 데이터 직접 변경 거절 |
| 단일 위치 소유 | 동일 셀·슬롯·AGV 중복 거절, 부품 AMR 적재 거절, 기대 출발 위치 검사, 실패 시 상태 보존, 성공 시 옛 위치 보유 제거 |

```sh
scripts/simulator.sh test
scripts/simulator.sh run --inspect-model --initial-bodies 3
scripts/dev-stack.sh compose up -d --build --wait factory-simulator
```

실제 로컬 설명 JSON은 `.build-cache/s02-01-model-preview.json`에 남겼다. 차체 3대의 tagId와 BODY-IN 위치가 확인됐다. 시뮬레이터 컨테이너만 새 이미지로 갱신했고 healthy가 됐다. 로그는 MODEL_INITIALIZED / registeredBodyCount=0 / factoryRunStarted=false다. Compose 기본 실행은 신규 차체를 자동 등록하지 않는다.

설정 오류 처리와 fixture 입력 방어를 보완한 뒤 영향받은 새 모델 테스트 3개만 재확인했다. DB/Java/GUI/기존 계약 전체 테스트는 반복하지 않았다. 등록/위치 규칙은 Python에서 직접 검증했고 JS 샘플 결과로 대체하지 않았다.
