# 작업 33. S08-01 만석·예약 반환과 셀 정지·정상화

> 작업 ID: S08-01 · 완료일: 2026-10-05 · 상태: 완료 · 검증 결과는 [S08 통합 기록](<../development/S08 장애·복구 통합 검증.md>) 참고

이번 작업은 공장 규칙이 Python 안에서만 맞는 것이 아니라, 실제 서버를 통과한 뒤에도 같은 의미로 보이는지 확인하는 작업입니다. 공장의 물리 상태를 결정하는 주체는 Python이고, 두 Spring 서비스와 Vue는 그 결과를 저장하고 관측합니다.

## 무엇을 확인했는가

검증 도구는 정상 BODY-IN 등록과 실제 모델 명령으로 공장을 움직입니다. 시험용 위치 이동이나 화면 JSON을 만들어 끼워 넣지 않습니다. `P0Driver`가 특정 상태에서 진행을 잠시 멈추므로 서버 조회와 모델 상태를 같은 지점에서 비교할 수 있습니다.

| 상황 | 기대하는 의미 |
|---|---|
| 출발 전 취소 | 예약 한 번 반환, 차체는 출발지 유지 |
| 같은 취소 반복 | 사건·반환을 추가하지 않음 |
| W2/R1/C3 | 여유 0, 추가 배출 금지; 예약 차체는 아직 출발 셀 또는 AGV |
| 목적 셀 DOWN 상태에서 예약 AGV 도착 | 도착을 허용하고 W3/R0/A0, 셀 진입은 기다림 |
| 출발 셀 DOWN | 조립을 끝낸 차체도 셀에서 대기 |
| 알람 확인 | 확인자만 기록, 고장·예약은 유지 |
| 셀 복구와 실제 차체 진입 | W2/R0/A1, 이후 재배차 가능 |

슬롯은 자리 예약표입니다. 예약한 차체는 실제로 그곳에 아직 없으므로, 차체 총수를 계산할 때 예약 수를 더하면 안 됩니다. 도착은 `R → W`, 셀 진입은 `W 감소`입니다.

## 어떤 파일이 어떤 역할인가

- [verify-recovery.py](../../scripts/verify-recovery.py): 위 상황을 실제 TCP→수집 DB→HTTP→관제 DB→조회 경로로 실행하고 비교합니다.
- [verification_runtime.py](../../scripts/verification_runtime.py): 검증 전용 서버와 DB를 띄우고, 그 프로세스만 종료합니다.
- [기존 공장 모델](../../services/factory-simulator/factory_simulator/model.py): 배차·적재·도착·셀 진입을 결정합니다. 검증 때문에 생산 규칙을 바꾸지 않았습니다.

현재 개발용 Compose와 기존 데이터에는 장애를 주입하지 않습니다. 성공·실패한 검증 DB와 원본을 별도 경로에 보존하며, 확인한 결과와 남은 범위는 통합 기록에 구분합니다.
