# 작업 2. 식별자와 사건 데이터 규격

> 작업 ID: S00-02 · 작업일: 2026-10-04~05  
> 상태: 완료 — 사건 데이터 규격·공통 예제와 필요한 예제 확인  
> 선행 작업: [작업 1](<작업 1. 서비스 책임과 데이터 소유권.md>)

## 1. 이번에는 무슨 일을 했나

작업 1에서는 각 프로그램의 담당을 정했다. 이번에는 그 프로그램들이 서로 주고받는 **공장 보고서의 양식**을 정했다. Python이 ‘차체가 도착했다’고 보내면 Java가 어떤 차체·차량·슬롯을 뜻하는지 알아야 하고, 재전송된 보고서도 구분해야 한다.

양식의 기준은 [v1 사건 계약](../../contracts/v1/events.md)에 기록했다. 실제 서버나 DB 기능을 만든 단계는 아니지만, 이후 구현에서 입력과 기대 결과를 함께 참고할 자료가 생긴다. 기술 스택은 그대로 유지했다.

## 2. JSON과 계약은 무엇인가

JSON은 프로그램들이 데이터를 주고받는 글쓰기 형식이다. 아래처럼 ‘항목 이름: 값’을 적는다.

```json
{"bodyId":"body-00042","tagId":"tag-00042"}
```

`bodyId`는 차체 이름, `tagId`는 붙어 있는 가상 태그 이름이다. `{}`는 항목을 묶은 객체, `[]`는 여러 항목의 목록이며, `null`은 지금 연결된 값이 없다는 뜻이다. `0`이나 빈 문자열과 의미가 다르다.

계약은 항목 이름뿐 아니라 ‘반드시 있는 항목인지’, ‘숫자인지 글자인지’, ‘어떤 값이 가능한지’, ‘서로 어떤 관계인지’를 정한 약속이다. 예를 들어 빈 슬롯은 소유자가 없어야 하고, 예약 슬롯은 차체·차량·운송·예약이 연결돼야 한다.

이번에 만든 규격은 사람이 읽는 필드 표와 실제 JSON 예제다. 별도 시스템이나 새 기술 스택을 도입한 것이 아니다.

## 3. 이름표가 여러 개인 이유

| 이름 | 쉬운 의미 | 필요한 이유 |
|---|---|---|
| runId | 공장을 한 번 실행한 회차 번호 | 실행을 다시 시작해도 이전 생산량과 섞이지 않음 |
| bodyId / tagId | 차체 번호 / 검색할 가상 태그 번호 | 태그로 같은 차체의 상태를 계속 찾음 |
| cellId / bufferId / slotId | 작업 셀 / 대기장 / 대기장 안 한 면 | 셀 작업 자리와 대기 공간을 구분 |
| vehicleId | AGV나 AMR의 이름 | 어떤 차량이 무엇을 운반하는지 연결 |
| transportId | 한 구간의 운송 작업 번호 | 다음 셀로 다시 이동하면 새 운송으로 기록 |
| reservationId | 목적지 공간을 먼저 약속한 번호 | 실제 도착 전에도 마지막 슬롯의 주인을 정함 |
| operationId / inspectionId | 한 작업 / 한 최종 검사의 번호 | 같은 완료 보고가 반복돼도 같은 사실임을 구분 |
| eventId | 보고서 한 장의 번호 | 보고서를 재전송해도 새 사건으로 오해하지 않음 |
| sourceSeq | 같은 송신원의 보고서 작성 순서 | 늦게 받은 과거 상태가 최신 상태를 덮지 않음 |

`body-00001`이 두 실행에 있어도 runId가 다르면 다른 차체다. 한 run 안에서는 차체와 태그의 연결을 바꾸지 않는다. `unitId`는 작업·검사 보고에서 쓰는 이름이며 값은 bodyId와 동일하다. 부품 키트는 `partsKitId`를 사용해 차체와 구분한다.

## 4. 보고서 번호와 시간은 다르다

예를 들어 sourceSeq=30인 상태 보고 뒤에 33번 보고가 도착했다고 하자. 나중에 30번이 다시 도착해도 현재 화면의 근거를 30번 상태로 되돌리지 않아야 한다. 다만 늦게 도착한 **검사 결과**는 과거 검사 사실로 보관할 수 있다. 현재 상태와 업무 이력을 따로 보는 이유다.

재전송할 때는 eventId·sourceSeq·발생 시각·내용을 그대로 보낸다. ‘다시 보냈으니까 새 번호’로 바꾸면 같은 검사 결과가 새로운 검사처럼 보일 수 있다. 번호를 보고 중복을 막는 실제 코드는 이후 구현한다.

| 시간 | 뜻 |
|---|---|
| occurredAt | Python에서 사건을 만든 때 |
| capturedAt | 공장 전체 상태를 얻은 때 |
| receivedAt / committedAt | 수집 서비스가 처음 받고 저장한 때 |
| appliedAt | 관제 서비스가 업무 기록으로 반영한 때 |
| publishedAt | 관제가 화면으로 정보를 내보낸 때 |
| simElapsedMs | 물리 공장이 진행한 누적 시간. 일시 정지 중에는 멈춤 |

보고서에는 UTC 시각을 넣고 화면에서는 한국 시간으로 바꾼다. `2026-10-04T04:00:01.000Z`는 한국 시간 13:00:01이다. 일시 정지 중 새 상태 보고의 시각은 갱신할 수 있지만 차체 작업 시간과 위치는 멈춘다. 그래서 ‘공장을 멈춘 것’과 ‘새 보고를 못 받은 것’을 구분할 수 있다.

## 5. 버퍼 예제를 차례대로 읽기

[버퍼 수명 예제](../../contracts/v1/examples/buffer-lifecycle.ndjson)는 한 줄에 JSON 보고서 하나를 넣는 NDJSON 파일이다. 공장 실행 전체 기록이 아니라 이미 차체가 있는 상황의 일부 구간이며, 실제 서버 실행 로그는 아니다.

| 상태 보고 순번 | 대기 W | 예약 R | 총 C | 남은 A | 차체 42의 실제 위치 |
|---|---:|---:|---:|---:|---|
| 30: 마지막 면 예약 | 2 | 1 | 3 | 0 | ASM-01 셀, 픽업 전 |
| 33: AGV 인계 완료 | 3 | 0 | 3 | 0 | BAY-ASM-02 |
| 37: 대기 차체 40이 셀 진입 | 2 | 0 | 3 | 1 | 차체 42는 계속 Bay 대기 |

첫 상태에서 42번 차체는 예약은 있지만 아직 앞 셀에 있다. 새 차체를 위한 추가 예약은 막히지만, **이미 자기 면을 예약한 42번의 픽업·도착은 진행할 수 있다.**

도착하면 ‘예약 1’이 ‘대기 1’로 바뀌므로 사용 슬롯은 여전히 3이다. 도착했다는 이유로 새 차체를 더 보내면 안 된다. 예제에서 ASM-02는 처음에 고장으로 멈춰 있고, 복구된 뒤 40번 차체를 받는다. 40번이 작업 자리로 들어가면 Bay의 실제 대기가 줄어 한 면을 반환한다.

보고서에는 셀·차체·슬롯·AGV·운송을 함께 넣었다. Java에서 ‘슬롯에는 42번 예약이 있는데 해당 운송이 없다’ 같은 입력을 확인할 수 있게 하기 위해서다. 알람 확인이나 통신 단절은 슬롯을 돌려주는 동작이 아니다.

## 6. 사건과 현재 상태를 구분하는 이유

`SLOT_RESERVED`는 ‘예약이 생겼다’는 이력이고 `FACTORY_SNAPSHOT`은 ‘지금 모든 면이 어떻게 돼 있다’는 보고다. 둘을 받았다고 예약 수를 두 번 더하지 않는다. 현재 값은 최신 전체 스냅샷에서 읽고, 이력은 해당 일이 일어났다는 설명으로 사용한다.

마찬가지로 생산량은 `INSPECTION_COMPLETED`의 고유 검사 사실로 계산한다. 스냅샷을 여러 번 받았다고 생산량이 증가하는 구조로 만들지 않는다. 검사 완료 차체가 아직 AGV에 실려 있을 수도 있으므로 검사 상태와 위치를 따로 적는다.

부품 AMR의 예제에는 부품 키트와 전용 도착 지점을 사용하고 reservationId/slotId는 null로 두었다. 부품 이동을 차체 Bay의 슬롯 사용량에 섞지 않기 위해서다.

## 8. 결과와 필요한 최소 확인

이번에는 문서·공통 예제와 그 확인 도구만 바뀌므로 서비스 기동·DB·GUI 테스트는 하지 않았다. Python 3.12.1의 표준 라이브러리로 JSON 읽기, 사건 봉투/payload의 필수 항목, 번호/시각·핵심 참조 관계, 버퍼 2+1→3+0→2+0과 차체 단일 위치를 확인했다. 새 패키지를 설치하지 않았다.

잘못된 입력의 확인은 **필수 runId 누락, 예약이 없는 운송을 참조, 차체를 셀과 Bay에 중복 보유, 부품 운송에 차체 예약 지정** 네 사례만 골랐다. 이 도구가 오류를 발견했다는 뜻이며, 미구현 수집/관제 서비스가 실제로 거절했다는 증거는 아니다.

최종 검토에서 픽업~도착의 예제 시각을 경로 구성의 4초 이동 시간과 맞췄다. 픽업은 13:00:02, 도착은 13:00:06, 셀 진입은 13:00:06.500이다. 예제를 수정하고 경로 시간 대조를 추가했으므로 영향을 받는 예제 확인만 다시 실행했다. 전체 테스트로 넓히지 않았다.

| 항목 | 결과 |
|---|---|
| 규격 | v1 사건 봉투·식별자·시각/순번·17종 payload·구성/전체 상태 정의 |
| 예제 | 독립 사건 17종, 수명 구간 10개 NDJSON 프레임과 전체 스냅샷 3개 |
| 실행 명령 | `python3 scripts/check_contract_examples.py` |
| 기대 결과 | 예제 형식·연결 정상, 예약 시 출발지 유지, 도착 시 여유 0, 셀 진입 후 여유 1 |
| 실제 결과 | 통과 — 사건 17종·프레임 10개·스냅샷 3개 일치, 대표 오류 4개 발견, 최대 프레임 4,553바이트(LF 포함) |
| 문서 확인 | 통과 — 관련 문서 6개의 로컬 링크 54개 정상. S00-01~02만 완료, S00은 진행 중, 다음 작업 S00-03 |
| 변경 기록 | 계약·예제·확인 도구·이 설명 작성, 계획/README 진행 상태와 기획서/해설집의 계약 참조 반영 |
| 구현 범위 | 사건 계약과 예제 확인 도구. 실제 송신·수집·DB·업무 처리 코드는 미구현 |
| 다음 작업 | S00-03: 저장 확인 응답과 서비스 간 전달·오류 처리 계약 |

예제 확인의 실제 출력은 다음과 같다.

```text
PASS: 17 event kinds, 10 NDJSON frames, 3 coherent snapshots, 4 representative errors rejected; W/R/A=[(2, 1, 0), (3, 0, 0), (2, 0, 1)]; max frame=4553 bytes (LF included).
```

문서의 로컬 링크와 진행 상태는 Python의 일회성 확인 명령으로 별도 확인했다. 예제 한 개의 최대 크기가 상한 안이라는 결과를 차체 100대·수백 대 차량의 성능/크기 검증으로 확대하지 않는다. 실제 TCP 분할/결합·저장·재전송·중복 반영은 후속 작업에서 확인한다.
