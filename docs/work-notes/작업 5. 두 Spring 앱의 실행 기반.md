# 작업 5. 두 Spring 앱의 실행 기반

> 작업 ID: S01-01 · 완료일: 2026-10-05  
> 결과: 수집/관제 앱의 독립 빌드·기본 설정·골격 기동·최소 테스트 구조 준비 완료. DB와 공장 업무 기능은 다음 작업부터 구현한다.

## 1. 이번 작업은 무엇인가

앞의 네 작업에서는 서비스의 역할과 서로 주고받을 자료를 정했다. 이번에는 그 설계를 담을 **실제 Java 프로그램 두 개**를 만들었다.

수집 앱은 공장 보고서를 접수하고 저장·전달하는 담당자이고, 관제 앱은 받은 보고서를 해석해 현재 상태·이력·화면 자료를 만드는 담당자다. 지금은 담당자별 프로그램의 시작점과 실행 방법을 준비한 단계다. 보고서를 실제로 접수하거나 태그 창에 값을 보내는 기능까지 만든 것은 아니다.

각 앱은 자기 폴더에서 빌드할 수 있다. 관제 앱을 빌드하기 위해 수집 앱을 먼저 설치할 필요가 없다. 앞으로 한쪽을 바꿨을 때 그쪽만 필요한 테스트로 확인할 수 있게 만드는 기반이다.

## 2. Java·Spring·Maven은 각각 무슨 일을 하나

| 구성 | 쉬운 역할 | 이번에 한 일 |
|---|---|---|
| Java 21 JDK | Java 코드를 실행 가능한 코드로 바꾸고 실행하는 도구 | 기존 설치 Temurin 21.0.7+6을 확인해 사용 |
| Spring Boot | 웹 서버·설정·라이브러리 연결에 필요한 기본 구성을 준비 | 앱마다 별도 main과 웹 서버 설정 생성 |
| Maven | 필요한 라이브러리를 받고 컴파일·테스트·패키징을 진행 | 앱마다 pom.xml 생성 |
| Maven Wrapper | 이 프로젝트에서 정한 Maven 버전을 자동으로 실행 | Maven 3.10.0 / Wrapper 3.3.4 고정 |
| JDBC / JdbcClient | Java에서 SQL로 DB를 읽고 쓰는 기반 | JDBC 의존성 준비, 실제 SQL은 이후 작업 |
| Flyway | DB 구조 변경 파일을 순서대로 적용하고 이력을 관리 | 의존성·검증/clean 금지 설정 준비, SQL 파일은 S01-02 |
| JUnit | 필요한 자동 검증을 실행하는 도구 | 앱당 골격 기동 테스트 1개 |

빌드는 코드를 실행 가능한 결과물로 만드는 과정이다. 이번 결과물은 각 앱의 **JAR 파일**이다. JAR에는 앱 코드와 실행에 필요한 라이브러리가 묶여 있으며 `java -jar …`로 시작할 수 있다. 소스 컴파일 성공과 JAR에 최신 코드가 들어갔는지는 별도로 확인했다.

Spring Boot **4.1.1**로 묶음을 고정했고, 하위 라이브러리는 그 버전이 관리하는 조합을 사용한다. 기존 Java·Spring·JDBC·PostgreSQL·Flyway·Maven 기술 스택을 유지했다. [실행 버전과 근거](<../development/실행 버전과 빌드 기준.md>)에 실제 버전과 공식 문서 링크를 적었다.

## 3. 파일은 어떻게 나뉘나

`services/ingestion-service/`와 `services/operations-service/`에 각각 다음 파일을 만들었다.

| 파일 | 역할 |
|---|---|
| pom.xml | 앱 이름·Java/Spring 버전·의존성과 빌드 방법 |
| mvnw / mvnw.cmd | macOS/Linux 및 Windows용 Maven 실행 시작점 |
| .mvn/wrapper/maven-wrapper.properties | 다운로드할 Maven 버전과 SHA-256 |
| src/main/java/…Application.java | 프로그램을 시작하는 main |
| src/main/java/…/configuration/DatabaseSettingsGuard.java | 일반 실행에서 필수 DB 설정이 없으면 명확히 종료 |
| src/main/resources/application.yml | 앱별 이름·주소/포트·DB 환경 변수·Flyway·로그 설정 |
| src/main/resources/application-bootstrap.yml | DB 없이 골격만 확인하는 명시적 실행 모드 |
| src/test/java/…ApplicationTests.java | 앱 실제 기동과 DB 없는 모드의 경계 확인 |

[service-maven.sh](../../scripts/service-maven.sh)는 프로젝트 루트에서 원하는 앱의 Wrapper를 실행하는 편의 스크립트다. 다운로드와 의존성 캐시를 `.build-cache/`에 두어 사용자 전역 Maven 설치/설정을 바꾸지 않는다. .gitignore에는 캐시·빌드 결과·로컬 비밀 설정을 제외하도록 적었다.

## 4. 왜 bootstrap 모드를 따로 두었나

DB는 다음 작업에서 만든다. 그런데 Spring JDBC/Flyway를 준비한 앱을 일반 실행하면 DB 연결이 필요하다. 이때 가짜 DB를 넣어 정상이라고 표시하면 실제 준비 상태를 오해할 수 있다.

그래서 `bootstrap`을 **직접 지정했을 때만** DB와 Flyway를 제외하고 웹 서버 골격을 시작하게 했다. 일반 실행에서 이 모드를 자동 선택하지 않는다. 일반 실행은 각 서비스의 DB URL·사용자·암호가 없거나 비어 있으면 필요한 변수 이름을 알려주고 종료한다. 오류에 암호/설정값은 출력하지 않는다.

수집 앱의 기본 HTTP 포트는 8081, 관제 앱은 8082다. 포트는 같은 컴퓨터에서 어느 프로그램으로 연결할지 구별하는 번호다. 기본 주소는 127.0.0.1로, 현재 컴퓨터 안에서 접속한다. 아직 화면 조회 컨트롤러가 없어 `/`와 계획된 `/api/v1/…`이 404인 것은 정상이다. TCP 수집 리스너·SSE·readiness도 이후에 만든다.

## 5. 실행 방법

프로젝트 루트에서 한 앱씩 빌드한다.

```sh
scripts/service-maven.sh ingestion-service --batch-mode --no-transfer-progress verify
scripts/service-maven.sh operations-service --batch-mode --no-transfer-progress verify
```

각 명령은 해당 앱을 컴파일하고 최소 테스트를 실행한 뒤 JAR로 묶는다. 첫 실행은 공식 저장소의 의존성을 내려받아야 한다. 캐시가 준비됐다면 `--offline`을 더해 인터넷 없이 빌드할 수 있다.

골격 실행은 각각 다른 터미널에서 한다.

```sh
scripts/service-maven.sh ingestion-service spring-boot:run -Dspring-boot.run.profiles=bootstrap
```

```sh
scripts/service-maven.sh operations-service spring-boot:run -Dspring-boot.run.profiles=bootstrap
```

자세한 환경 변수와 JAR 실행 방법은 [서비스 실행 안내](../../services/README.md)에 있다. 아직 실제 DB 기동이나 공장 화면 연결 명령은 아니다.

## 6. 꼭 필요한 검증과 결과

이번 변경은 앱 시작/설정/빌드 기반이다. 슬롯·검사·TCP·GUI의 전체 테스트는 하지 않았다. 각 앱의 테스트는 실제 임시 포트로 웹 서버를 띄우고, 앱 이름이 맞으며 DB/Flyway가 생성되지 않는지 확인한다. main을 실제로 호출하는 테스트라 시작 시 설정 검증도 함께 실행된다.

최종 코드 기동 검증 명령:

```sh
scripts/service-maven.sh ingestion-service --offline --batch-mode --no-transfer-progress verify
scripts/service-maven.sh operations-service --offline --batch-mode --no-transfer-progress verify
```

| 확인 | 실제 결과 |
|---|---|
| 수집 앱 기동·컴파일 | BUILD SUCCESS, Tests run: 1 / Failures: 0 / Errors: 0 |
| 관제 앱 기동·컴파일 | BUILD SUCCESS, Tests run: 1 / Failures: 0 / Errors: 0 |
| 실행 JAR | 두 앱 모두 해당 main/최신 설정 검증 클래스 포함 확인 |
| 필수 DB 설정 없는 일반 모드 | 두 앱 모두 종료 코드 1, 필요한 DB 변수 3개 명시, JDBC 연결 시도 전에 종료 |
| 문서·경로 | 로컬 링크 154개 연결, 두 앱 버전/Wrapper 일치와 완료 상태 확인 |

필수 설정 누락 확인은 다른 셸 설정이 섞이지 않도록 PATH/LANG/TZ만 전달한 별도 프로세스로 했다. 웹 포트가 필요 없는 이 확인에서는 다음 JAR 명령을 사용했다(서비스별 한 번).

```sh
java -jar services/ingestion-service/target/ingestion-service-0.1.0-SNAPSHOT.jar --spring.main.web-application-type=none
java -jar services/operations-service/target/operations-service-0.1.0-SNAPSHOT.jar --spring.main.web-application-type=none
```

두 명령은 실패 종료가 기대 결과다. DB 변수가 없는 상태에서 `missing required DB settings`와 서비스별 변수 이름만 보였고, 암호/설정값은 넣지 않았다.

관제 앱의 최초 기동 테스트는 샌드박스의 `SocketException: Operation not permitted`로 실패했다. 실제 localhost 소켓을 사용할 수 있는 허용 환경에서 같은 테스트를 실행해 통과했다. 테스트를 가짜 웹 서버로 바꾸어 성공 처리하지 않았다.

일반 실행의 처음 오류가 JDBC 드라이버 메시지여서 필수 변수 이름을 명확히 알려주는 시작 검증을 추가했다. 이 코드 변경 때문에 앱별 기동 검증을 다시 수행했다. 그 뒤 패키징 확인에서 고정한 미래 시각 때문에 이전 JAR을 재사용하는 문제를 발견했다. 그 설정을 제거하고 **생성된 JAR만** 다시 만든 후 최신 클래스 포함을 확인했다. 기동 테스트는 다시 반복하지 않고 다음 패키징 명령에서 생략했다.

```sh
scripts/service-maven.sh ingestion-service --offline --batch-mode --no-transfer-progress -DskipTests verify
scripts/service-maven.sh operations-service --offline --batch-mode --no-transfer-progress -DskipTests verify
```

최종 JAR과 기존 테스트 결과는 각 target에 남겼고 빌드/설정 실패 확인 로그는 `.build-cache/verification/`에 보관했다. Windows 실행, 실제 PostgreSQL 접속·권한·마이그레이션, Compose, Python/Vue, 업무 기능은 이번에 검증하지 않았다. S00 계약 자료는 변경하지 않아 기존 예제 테스트도 반복하지 않았다.
