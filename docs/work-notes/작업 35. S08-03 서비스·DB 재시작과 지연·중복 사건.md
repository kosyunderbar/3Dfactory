# 작업 35. S08-03 서비스·DB 재시작과 지연·중복 사건

> 작업 ID: S08-03 · 완료일: 2026-10-05 · 상태: 완료 · 검증 결과는 [S08 통합 기록](<../development/S08 장애·복구 통합 검증.md>) 참고

MSA로 서비스를 나눈 의미를 확인하는 작업입니다. 수집 서비스가 저장을 끝내도 관제 서비스는 잠시 중단될 수 있습니다. 어느 쪽에서 멈췄는지 구별하고, 각 서비스가 맡은 기록을 보존해야 합니다.

## 장애마다 누가 기다리는가

| 장애 지점 | 기다리는 곳 | 복구 기준 |
|---|---|---|
| 수집 TCP/서비스 | Python 미확인 원본 | 동일 원본의 정상 저장 ACK |
| 수집 DB | Python 미확인 원본 | DB 복구 후 commit/ACK |
| 관제 서비스 | 수집 DB outbox | 관제의 업무 commit 확인 |
| 관제 DB | 수집 DB outbox | 같은 head 사건 재전달 후 확인 |
| PostgreSQL 프로세스 | Python와 영속 outbox | 같은 데이터 디렉터리 재시작 후 재처리 |

outbox는 ‘저장했지만 다음 서비스에서 처리 확인이 끝나지 않은 사건 목록’입니다. 서버 재시작에도 DB에 남아 있고, 처리 완료가 확인되기 전에는 전달 순번을 넘기지 않습니다.

## 복원과 최신 보고는 다르다

관제 서버를 다시 띄우면 DB의 마지막 위치를 읽을 수 있습니다. 하지만 지금도 그 위치라는 새 보고를 받은 것은 아니므로 `RESTORING`입니다. 새 sourceSeq의 전체 스냅샷을 받은 뒤에 최신 관측으로 전환합니다. 서버 시작마다 `serverEpoch`도 바뀌어 이전 서버의 화면 순번과 구별합니다.

## 늦은 기록과 중복 기록

작업·운송·검사는 실제로 일어난 사실의 기록입니다. 늦은 고유 검사 결과는 보관하고 해당 시각의 집계에 반영해야 합니다. 오래된 스냅샷은 이력으로 남길 수 있어도 현재 위치를 되돌리면 안 됩니다.

같은 원본은 한 번만 적용합니다. 다른 eventId로 같은 검사·작업·운송 번호를 다시 제출해도 사실을 중복 생성하지 않습니다. 이를 위해 기존 Java 통합 테스트 중 지연 스냅샷/사실·중복 번호·run 분리와 늦은 검사/페이지 고정 경계에 해당하는 **두 메서드만** 실행합니다.

기존 S05의 내부 HTTP 응답 유실·결과 저장 rollback 검증은 이전 증거를 재사용합니다. 새 통합 실행에서는 실제 서버 중단, 두 DB의 개별 접속 차단, PostgreSQL 프로세스 재시작을 보강합니다.

DB 접속 차단은 검증 전용 DB의 연결을 끊고 신규 연결을 거부하는 방식입니다. 두 논리 DB는 하나의 PostgreSQL 인스턴스에 있으므로 각각의 저장 경계를 이렇게 구별하고, 프로세스 전체 중단도 별도로 확인합니다.

## 실제 완료 결과

최종 격리 클러스터에서 양 서비스/개별 DB/PG 재시작과 RESTORING을 확인했다. Java의 지연/중복 경계2개도 통과했다. 성공·실패 모두 데이터는 남기며, 최종 ownedProcessesStopped=true다. 상세 실행 번호·원본·DB·로그와 캡처 위치는 S08 통합 기록에 있다.
