# 작업 12. 슬롯 예약과 AGV 배차

> 계획 ID: S02-03 · 작업일: 2026-10-05 · 상태: 완료  
> 선행: S02-01~02 공장 설정·차체/태그·셀 작업·검사  
> 다음: S02-04 픽업·이동·Bay 인계·셀 진입·슬롯 반환·재배차

## 이번 작업은 무엇인가

앞 작업에서 셀의 조립·검사가 끝나면 차체가 작업 셀 안에 남도록 만들었다. 이번에는 **그 차체를 다음 장소로 보낼 수 있는지 결정하는 배차 담당자**를 Python에 추가했다.

배차 담당자는 목적지의 빈 슬롯과 차체 운반 AGV를 함께 확인한다. 둘 다 확보할 수 있을 때만 운송을 승인한다. 승인하면 목적지 슬롯에 예약을 걸고 AGV를 해당 운송에 배정한다. **이때 차체를 AGV에 싣지는 않는다.** 픽업·출발·이동·도착은 다음 작업에서 연결한다.

공장에 비유하면 다음 셀의 주차면 하나를 확보하고 운반차 기사에게 같은 운송 번호를 전달하는 단계다. 아직 차체가 출발 셀에 있어도 그 주차면은 다른 차체에게 내줄 수 없다.

## 버퍼의 대기와 예약은 어떻게 세는가

이번 구현은 사용자가 정한 기준을 그대로 따른다.

```text
W = 목적지 Bay에 실제로 대기하는 차체 수
R = 그 Bay 슬롯을 이미 확보한 활성 운송 수
C = Bay의 물리적 슬롯 수
A = C - W - R

W + R >= C이면 신규 배차 승인 거절
```

R에는 **픽업 전 ASSIGNED 운송부터** 포함한다. 아직 AGV가 차체를 싣지 않았다는 이유로 예약을 빼면 여러 차량이 같은 빈자리로 출발할 수 있기 때문이다. 이후 IN_TRANSIT 운송도 같은 예약을 계속 사용한다.

| C | W | R | A | 신규 배차 |
|---|---|---|---|---|
| 3 | 2 | 0 | 1 | 슬롯과 AGV가 있으면 승인 가능 |
| 3 | 2 | 1 | 0 | BUFFER_FULL로 거절 |
| 3 | 3 | 0 | 0 | BUFFER_FULL로 거절 |

셀의 조립 자리는 C에 포함하지 않는다. Bay만 2~4칸이며 기본은 3칸이다. 각 슬롯은 다음 상태 중 하나다.

| 슬롯 상태 | 뜻 |
|---|---|
| FREE | 실제 차체도 예약도 없음 |
| RESERVED | 활성 운송에 해당 자리를 약속함 |
| OCCUPIED | 실제 차체가 해당 Bay/slotId에 있음 |

W와 R을 임의로 올리고 내리는 별도 카운터는 두지 않았다. 실제 차체의 단일 위치와 활성 운송의 슬롯 참조에서 계산한다. `buffer(buffer_id)`는 이 정보를 읽기용 사전으로 반환하므로 출력 내용을 수정해도 실제 모델은 바뀌지 않는다.

## 슬롯과 AGV를 함께 확보한다는 것은 무엇인가

`assign_transport(body_id)`는 다음 순서로 처리한다.

1. 모델이 일시정지가 아닌지, 차체가 INPUT의 신규 대기 차체 또는 작업을 끝낸 CELL의 차체인지 확인한다.
2. 완료 공정 이력으로 다음 목적지를 결정한다. 조립 후에는 다음 셀의 Bay, QC 검사 후에는 PASS→GOOD/FAIL→HOLD다.
3. Bay 목적지이면 W+R와 실제 FREE 슬롯을 확인한다.
4. 다른 운송에 배정되지 않았고 차체도 싣지 않은 IDLE AGV를 찾는다. 부품 AMR은 제외한다.
5. 구성된 경로와 시각을 확인한 뒤 슬롯 예약·운송·차체 참조·AGV 배정을 함께 기록한다.

모델을 만든 스레드 한 곳에서 요청을 순서대로 처리한다. 여러 웹 요청을 그대로 동시에 모델에 쓰는 방식이 아니다. 미래의 외부 요청도 이 변경 흐름에 넣어야 한다.

마지막 한 슬롯을 두 차체가 요구하면 첫 요청이 슬롯과 AGV를 확보한다. 두 번째 요청이 확인할 때는 이미 A=0이므로 거절된다. 두 요청 중 어떤 것을 먼저 처리할지는 호출 순서이며 복잡한 우선순위 스케줄러는 이번 범위가 아니다.

AGV가 없으면 슬롯이 비어 있어도 예약하지 않는다. 시각 검증 등에서 오류가 나도 운송/예약 번호나 자원 일부만 남기지 않는다. 반대로 같은 차체를 반복 요청하면 기존 transportId를 반환하며 예약이나 AGV를 추가로 소비하지 않는다.

## 승인과 실제 배출은 어떻게 구분하는가

| 항목 | 배차 승인 직후 |
|---|---|
| 운송 | ASSIGNED, 시작/완료 시각 null |
| 목적지 Bay 슬롯 | RESERVED |
| 차체 | 출발 INPUT/CELL에 그대로 있음 |
| 조립 완료 차체 상태 | WAITING_UNLOAD 유지 |
| 검사 완료 차체 상태 | COMPLETED 유지 |
| AGV | TO_PICKUP, transportId 보유, 실제 적재 bodyId=null |
| 출발 셀 | BLOCKED, 완료 차체와 operationId 보유 |

차체에는 활성 transportId/reservationId를 연결한다. 슬롯·AGV·운송의 참조도 같은 배정과 일치한다. GOOD/HOLD로 가는 운송은 transportId만 있고 reservationId/slotId는 null이며 Bay 슬롯을 소비하지 않는다.

셀의 blockedReason은 다음처럼 구분한다. 목적지 만석을 차량 부족보다 먼저 확인한다.

| 이유 | 의미 |
|---|---|
| BUFFER_FULL | 목적지 Bay의 W+R≥C라 신규 배차가 불가능함 |
| NO_VEHICLE | 목적지에 자리가 있지만 가용 차체 AGV가 없음 |
| WAITING_PICKUP | 배차 승인 후 픽업을 기다림; 배차 요청 전 로컬 대기 표시에도 사용 |

WAITING_PICKUP이라는 이름만 보고 승인 여부를 판단하지 않는다. **실제 승인 여부는 차체의 활성 transportId와 운송 기록으로 확인한다.** 아직 요청하지 않았으나 슬롯/AGV가 있는 셀도 로컬 대기 이유는 WAITING_PICKUP이다.

작업 완료, 배차, 시험용 자리 변경 때 BLOCKED 셀의 이유를 다시 계산한다. 새 예약으로 A가 0이 되면 아직 배정되지 않은 대상은 즉시 BUFFER_FULL 판단을 받는다. 이미 자기 슬롯을 확보한 차체의 승인을 A=0 때문에 취소하지 않는다. 이유 재계산은 자동 배차를 실행하지 않는다.

일반 모델에는 직접 위치를 바꾸는 우회 동작을 허용하지 않는다. 기존 내부 위치 함수는 명시적인 시험 배치 모드에서만 사용할 수 있게 제한했고, 이미 배차된 차체는 그 함수로도 옮길 수 없다. 운영용 실제 배출은 S02-04의 승인된 운송 수명 동작으로 구현한다. 따라서 이번에는 승인/거절과 차체 보유를 검증했으며 실제 Unload 실행을 검증했다고 주장하지 않는다.

## 시간이 지나도 예약은 유지하는가

예약은 슬롯을 확보한 운송의 상태다. 단순한 시각이나 통신 연결 시간이 아니다. 하루 뒤의 시각을 조회하거나 모델 tick을 진행하거나 일시정지해도 예약을 자동 반환하지 않는다.

이번에는 픽업·도착·취소 명령이 아직 없으므로 승인된 운송은 ASSIGNED에 남는다. Bay 인계 때 RESERVED→OCCUPIED, 셀 진입 때 자리 반환은 S02-04다. 출발 전 취소와 반복 취소/도착 방어는 S02-05다. 통신 끊김으로 예약을 풀어 주는 기능은 추가하지 않았다.

## 서버 없이 직접 확인하기

프로젝트 루트에서 기존 Python 3.12 환경으로 실행한다.

```sh
scripts/simulator.sh run --demo-dispatch
```

출력은 두 개의 별도 run을 사용하는 시험이다.

첫째, ASM-02 Bay를 실제 대기 3대로 채우고 ASM-01 작업을 완료한다. 배차는 BUFFER_FULL로 거절되고 완료 차체는 ASM-01에 WAITING_UNLOAD로 남는다. 그 뒤 시험용으로 대기 한 대를 다른 위치에 배치하고 요청하면 W=2/R=1/A=0으로 승인된다. 차체는 여전히 ASM-01에 남는다.

둘째, ASM-01 Bay에 2대를 배치하고 INPUT의 서로 다른 두 차체가 마지막 한 슬롯을 요구한다. 결과는 다음과 같다.

```json
[
  {"approved": true, "reason": "WAITING_PICKUP", "transportId": "transport-00001"},
  {"approved": false, "reason": "BUFFER_FULL", "transportId": null}
]
```

데모의 자리 제거는 **시험 배치(TEST_ARRANGEMENT_ONLY)**다. 실제 Bay 인계·셀 진입·슬롯 반환을 구현한 것으로 해석하지 않는다. 출력에 demoFixture=true, allocationImplemented=true, physicalTransportImplemented=false를 표시한다. 일반 기동은 기존 MODEL_INITIALIZED와 heartbeat를 유지한다.

실제 기본 출력은 `.build-cache/s02-03-dispatch-preview.json`에 남겼다. --demo-dispatch는 TCP 설정이나 서버가 필요 없고 --initial-bodies와 함께 사용할 수 없다. 시험 차체 수 때문에 maxBodies는 ASM-01/02 중 큰 Bay 용량+1 이상이어야 한다.

**새 테스트는 3개만 추가했다.** 공통 모델 변경에 영향받는 기존 Python 검증을 포함해 총 **10개 통과**했다.

| 새 테스트 | 꼭 확인한 규칙 |
|---|---|
| 마지막 슬롯/예약 | C=2/3/4에서 W=C-1/R=1/A=0, 다음 요청 거절, 픽업 전 출발지 보유, 중복 요청이 기존 배정 반환, 예약 슬롯/AGV 중복 사용 거절, 조회 결과 수정으로 모델 변경 불가 |
| 완료 셀/차량/결과 구역 | 만석 거절 시 완료 차체 보유, 시험용 자리 확보 후 승인, 두 AGV 사용 중 NO_VEHICLE이면 예약 없음, AMR 제외, QC PASS/FAIL 목적지와 예약 미소비 |
| 실패/예약 유지 | 잘못된 시각·정지 중 요청·미완료 셀·알 수 없는 차체 거절, 실패 시 번호/상태 보존, 시간 경과/정지 중 예약 유지, 일반 모델의 직접 이동 우회 거절 |

```sh
scripts/simulator.sh test
scripts/simulator.sh run --demo-dispatch
scripts/dev-stack.sh compose up -d --build --wait factory-simulator
```

Python 시뮬레이터 컨테이너만 새 이미지로 갱신했고 healthy를 확인했다. 기동 로그는 MODEL_INITIALIZED / registeredBodyCount=0 / factoryRunStarted=false다. DB/Java/GUI/기존 계약 전체 검증은 반복하지 않았다. GUI 샘플이나 서버 준비 상태를 배차 규칙의 검증으로 대신하지 않았다.
