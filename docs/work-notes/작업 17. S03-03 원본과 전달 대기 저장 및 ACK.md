# 작업 17. S03-03 원본과 전달 대기 저장 및 ACK

> 작업 ID: S03-03 · 완료일: 2026-10-05 · 상태: 완료  
> PostgreSQL 17.11 · 기존 Flyway V1 유지 · 원본/outbox/실행 정보 동시 저장

검증한 사건을 실제 수집 DB에 저장하고, 저장이 확정된 뒤 Python에 ACK를 보내도록 구현했다. ACK는 “이 보고서를 수집 DB가 맡았다”는 답장이다. 관제 서비스가 검사 실적을 집계하거나 GUI가 차체를 표시했다는 답장은 아니다.

## 세 표가 함께 있어야 하는 이유

| 저장 표 | 역할 |
|---|---|
| raw_event | 받은 원본 문자열·SHA-256·실행/사건/순번·최초 수신 시각 보존 |
| event_outbox | 이 사건을 관제 서비스에 전달할 책임. 신규 상태 PENDING |
| delivery_stream | run의 송신원과 다음 전달 순번. 최초 next_source_seq=1 |

outbox는 보고서 전달 대기 목록이다. 차체가 대기하는 Parking Bay와 다른 공간이다. 보고서가 DB에 안전하게 있어도, 전달 worker가 아직 없으면 관제 서비스에는 반영되지 않는다.

[EventStore.java](../../services/ingestion-service/src/main/java/dev/factory/ingestion/receiver/EventStore.java)는 트랜잭션으로 세 표를 함께 처리한다. 트랜잭션은 여러 저장을 하나의 확정 단위로 묶는 기능이다. raw_event만 쓴 뒤 실패하면 그 원본도 되돌려야 한다. COMMIT은 저장 확정, rollback은 중간 변경 취소다.

처리 순서는 입력 검사 → 기존 원본/충돌 확인 → 신규 사건의 시각·상한 확인 → 실행/원본/outbox 저장 → COMMIT 확인 → 성공 ACK다. Spring의 TransactionTemplate이 COMMIT 뒤 반환한 다음 committedAt을 얻고 답장을 만든다. COMMIT 결과가 불명확하거나 실패하면 DB_UNAVAILABLE 또는 연결 오류로 원본 재전송 책임을 유지한다.

동일 원본의 중복 확인은 신규 접수 제한보다 먼저 한다. outbox/보관 상한에 도달해도 이미 맡은 보고서의 ACK를 다시 줄 수 있다. 최초 receivedAt은 DB에 보관해 중복 ACK에도 유지한다. committedAt은 이번 응답에서 커밋을 확인한 시각이며 최초 COMMIT 순간을 DB에 저장한 값은 아니다.

## 신규 접수 제한

- 발생 시각이 최초 수신 시각보다 5초 초과 미래이면 CLOCK_AHEAD.
- 미전달 outbox는 최대 5,000건·128MiB. DELIVERED 이외의 격리/보류 기록도 포함한다.
- 보관 원본은 run당 50,000건·512MiB, 전체 250,000건·1GiB.

건수와 원본 UTF-8 바이트를 모두 확인한다. 위 제한은 DB 디스크 사용량 자체가 아니다. 제한을 넘는 신규 접수는 OUTBOX_FULL/HISTORY_LIMIT로 보류하며 기존 기록을 자동 삭제하지 않는다. P0의 단일 접수 worker와 DB 트랜잭션 잠금으로 상한 판단과 삽입을 직렬화한다.

## 실제 DB로 확인한 결과

```sh
python3 scripts/verify-databases.py --suite ingestion
python3 scripts/verify-ingestion-source.py
```

첫 명령의 최종 Java 7개 중 실제 DB/TCP 시나리오는 3개다. 다음 경계를 확인했다.

- 정상 커밋 뒤 다른 DB 조회에서 raw_event/outbox가 함께 존재하고 전달 커서는 1 유지.
- raw_event 삽입 후 outbox의 실제 PostgreSQL 제약 위반을 발생시키면 세 표 모두 0건으로 rollback. 실패 ACK에는 committedAt이 없음.
- ACK를 읽지 않고 연결을 종료한 뒤 동일 원본을 재전송하면 DUPLICATE_RECEIVED, 원본/outbox 추가 없음.
- 신규 건수/바이트/보관/미래 시각 상한은 거절하고, 같은 원본 확인은 상한에서도 성공.

두 번째 명령은 이미 실행 중인 Compose 환경에서 Python → Spring TCP → PostgreSQL을 연결한다. 새 run 차체 1대의 HOLD 도착 흐름에서 원본 39건과 성공 ACK 39개를 확인했다. DB 원본 바이트와 해시가 송신 원본과 정확히 같고, 재접속 후 첫 원본 중복 확인에서도 outbox는 39건이었다. 전부 PENDING, 커서는 1이었다. 검증 후 이 UUID run의 행만 정리했고 기존 DB/볼륨은 보존했다.

연결 증거: `.build-cache/ingestion-source-verification/119a5f939b74489285b3a94a087d8a5d/result.json`. 이는 실시간 성능 시험이나 화면 연결 완료 증거가 아니다.

## 남은 전달 책임
