# 작업 57. 후면 AMR 실제 운송과 부품 선보급 연동

2026-10-11

사용자가 남아 있던 AMR 연동을 지적했다. 작업 54의 승인된 후면 배치와 작업 55의 선보급 설계를 실제 시뮬레이터·수집 서버·관제·3D 화면에 연결한다.

## 동작

- 정책 4 정상 1대/3대 및 수동 복구 연결 실행은 후면 부품 공급을 활성화한다. 과거 실행과 기존 P0 자동 검증 데모는 당시 배치를 보존한다.
- 부품 공급 구역의 AMR 접안점 `(0,-140)`, ASM별 공급 접안점 `(150,-140)/(350,-140)`, 공급대 중심 y=-80, 후면 통로 y=-220, AMR 대기점 `(-90,-240)`을 사용한다. AGV의 앞쪽 배치와 최종 외곽 복귀를 유지한다.
- 공정별 초기 재고 2키트를 시작 조건으로 명시한다. 차체 도착 이후 첫 부품을 기다리게 하지 않는다. `maxBodies=1`인 설정에서는 초기 재고를 1로 제한한다.
- ASM 작업을 시작할 때 공급대의 실제 키트 1개를 소비한다. 수동 장애 중에는 추가로 소비하지 않고, 복구 시 이미 시작한 작업을 이어간다.
- 실제 재고 + 배정/운송 중 키트가 목표 수량보다 적을 때 AMR에 한 키트씩 배차한다. 남은 등록 차체의 수요를 초과해 채우지 않으며, 재고가 적고 다음 차체가 임박한 공정을 우선한다.
- 부품이 없으면 직접 ASM 배차를 승인하지 않는다. 실제 AMR 하차가 완료돼야 재고가 늘고 조립이 가능해진다. 공급 부족을 무시하거나 화면에서만 재고를 만들어내지 않는다.
- 후면 AMR 통로와 앞쪽 AGV 통로의 사용을 차종별로 제한한다. 기존 회전·가감속·적재 전진·충돌 여유 검사를 그대로 적용한다. AMR은 보급할 일이 없으면 후면 대기점으로 복귀한다.

## 관측과 UI

- RUN_STARTED.config의 선택 필드 `partsSupply`와 FACTORY_SNAPSHOT의 공정별 `partsSupply` 배열을 추가했다. 수집/운영 양쪽의 엄격한 입력 검증기를 함께 갱신했다. 과거 메시지는 그대로 허용한다.
- 관제 서버는 재고·보급 중·누적 도착·사용량·부품 부족 대기 시간을 원본 스냅샷에서 전달한다. 현재 재고와 운송 수량을 관제에서 재계산해 꾸미지 않는다.
- 공급대의 3D 키트 개수, 작은 재고 라벨, AMR 적재물·목적지·후면 이동 경로를 실제 값으로 표시한다. 우측에 두 ASM의 재고와 부품 대기 시간을 짧게 표시한다.
- `available + consumed = initialStock + delivered`, `available + inbound <= capacity`를 검증한다. 공정별 소비량은 실제 작업을 시작한 차체 수와 일치해야 한다.
- 모델은 조립용 키트 단위다. 개별 BOM 품목 및 부품 공급 구역의 외부 입고·유한 총재고는 이번 범위에 포함하지 않는다.

## 검증

- Python 전체 57개 테스트 통과. 새 테스트는 정상 3대/10대의 부품 대기 0초, 실제 재고 소진 시 배송 전 작업 금지, 수동 장애 시 중복 소비·과잉 재고 방지, 공급대 만재 시 배정 금지를 확인한다.
- 오프라인 정상 3대는 공정별 초기 2 + AMR 보급 1 = 사용 3, 10대는 초기 2 + 보급 8 = 사용 10. 모두 부품 대기 0ms, 잔여 재고 0, 전 차량 초기 위치 복귀다.
- Java 계약/모델 검사에 실제 생산 이벤트 fixture `parts-supply-scenario.ndjson` 140개를 추가했다. 공급 수량과 실제 활성 운송/차체 작업의 일치 및 잘못된 재고 거부를 검증한다.
- Java 전체 실행 결과: 수집 13개 중 6개 통과·7개 환경 조건 스킵, 관제 14개 중 8개 통과·6개 환경 조건 스킵. 실패/오류 0. 초기 샌드박스의 로컬 포트 제한으로 실패한 웹 기동 테스트는 필요한 권한으로 재실행해 통과했다.
- 콘솔 기존 18개 테스트 통과, 빌드 성공(기존 대형 청크 경고만 존재).
- 로컬 수집·운영·웹 컨테이너를 데이터/볼륨 삭제 없이 갱신했다. 실제 연결 정상 생산과 수동 복구 생산을 별도 run으로 실행해 검증했다.

정상 실행: `run-20261010-224a53bb565e42e9a4cec7996f54b5fb`.

수동 복구 실행: `run-20261010-95f05fc36e894e8cbd5a2259b1da561c`.

Chrome에서 AMR 적재 운송, 실제 재고 감소/증가, 수동 정지 중 재고 2키트까지 보충 후 대기점 복귀, 사용량 유지(1키트)를 확인했다. 수동 점검과 조치 완료 버튼을 직접 눌렀다. 장애는 시뮬레이션 22.7초에 발생, 43.4초 점검 시작, 81.5초 조치 완료, 83.5초 복구 완료됐다. 정지 시간 60.8초 동안 작업 진행량을 보존했다.

재현: `http://127.0.0.1:5174/`에서 새 정상 생산 또는 수동 복구 시뮬레이션을 시작한다. 과거 실행은 AMR 배치·재고 연동을 소급 적용하지 않는다. 정적 관제 `http://127.0.0.1:5173/`도 새 실행의 부품 관측을 표시한다.

## 실제 연결 검증 결과

- 정상 실행: 698개 이벤트, 598개 스냅샷, AMR 적재 관측 63회, ASM별 1회씩 실제 보급. 공정별 초기 2 + 도착 1 = 소비 3, 부품 대기 0ms. 3대 모두 GOOD/PASS, 모든 차량 원위치 IDLE, 서버 최종 관측과 원본 재고 일치, 미전달 이벤트 0개.
- 정상 3D 검증: 보간된 차량 전체 프레임 4,186개, 적재 구간 관측 1,194회에서 전진 및 장애물/차량 간 여유 통과. AGV 두 대 최종 외곽 복귀 확인.
- 공급대 라벨을 위로 옮겨 실제 공급대와 ASM 모델을 가리지 않게 조정한 뒤 웹 컨테이너에도 최종 반영했다.
