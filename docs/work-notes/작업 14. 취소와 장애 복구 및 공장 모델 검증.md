## 이번 작업은 무엇인가

앞 작업까지는 차체가 조립 셀과 Bay, AGV 사이를 이동하는 정상 흐름을 만들었다. 이번에는 **운송을 취소하거나 셀이 고장 나도 등록·자리·작업 기록이 틀어지지 않는 규칙**을 추가했다. 부품 AMR도 차체 운송과 구별해서 움직이게 했다.

마지막으로 Python이 만든 결과를 다른 서비스에 전달할 수 있도록 **계약에 맞는 사건과 전체 상태 보고서**를 만들었다. 아직 네트워크로 보내지는 않는다. 지금 완성한 것은 Python 공장 모델이며, TCP 수집·DB 저장·웹 조회·GUI 연결은 뒤 단계다. 기술 스택과 흰색·네이비 UI 기준을 유지한다.

## 출발 전 취소는 무엇을 돌려주는가

`cancel_transport(transport_id)`는 BODY/ASSIGNED 운송이고 차체가 출발지에 있을 때만 허용한다. 빈 AGV의 TO_PICKUP 이동과 적재 완료 전 LOADING까지다. 차체가 AGV로 넘어간 IN_TRANSIT부터는 거절한다. v1에서는 부품 운송 취소를 지원하지 않는다.

취소를 승인하면 한 전환에서 다음을 처리한다.

- 운송을 CANCELLED로 기록하고 취소 시각/SCENARIO_CANCEL을 남긴다.
- 목적지의 예약을 반환한다.
- AGV 배정과 진행 구간을 해제하고 IDLE로 돌린다. 현재 좌표를 유지한다.
- 차체는 기존 INPUT/CELL에 남기고 활성 운송/예약 참조를 비운다.

같은 취소를 다시 요청하면 기존 결과를 반환한다. 번호를 새로 만들거나 슬롯을 두 번 반환하지 않는다. 이후 다른 운송으로 재배정한 차체에 예전 취소 번호가 다시 들어와도 새 배정을 지우지 않는다.

**취소한 차체만 자동 재배차를 보류**한다. 그렇지 않으면 다음 tick에서 방금 취소한 운송을 즉시 다시 만들 수 있기 때문이다. 명시적으로 assign_transport(body_id)를 재시도해 승인받으면 새 운송/예약 번호를 발급하고 보류를 해제한다. 다른 차체의 자동 배차는 계속 진행할 수 있다.

## 도착 요청을 여러 번 받으면 어떻게 되는가

`complete_transport(transport_id)`는 지정 장소에서 UNLOADING 시간이 끝나고 실제 화물/예약 참조가 맞을 때만 인계를 수행한다. 출발 전이나 인계 전 호출은 거절한다.

이미 COMPLETED인 번호는 기존 결과를 반환한다. 차체가 나중에 Bay에서 셀로 들어갔더라도 예전 도착 요청 때문에 그 차체를 Bay로 되돌리거나 슬롯을 다시 점유하지 않는다. 같은 검사/작업 기록도 추가하지 않는다.

시간 경과·통신 단절을 예약 반환 조건으로 쓰지 않는다. 취소가 가능한 출발 전 전환, 도착 인계, 실제 셀 진입의 의미를 구분한다.

## 부품 AMR은 차체 AGV와 무엇이 다른가

`assign_parts('ASM-01')` 또는 ASM-02로 부품 운송을 승인한다. IDLE AMR 하나와 합성 부품 키트를 사용한다.

| 항목 | 차체 운송 | 부품 운송 |
|---|---|---|
| 차량 | AGV | AMR |
| 화물 번호 | bodyId | kit-00001 등의 partsKitId |
| 태그 | 차체와 1:1 tagId | 차체 태그를 만들지 않음 |
| 출발지 | INPUT 또는 CELL | STORE / PARTS-STORE |
| 목적지 | Bay 또는 GOOD/HOLD | PARTS_DOCK / PARTS-ASM-01 또는 02 |
| Bay 예약 | Bay 목적일 때만 사용 | 사용하지 않음 |

기존 차량 시간/좌표 흐름으로 픽업·운반·인계·귀환한다. AMR이 실제로 실은 키트는 차량의 partsKitId에 표시하고 bodyId는 null이다. 완료 후 키트의 위치는 PARTS_DOCK이고 차량은 비워져 귀환한다.

차체 등록부와 키트 등록부를 분리했다. 부품 운송 중에도 Bay의 W/R/A와 차체/태그 수가 바뀌지 않는다. 키트 등록 상한은 maxBodies×2로 제한한다. 실제 부품 재고량, 조립에 필요한 키트 소비 조건, 부품 부족으로 인한 작업 정지는 이번 모델에 연결하지 않았다.

## 셀 고장과 복구는 어떻게 재현하는가

`fail_cell(cell_id)`는 셀을 DOWN으로 만들고 기존 상태를 resumeState에 보관한다. 차체 위치·작업 번호·진행 시간·완료 차체 보유를 그대로 유지한다.

| 고장 전 상태 | DOWN 동안 | 복구 후 |
|---|---|---|
| IDLE | 셀 진입 금지 | 빈 작업 자리로 복구 |
| RUNNING | 작업 시간 감소하지 않음 | 같은 operationId의 남은 부분 진행 |
| BLOCKED | 완료 차체와 예약 보존 | 배출 조건을 다시 확인 |

출발 셀이 DOWN이면 차량이 픽업 위치까지 와도 적재 완료를 보류한다. 차체를 고장 셀에서 강제로 빼내지 않는다. 목적지 셀이 DOWN이어도 이미 예약한 Bay에는 도착할 수 있다. Bay에서 셀로 들어가는 동작은 복구 전까지 거절한다.

`recover_cell`은 저장한 상태로 되돌리고 필요한 배차를 재평가한다. 같은 고장/복구 명령을 반복해도 같은 상태의 변경 사건을 다시 만들지 않는다. 복구할 때 작업 번호를 새로 만들거나 앞서 진행한 시간을 잃지 않는다.

추가로 다음 시나리오를 명시적으로 호출할 수 있다.

- `delay_transport(id, milliseconds)`: ASSIGNED 운송의 적재 운반 시간에 누적 지연 추가. 예약을 반환하거나 취소하지 않는다.
- `set_quality_pattern(('FAIL', 'PASS'))`: 이후 검사부터 고정 배열을 순환 적용. 검사 전 PASS를 미리 기록하지 않는다.

고장·복구·취소·지연·품질 변경은 SCENARIO_CHANGED 사건에 대상과 입력을 기록한다. 모델 시간으로 재현하므로 기다리는 컴퓨터의 속도로 검사 결과나 고장 조건을 정하지 않는다. runId·eventId·실제 UTC 시각은 실행마다 다르다.

## 사건과 전체 스냅샷은 어떤 역할인가

**사건은 “무슨 일이 일어났는가”, 스냅샷은 “그 결과 지금 전체가 어떤 상태인가”**를 나타낸다.

예를 들어 슬롯 반환 사건에는 차체와 슬롯·기존 운송 번호가 있다. 반환 직후 다른 차체가 그 슬롯을 예약했다면 최신 스냅샷에는 새 예약이 표시된다. 서버에서 사건 두 개를 각각 현재 카운터에 더하는 방식으로 처리하지 않는다.

`events`는 변경 불가능한 Event 객체들의 튜플이다. Event.to_dict는 사본을 반환하며 ndjson에는 다음 필드와 LF가 포함된다.

| 필드 | 역할 |
|---|---|
| schemaVersion | 현재 규격 1 |
| eventId | 새 사건의 UUID v4 |
| runId / sourceId | 어느 실행/생산자의 기록인지 |
| sourceSeq | 이 실행에서 새 사건을 만든 순서 |
| eventType | 작업 완료·검사·예약·운송·상태 변경 등 종류 |
| occurredAt | 원래 전환의 UTC 기록 시각 |
| payload | 해당 사건의 계약 필드 |

첫 사건은 RUN_STARTED다. 작업·검사·슬롯·셀 진입·운송·셀 상태·실행 상태·시나리오를 기록한다. 별도의 TELEMETRY_UPDATED는 현재 발행하지 않고 차량 위치는 전체 스냅샷에서 보고한다. 같은 취소/도착/상태를 반복해도 새 사건을 생성하지 않는다. 상태 변경이 실패하면 사건과 번호도 함께 되돌린다.

UTF-8/LF 포함 65,536바이트 상한을 사건 생성 시 검사한다. 원본 Event.ndjson을 다시 사용하면 봉투가 그대로 유지된다. 이것을 실제 재전송/ACK 기능을 구현한 것으로 기록하지 않는다. 저널은 메모리에 있으며 프로세스 재시작 복원·디스크 영속화는 없다.

## 전체 보고는 어떻게 얻는가

`inspect()`는 작업 이력과 시험용 표시가 있는 로컬 진단이다. 네트워크용으로 그대로 보내지 않는다.

`snapshot()`은 v1의 전체 payload를 반환한다. 모든 셀·Bay/슬롯·등록 차체·차량·활성 운송과 같은 capturedAt을 담는다. 차체의 lastObservedAt도 이 시각과 같다. 진단용 createdAt/fixturePendingStart/이력 배열을 섞지 않는다.

`publish_snapshot()`은 그 payload를 FACTORY_SNAPSHOT 사건으로 기록한다. 관련 전환 사건 뒤에 현재 상태 보고를 만든다. 정지 상태에서는 simElapsedMs가 멈춰 있어도 현재 UTC로 상태를 보고할 수 있다.

초기 시험 배치의 IDLE 셀에 아직 작업을 시작하지 않은 차체가 있으면 완전한 v1 보고를 거절한다. 작업/소유 상태를 먼저 맞춰야 한다. 일반 등록/운송 모델에는 이 중간 배치 상태가 없다.

이번에는 명시적으로 보고를 요청하는 API를 완성했다. 기본 서비스의 500ms 자동 발행·실시간 구동·TCP 송신은 다음 단계와 연결해야 한다.

## 실행 종료는 어떻게 기록하는가

`finish_run()`은 모든 차체가 RESULT에 있고 셀/차량이 IDLE이며 활성 운송/차량 구간이 없을 때만 받는다. 아직 Bay에 차체가 있거나 빈 차량이 귀환 중이면 거절한다.

완료되면 RUN_STATE_CHANGED(FINISHED) → 최종 FACTORY_SNAPSHOT → RUN_FINISHED 순서로 기록한다. RUN_FINISHED의 uniqueEventCount는 자신을 포함한 마지막 sourceSeq와 같다. 이후 새 변경/보고 사건을 만들지 않는다. 최종 상태 조회와 같은 finish 요청의 반복은 가능하다.

이는 모델 실행의 종료다. DB에 저장됐다거나 GUI가 이 보고를 받았다는 뜻은 아니다.

## 꼭 필요한 검증과 실제 결과

**새 테스트는 4개만 추가했다.** 공통 모델의 기존 검증을 포함해 Python 테스트 총 **17개 통과**했다.

| 새 테스트 | 필요한 확인 |
|---|---|
| 취소/반복 처리 | ASSIGNED·TO_PICKUP·LOADING 취소, 출발 후 거절, 반복 취소가 새 배정 보존, 반복/이른 도착 방어, 사건 추가 없음 |
| 부품 AMR | BODY/태그 없음, kit 화물, 차체 Bay 예약 없음, 차량 부족 시 키트/번호 미소비, 인계/귀환과 계약 출력 |
| 고장/시나리오 | DOWN의 작업 번호/시간 보존, 예약 픽업 보류와 복구, 고장 목적지 Bay 도착/셀 진입 거절, 누적 지연·품질 배열, 반복 상태 사건 없음 |
| 단계 전체 | C=2/3/4 각각 100대 흐름, 단일 위치·태그·슬롯 보존, 작업/검사/운송 사실과 전체 스냅샷 일치, 순번/UUID/필드/참조·프레임 상한·종료 기록 |

100대 검증은 **작업 시간과 적재 경로 시간을 각각 200ms로 단축한 설정**이다. 모델의 보존/보고 규칙을 빠르게 확인하기 위한 시험이고 실시간 100대 성능 실적이 아니다. 각 용량에서 다음을 확인했다.

| 항목 | 각 실행 결과 |
|---|---|
| 차체 / 고유 태그 | 100 / 100 |
| 완료 작업 / 검사 | 300 / 100 |
| 완료 운송 / 셀 진입 | 400 / 300 |
| 고정 PASS / FAIL | 50 / 50 |
| 최종 셀 / 차량 | 모두 IDLE |
| 최종 Bay | W=0/R=0/A=C |
| 사건 | 연속 sourceSeq, 고유 UUID, 검사 100건만 생성 |

생성한 실제 사건/스냅샷을 기존 v1 예제 확인기의 해당 함수에 넣어 필드·참조·단일 위치·예약 대응을 검사했다. 기존 계약 예제 전체 검사를 반복한 것이 아니다. 최종 보고와 실제 모델 상태, 작업/검사/운송 fact의 고유 개수를 함께 확인했다.

AMR 귀환의 시간 올림에서 부동소수점 오차로 한 tick 늘어나는 경계를 발견해, 올림 직전의 표현 오차를 보정했다. 관련 검증을 포함한 전체 Python 17개가 통과했다. 시뮬레이터 컨테이너만 갱신했고 healthy와 MODEL_INITIALIZED / registeredBodyCount=0 / factoryRunStarted=false를 확인했다.

```sh
scripts/simulator.sh test
scripts/simulator.sh run --demo-scenarios
scripts/dev-stack.sh compose up -d --build --wait factory-simulator
```

DB/Java/GUI 전체 검증과 수백 대 성능/장시간 시험은 수행하지 않았다. 이번 작업에 필요한 모델·보고 경계를 검증했고 새 기능이 없는 경계의 테스트를 반복하지 않았다.

| 파일 | 역할 |
|---|---|
| factory_simulator/events.py | 변경 불가능한 v1 사건과 전환 fact 추출 |

| factory_simulator/__main__.py | --demo-scenarios 진입점 |
