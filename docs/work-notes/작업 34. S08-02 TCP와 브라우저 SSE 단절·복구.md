# 작업 34. S08-02 TCP와 브라우저 SSE 단절·복구

> 작업 ID: S08-02 · 완료일: 2026-10-05 · 상태: 완료 · 검증 결과는 [S08 통합 기록](<../development/S08 장애·복구 통합 검증.md>) 참고

이 프로젝트에는 두 종류의 연결이 있습니다. Python이 사건을 보내는 TCP 연결과, 관제 서버가 브라우저에 관측값을 보내는 SSE 연결입니다. 화면이 끊겼다고 공장이 멈춘 것은 아니며, 화면 연결이 살아 있어도 공장 보고가 멈출 수 있습니다.

## TCP와 ACK는 무엇인가

TCP는 사건 원본을 보내는 통신 경로이고, ACK는 수집 서비스가 자기 DB에 저장했다는 확인 응답입니다. 관제 업무까지 완료했다는 뜻은 아닙니다.

실제 수집 DB에 저장한 사건의 ACK를 일부러 버리고, Python이 보관 중인 같은 바이트를 다시 보냅니다. 수집 서비스는 `DUPLICATE_RECEIVED`로 응답하고 원본·outbox를 더 만들지 않습니다. 연결 실패 중에도 대기 목록의 맨 앞 사건은 바뀌지 않습니다.

새 공장 보고 없이 12초가 지나면 서버는 STALE을 거쳐 DISCONNECTED로 표시합니다. 이미 알던 위치와 예약은 남습니다. 새 전체 보고가 도착해야 LIVE가 됩니다. 시간 경과만으로 예약을 풀지 않습니다.

## SSE는 무엇인가

SSE는 브라우저가 열어 둔 연결로 서버가 최신 전체 관측 묶음을 계속 보내는 방식입니다. 화면은 사건별로 슬롯을 더하고 빼지 않고, 같은 시점의 차체·차량·셀·슬롯을 함께 교체합니다.

검증 전용 프록시가 SSE만 끊고 REST 조회와 Python TCP 보고는 계속 통과시킵니다. 실제 Chrome에서 다음을 확인합니다.

1. 실시간 관측 상태에서 태그를 검색하고 상세 창을 엽니다.
2. SSE만 끊으면 화면 연결 경고가 나오고 마지막 차체 위치·운송·예약이 남습니다.
3. 이때 서버의 sourceSeq는 증가하며 공장 보고는 LIVE입니다.
4. SSE를 복구하면 최신 묶음을 받고 LIVE로 돌아오며 검색과 선택이 유지됩니다.

프록시는 검증 도구 안의 임시 장치입니다. 운영 서비스에 장애 버튼이나 별도 API를 추가하지 않았습니다.

## 테스트 범위

실제 브라우저의 정상·단절·복구 DOM과 캡처를 남깁니다. 스냅샷 순서와 오래된 REST 응답 배제는 변경 없는 S06/S07 검증을 재사용합니다. 이번 작업으로 Python 프로세스 자체가 종료된 뒤의 미확인 목록 복원까지 보장하지는 않습니다. 해당 목록은 현재 메모리 기반이며 재시작은 새 run입니다.

다음 작업은 서비스와 DB의 장애 책임을 확인하는 S08-03입니다.

## 실제 완료 결과

최종 TCP/12초 소스 단절 검증은 05f6bac4…에서 통과했다. 실제 Chrome SSE 검증은 879a42e6…의 다른 run에서 1회 단절·31회 접속 요청·선택/위치/예약 보존과 LIVE 복구가 통과했다. 전체 실행과 브라우저 실행 번호를 섞지 않는다. 상세 실행 번호·원본·DB·로그와 캡처 위치는 S08 통합 기록에 있다.
