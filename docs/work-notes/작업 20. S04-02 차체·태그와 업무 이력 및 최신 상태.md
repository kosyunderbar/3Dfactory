# 작업 20. S04-02 차체·태그와 업무 이력 및 최신 상태

> 작업 ID: S04-02 · 완료일: 2026-10-05 · 상태: 완료  
> 공장 상태 결정은 Python · 관제는 검증·보관·조회

차체/가상 태그 등록부, 셀 작업·운송·검사 이력, 최신 전체 공장 상태를 관제 DB에 반영하도록 구현했다. 같은 사건을 받아도 현재 위치와 과거 실적은 서로 다른 규칙으로 다룬다.

## 이름표와 현재 위치의 차이

BODY_REGISTERED가 오면 bodyId와 tagId를 같은 run 안에서 1:1로 연결한다. 이 등록부는 “태그 1번은 차체 1번의 이름표”라는 정보다. 공장 상태 보고를 아직 받지 않았다면 그 차체의 현재 위치를 추정하지 않는다. 등록됐지만 관측 안 된 차체는 조회에서 data=null로 표시한다.

FACTORY_SNAPSHOT은 차체·셀·Bay 슬롯·차량·활성 운송을 같은 시점에 촬영한 전체 보고다. 한 차체를 셀에도 있고 AGV에도 있는 것으로 동시에 표시하면 안 되므로, 각 배열을 조합해 소유 관계를 검증한 뒤 전체를 교체한다.

## 실제로 저장하는 내용

| 관제 표 | 저장 의미 |
|---|---|
| simulation_run / equipment / factory_buffer / vehicle | RUN_STARTED의 실행·설비·Bay 슬롯·차량·경로 구성 |
| body | 차체·태그·차종·사양·등록 시각·초기 위치 |
| operation_history | 작업 ID별 차체·설비, 진입 시각과 완료/소요 시간 |
| transport_history | 운송 ID별 차체/부품·차량·경로·예약과 배정→출발→완료/취소 |
| inspection_result | 검사 ID·차체·QC 결과·검사 시각. 차체당 최종 검사 한 번 |
| factory_snapshot | 가장 큰 sourceSeq의 검증된 전체 물리 상태 |
| event_projection | 유효 사건의 조회용 원래 payload와 검색 인덱스 |

실제 쓰기는 [EventApplication.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/EventApplication.java), 관계 검증은 [ModelRules.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/ModelRules.java)가 맡는다. S01의 기존 Flyway V1 13개 표를 그대로 사용하며 이미 적용한 마이그레이션을 수정하지 않았다.

BODY_ENTERED_CELL은 작업 ID의 소개다. 이후 OPERATION_COMPLETED가 그 작업을 완성한다. 초기 fixture에서 이미 셀 안에 있던 차체는 최초 스냅샷으로 작업 ID를 소개할 수 있지만, 모르는 진입 시각을 임의로 만들지 않는다. 운송도 TRANSPORT_ASSIGNED 소개가 먼저 필요하다. 운송 ID에 연결된 차체·차량·경로·예약은 바뀌지 않으며 이미 끝난 운송을 새 보고로 출발 상태로 되돌리지 않는다.

## 오래된 상태와 늦은 사실을 다르게 처리한다

현재 스냅샷이 순번 59인데 처음 스냅샷인 순번 7이 뒤늦게 도착하면, 순번 7은 STALE_SNAPSHOT_RECORDED로 이력에만 남긴다. 차체의 현재 HOLD 위치를 과거의 입력 위치로 바꾸지 않는다. 더 큰 순번의 보고도 완료 공정이나 확정 검사 결과가 퇴행하는 모순을 허용하지 않는다.

반면 검사 결과는 이미 끝난 사실이다. 더 큰 순번의 다른 보고를 처리한 뒤 처음 도착한 검사도 차체/구성 참조가 유효하면 inspection_result에 보관한다. 검사 시각이 2분 전이면 최근 5분 집계의 해당 발생 구간에 반영한다. 같은 검사 ID의 같은 사실은 FACT_ALREADY_RECORDED이며 새 사건 번호를 사용해도 분모를 또 늘리지 않는다. 같은 업무 ID에 내용이 달라지면 BUSINESS_ID_CONFLICT다.

## 버퍼 공식을 관제에서도 지킨다

Bay의 각 슬롯이 FREE/OCCUPIED/RESERVED 중 하나인지 확인하고, 실제 슬롯에서 센 W와 R이 보고된 waitingCount/reservedInboundCount와 같은지 검증한다. A=C-W-R이며 W+R>C나 서로 맞지 않는 예약·운송·차체 소유는 잘못된 보고다. 차체 소유 위치는 정확히 한 곳이어야 한다.

SLOT_RESERVED/SLOT_RELEASED 사건을 받을 때 Java가 별도의 W/R 카운터를 증감하지 않는다. 현재 화면 수치는 항상 하나의 검증된 전체 스냅샷에서 읽는다. 따라서 늦은 사건 때문에 현재 슬롯을 두 번 반환하는 일이 없다. 배출 승인·차체 이동·예약 해제는 계속 Python의 권한이다. 부품 AMR은 차체/태그와 Bay 예약을 소비하지 않는다.

## 최소 검증과 남은 범위

S04 공통 7개 검증에서 정상 전체 시나리오, 같은 검사/작업/운송 사실의 새 사건 재보고, 태그 충돌, 잘못된 슬롯 소유, 오래된 스냅샷의 최신 값 보존, 늦은 고유 검사와 run 분리를 확인했다. 실제 Compose의 모델 사건 60건은 작업 3건·운송 6건·고유 검사 1건으로 저장됐고 차체 최종 위치는 HOLD였다.

```sh
python3 scripts/verify-databases.py --suite operations
python3 scripts/verify-operations.py
```

공통 검증을 네 작업별로 반복하지 않았다. [검증 안내](<../validation/최소 검증 시나리오와 도구.md>)와 [관제 실행 안내](../../services/operations-service/README.md)를 따른다. 저장한 상태의 REST 조회는 S04-03에서 연결했고, 실제 Vue 창에 연결하는 일은 S06/S07에 남아 있다.
