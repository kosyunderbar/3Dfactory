# 작업 11. 셀 작업과 최종 검사

> 계획 ID: S02-02 · 작업일: 2026-10-05 · 상태: 완료  
> 선행: S02-01 공장 설정·차체/태그·단일 위치  
> 다음: S02-03 슬롯 예약·배출 차단

## 이번 작업은 무엇인가

앞 작업에서는 공장의 배치도를 만들고 차체에 가상 이름표를 붙였다. 이번에는 **셀에서 차체를 작업하고, 끝났다는 기록을 남기고, 마지막 셀에서 검사 결과를 만드는 규칙**을 Python에 추가했다.

공장에 비유하면 ASM-01의 조립 담당자, ASM-02의 다음 조립 담당자, QC-01의 검사 담당자를 만든 단계다. 작업을 끝내는 것과 차체를 내보내는 것은 별도의 동작이다. **조립이 끝나도 차체는 작업 셀에 남는다.** 다음 작업에서 목적지의 빈자리와 AGV를 함께 확보해야 배출을 허용할 수 있다.

이는 Python 안의 공장 모델이다. Java 수집 서비스는 앞으로 이 모델의 보고서를 받고, Java 관제 서비스는 기록을 저장해 조회에 쓰고, Vue는 그 정보를 화면에 표시한다. 이번에는 작업 결과를 DB나 화면으로 보내지 않는다. 기술 스택과 흰색·네이비 UI 기준은 유지한다.

## 차체와 셀의 상태는 무엇이 다른가

차체 상태는 “이 차체가 지금 무엇을 기다리는가”, 셀 상태는 “이 작업 자리가 어떤 상태인가”를 나타낸다.

| 장면 | 차체 상태 | 셀 상태 | 검사 결과 |
|---|---|---|---|
| 작업 시작 | PROCESSING | RUNNING | NOT_INSPECTED |
| ASM-01/02 조립 완료 | WAITING_UNLOAD | BLOCKED | NOT_INSPECTED |
| QC-01 검사 완료 | COMPLETED | BLOCKED | PASS 또는 FAIL |

조립이나 검사가 완료돼도 **차체의 현재 위치는 해당 CELL**이다. BLOCKED는 그 차체가 자리를 차지하고 있어 새 차체를 받을 수 없다는 뜻이다. 남은 작업 시간은 0이고 완료 operationId는 보유한다.

이번 로컬 모델의 blockedReason은 WAITING_PICKUP이다. 아직 배차가 승인된 것은 아니며, 작업을 마치고 픽업을 기다리는 표시다. BUFFER_FULL/NO_VEHICLE의 실제 판단과 예약 승인 조건은 S02-03에서 추가한다. W+R≥C에 의한 Unload 차단을 벌써 구현한 것으로 기록하지 않는다.

COMPLETED는 **최종 검사가 끝났다는 뜻**이다. GOOD/HOLD 구역에 도착했다는 뜻이 아니다. 검사 완료 차체가 나중에 AGV에 실려도 COMPLETED와 검사 결과는 유지한다. 검사 전 차체의 운송 상태는 IN_TRANSIT, 대기 상태는 WAITING이며 실제 운송 절차는 S02-04에서 구현한다.

## 작업 순서는 어떻게 지키는가

차체의 completedCellIds에 완료 공정을 순서대로 쌓는다. nextCellId는 이 이력으로 계산한다.

| 완료 공정 이력 | 다음 공정 |
|---|---|
| 없음 | ASM-01 |
| ASM-01 | ASM-02 |
| ASM-01, ASM-02 | QC-01 |
| ASM-01, ASM-02, QC-01 | 없음(null) |

`start_work(cell_id)`는 다음 조건을 확인한다.

- 모델이 일시정지 상태가 아니고 셀이 IDLE이어야 한다.
- 그 셀 안에 차체가 정확히 한 대 있어야 한다.
- 차체는 WAITING이고, 그 셀이 정확한 다음 공정이어야 한다.
- 아직 최종 검사를 받지 않은 차체여야 한다.

조건이 맞으면 차체를 PROCESSING, 셀을 RUNNING으로 함께 변경하고 operationId를 발급한다. 잘못된 순서나 중복 시작을 거절하면 상태와 번호를 바꾸지 않는다. 진행 중인 차체를 내부 위치 변경 함수로 빼내는 것도 거절한다.

완료 후에는 셀이 BLOCKED이므로 같은 작업을 다시 시작하거나 완료 기록을 반복 생성하지 않는다. 다른 작업자가 같은 완료 이력을 덧붙이는 별도 목록도 두지 않는다. 변경 명령은 기존처럼 모델을 만든 단일 스레드에서만 처리한다.

## 시간은 어떻게 흐르는가

기본 tick은 100ms다. `tick()`은 한 tick, `advance(delta_ms)`는 tick의 양의 정수 배수만큼 모델을 진행한다. 셀의 기본 작업 시간은 ASM-01 4초, ASM-02 6초, QC-01 3초다. 여러 RUNNING 셀은 같은 tick에서 각자 작업 시간을 진행한다.

작업 완료 기록의 durationMs는 실제로 진행한 **모델 작업 시간**이다. UTC의 startedAt/completedAt은 기록 시각이다. 두 값을 구분한다. `pause()` 상태에서는 tick을 호출해도 simElapsedMs나 남은 작업 시간이 줄지 않는다. `resume()` 후 남은 부분만 진행한다. 조립 완료 후 픽업 대기 시간도 조립 시간에 더하지 않는다.

이번에는 시간을 직접 진행하는 모델 함수까지 구현했다. 일반 실행의 heartbeat 루프를 자동 생산 루프로 바꾸지는 않았다. 오프라인 확인 명령은 13초의 모델 작업을 빠르게 계산하므로 컴퓨터 앞에서 실제로 13초 기다리는 데모가 아니다. speed 설정의 실시간 구동이나 설비 DOWN 복구는 후속 범위다.

## 검사 결과와 스마트태그는 어떻게 연결되는가

검사 전에는 inspectionResult=NOT_INSPECTED, inspectedAt=null이다. 조립을 완료했다고 PASS로 바꾸지 않는다.

QC-01의 작업이 끝나는 순간 inspectionId를 하나 만들고 해당 차체의 검사 결과와 시각을 갱신한다. PASS는 defectCode=null, FAIL은 SIM_DEFECT_01이다. 한 차체의 최종 검사 기록은 한 번만 생성한다.

기본 결과 생성은 실행 설정의 seed/failProbability를 사용한다. 같은 seed와 같은 검사 완료 순서라면 같은 PASS/FAIL 순서를 얻는다. 이는 가상의 품질 결과이며 실제 센서 판독은 아니다. 시험할 때는 모델 생성에 `quality_results=('PASS', 'FAIL')` 같은 고정 순환 배열을 넣을 수 있다. 오프라인 데모는 고정 PASS 한 건을 사용한다.

기존 tagId→차체 등록 관계를 통해 이제 위치 외에 상태·완료 공정·검사 결과를 조회할 수 있다. 태그에서 정보를 직접 읽어오는 장치나 GUI 창 연결은 아직 구현하지 않았다.

## 서버 없이 직접 확인하기

프로젝트 루트에서 실행한다. 기존 Python 3.12 가상환경을 사용한다.

```sh
scripts/simulator.sh run --demo-work
```

새 run에 차체 한 대를 시험 배치하고 세 공정의 시작/완료를 계산한다. 공정 간 차체 위치 변경은 시험용 배치이며 **실제 AGV 운송이나 슬롯 예약이 아니다.** 초기 위치를 우회하는 모드는 이 명령에서만 명시적으로 켠다. 일반 기동과 --inspect-model은 기존대로 BODY-IN 등록만 사용한다.

결과를 읽을 때는 다음 항목을 보면 된다.

| 항목 | 이번 기본 실행의 결과 |
|---|---|
| demoFixture / transportImplemented | true / false |
| handoffs | TEST_FIXTURE_ONLY |
| simElapsedMs | 13000 |
| operations | ASM-01 4000ms, ASM-02 6000ms, QC-01 3000ms |
| inspections | inspection-00001, PASS 한 건 |
| 차체 | body-00001/tag-00001, COMPLETED, CELL/QC-01 |
| 다음 공정 | null |
| QC 셀 | BLOCKED, 남은 작업 0ms, WAITING_PICKUP |

출력은 로컬 확인 JSON이며 v1 사건 봉투나 완전한 FACTORY_SNAPSHOT이 아니다. sourceSeq/eventId를 발급하거나 TCP/SSE로 보내지 않는다. 시험용 초기 배치는 해당 셀 앞의 정확한 공정 이력을 요구한다. 배치 직후 아직 start_work를 하지 않은 IDLE 셀은 fixturePendingStart=true로 표시하며, 이것을 계약의 완전한 운영 스냅샷으로 쓰지 않는다.

실제 기본 확인 결과는 `.build-cache/s02-02-work-preview.json`에 남겼다. 이 파일의 runId와 UTC 시각은 실행마다 달라진다. --demo-work와 --initial-bodies는 함께 사용할 수 없다.

## 꼭 필요한 검증과 실제 결과

**새 테스트는 3개만 추가했다.** 기존 공통 모델/설정 검증을 포함한 Python 테스트 총 7개가 통과했다.

| 새 테스트 | 핵심 확인 |
|---|---|
| 공정·시간·대기 | 세 공정 순서, 완료 직전 경계, 일시정지 중 작업/모델 시간 유지, 4/6/3초 기록, 완료 후 셀 내 보유, 중복 완료 방지, COMPLETED 유지 |
| 검사 결과 | 검사 전 NOT_INSPECTED, 고정 PASS/FAIL 순환, 동일 seed 재현, 확률 0/1 경계, 검사 ID/차체당 기록 고유성, defectCode |
| 잘못된 명령 | 선행 이력·잘못된 공정·빈 셀·중복 시작·정지 중 시작·작업 중 이동·잘못된 tick 입력 거절, 실패 시 상태/번호 유지 |

```sh
scripts/simulator.sh test
scripts/simulator.sh run --demo-work
scripts/dev-stack.sh compose up -d --build --wait factory-simulator
```

시뮬레이터 컨테이너만 변경된 이미지로 갱신했고 healthy가 됐다. 일반 기동은 MODEL_INITIALIZED / registeredBodyCount=0 / factoryRunStarted=false를 유지한다. heartbeat 상태 확인은 자동 생산이나 데이터 전송 성공을 뜻하지 않는다.

DB/Java/GUI/계약 전체 검증은 반복하지 않았다. 이번 변경은 Python 모델과 로컬 확인 명령에 한정되므로 해당 경계의 최소 검증으로 마무리했다. GUI 샘플의 결과를 Python 규칙 검증으로 대신하지 않았다.
