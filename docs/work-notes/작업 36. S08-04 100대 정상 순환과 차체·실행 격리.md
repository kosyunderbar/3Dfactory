# 작업 36. S08-04 100대 정상 순환과 차체·실행 격리

> 작업 ID: S08-04 · 완료일: 2026-10-05 · 상태: 완료 · 검증 결과는 [S08 통합 기록](<../development/S08 장애·복구 통합 검증.md>) 참고

차체 100대를 정상 등록한 뒤 세 셀을 거쳐 GOOD/HOLD로 보내는 작업입니다. 차체가 복제되거나 사라지지 않는지, 반복 전송으로 실적이 늘지 않는지, 다른 실행의 태그가 섞이지 않는지 확인합니다.

## 100대는 무엇을 뜻하는가

차체 100대를 뜻합니다. 차량은 기획의 AGV 2대·AMR 1대를 그대로 유지합니다. 작업과 이동 시간을 줄이고 100ms 논리 tick을 빠르게 진행합니다. 이는 공정 정확성 검증이며 실제 시간의 처리량·지연·수백 대 차량 운영 성능은 S09/P1 범위입니다.

## 왜 차체 위치를 하나만 두는가

차체는 BODY-IN, 셀, Bay, AGV, GOOD/HOLD 중 한 곳에만 있습니다. AGV가 차체를 싣기 전에는 출발지 소유이며, 목적지의 RESERVED 슬롯은 도착 예정표입니다. 예약을 실제 차체처럼 세면 같은 차체를 두 번 셉니다.

매 tick에서 차체 100개의 고유 번호와 실제 셀·OCCUPIED 슬롯·차량 소유를 대조하고 `0 ≤ W+R ≤ C`, `A=C-W-R`를 확인합니다. 중간 전체 스냅샷과 최종 스냅샷은 실제 관제 API와 비교합니다.

## 완료했을 때의 숫자

| 기록 | 기대 값 |
|---|---:|
| 차체 / 태그 | 각각 100 |
| 공정 완료 | 300 — 차체마다 세 셀 |
| 최종 검사 | 100 |
| 차체 운송 | 400 — 투입·셀 사이 두 번·결과 구역 |
| 검사 PASS / FAIL | 80 / 20 — 명시적인 검증 패턴 |
| 누적 불량률 | 20.0% |

완료한 검사 원본과 운송 원본을 각각 10회 재전송해도 위 숫자는 그대로입니다. 원본 전체의 순번·바이트·SHA-256이 두 DB에서 같은지도 확인합니다. 태그 번호가 같은 두 run을 조회해 한쪽의 5대/검사 5건과 다른 쪽의 100대/검사 100건이 섞이지 않는지 대조합니다.

## 남긴 결과와 다음 단계

결과 JSON, 두 실행의 원본 NDJSON, 단계별 스냅샷, DB 데이터와 서버 로그, 브라우저 증거를 검증 전용 경로에 보존합니다. 최종 숫자와 실행 방법은 통합 기록에 있습니다. UI·업무 서비스·DDL을 검증 편의에 맞춰 바꾸지 않습니다.

S08-01~04 이후 다음은 S09-01입니다. 기본 입력 부하·프레임 크기·처리 지연·대기량을 실제로 측정합니다. 이번 정확성 결과를 성능 보장으로 바꾸어 설명하지 않습니다.

## 실제 완료 결과

실제 원본3,533건·최대 프레임45,147바이트·2,764 tick·중간 snapshot28개, 작업300/검사100/운송400·80/20·중복 증가0과 두 run 격리가 통과했다. 100대는 실제 두 DB/REST와 모델을 비교한 결과이며 브라우저 SSE 선택 보존은 별도 소수 차체 실행 증거다. 상세 실행 번호·원본·DB·로그와 캡처 위치는 S08 통합 기록에 있다.
