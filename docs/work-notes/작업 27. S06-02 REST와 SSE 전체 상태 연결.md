# 작업 27. S06-02 REST와 SSE 전체 상태 연결

> 작업 ID: S06-02 · 완료일: 2026-10-05 · 상태: 완료

## 이번 작업은 무엇인가

관제에 저장한 현재 상태를 브라우저가 계속 받을 수 있게 했다. REST는 필요할 때 한 번 조회하는 요청이고, SSE는 서버가 열린 HTTP 연결을 통해 새 상태를 이어서 보내는 방식이다. 새 사건 한 건씩을 브라우저에서 다시 조립하는 대신 차체·셀·슬롯·차량·신선도·진단을 담은 **전체 상태 묶음**을 보낸다.

이미 있던 ViewPublisher를 그대로 기준으로 삼아 REST와 SSE가 같은 epoch/revision의 묶음을 공유한다. sourceSeq는 공장 스냅샷의 순번, revision은 관제 묶음의 판이다. 공장 위치가 같아도 신선도/알람/품질이 바뀌면 새 revision을 보낼 수 있다.

## 실제 전달 형식

`GET /api/v1/runs/{runId}/stream`을 같은 관제 API 주소로 제공한다.

```text
id: 서버시작UUID:묶음revision
event: factory-snapshot
data: 한 줄의 전체 JSON

```

연결 첫머리는 retry:2000, heartbeat는5초마다 주석 프레임이다. heartbeat나 HTTP 연결 성공을 새로운 공장 관측으로 세지 않는다. Last-Event-ID를 받더라도 과거 화면을 재생하지 않고 최신 전체 묶음을 보낸다. 이력은 기존 REST 조회의 책임이다.

등록 실행의 스냅샷이 아직 없으면 실제 등록 정보를 가진 WAITING 묶음을 보낸다. 등록되지 않은 run은404이며 가짜 실행을 만들지 않는다. 첫 묶음 생성 실패는503이고, 성공처럼 잘린 차체/슬롯 배열을 보내지 않는다.

## 느린 브라우저가 전체 관제를 막지 않도록

연결은 최대20개다. 넘으면 STREAM_LIMIT/429와 Retry-After:2를 응답한다. 연결마다 **전송 중1개 + 대기 최신1개**만 유지한다. 브라우저가 느리면 아직 보내지 않은 과거 화면을 최신 것으로 교체한다. DB의 업무 이력은 그대로 남는다.

Jakarta Servlet의 non-blocking 출력으로 쓸 수 있을 때만 최대8KiB씩 쓴다. 쓸 수 없는 동안 스레드를 붙잡고 기다리지 않는다.5초를 넘긴 미완료 전송은 구독/대기 자료를 정리하고 연결을 완료한다. 컨테이너 연결 제한도5초로 둔다. 구독 제거는 정상 종료·오류·타임아웃·서버 종료에서 같은 경로로 처리한다. 크기 상한은 전체 JSON512KiB, 보내는 빈도는 연결별 최대2회/초다.

이 방식의 API 기준은 [Jakarta ServletOutputStream](https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/servletoutputstream)과 [AsyncContext](https://jakarta.ee/specifications/servlet/6.1/apidocs/jakarta.servlet/jakarta/servlet/asynccontext)를 확인했다. 애플리케이션의 대기 상태 정리와 OS에 이미 전달된 바이트의 소비 완료는 같은 보장이 아니다. 실제 느린 네트워크의 대규모 부하는 S08/S09 범위다.

## 변경한 구성

- SnapshotStreams: 실행별 관제 묶음을 구독자에게 전달, 연결20개 제한/heartbeat/정리.
- SnapshotChannel: 전송 중 한 프레임·교체 가능한 최신 프레임·non-blocking 쓰기/5초 제한.
- StreamFilter: 계약의 /stream 경로만 Servlet async 처리, 안전한 오류 봉투. 다른 REST는 기존 MVC 유지.
- Vue Nginx/Vite: 같은 origin의 /api 경로로 중계. SSE proxy buffering과 캐시를 끈다.

새 DB 구조·언어·브로커·프레임워크는 추가하지 않았다. 수집은 자기 DB만, 관제는 자기 DB만 읽고 쓰는 MSA 경계를 유지한다.

## 꼭 필요한 검증 결과

`python3 scripts/verify-databases.py --suite stream`에서 **Java3개**가 통과했다. 느린 출력의 대기2개 상한/최신 교체/5초 정리1개, 실제 PostgreSQL과 Tomcat HTTP의 SSE 형식·REST 묶음 공유·WAITING·재접속·20개 상한/429·연결 해제1개, 영향받은 bootstrap 격리1개다. 순수 채널 시험은 쓰기 가능 상태/단조 시간을 제어했고 HTTP 프레임/연결 정리는 실제로 확인했다.

Compose에서는 Python의 실제 보고가 Nginx를 통과한 SSE와 Chrome 화면까지 도착했다. sourceSeq가 증가하면서 셀/차체 상태가 바뀌고, 소스 중단 때 받은 물리 상태는 유지한 채 신선도 표시만 바뀌는 것을 확인했다. 최종 수량/증거는 [공유 결과](<../validation/최소 검증 시나리오와 도구.md>)에 기록했다. 최종 점검에서 연결 초기화 예외의 슬롯 회수를 보완한 뒤 영향받은 같은 Java3개만 한 번 재확인했다. 다른 단계의 전체 검증은 반복하지 않았다.
