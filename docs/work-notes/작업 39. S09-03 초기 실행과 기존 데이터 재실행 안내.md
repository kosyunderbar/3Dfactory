# 작업 39. S09-03 초기 실행과 기존 데이터 재실행 안내

> 작업 ID: S09-03 · 2026-10-05 · 완료 · 실행 안내: [초기 실행·재실행·복구·시연](<../development/초기 실행·재실행·복구·시연.md>)

이번 작업은 같은 프로젝트를 다시 켰을 때도 기존 기록을 지키고 새 공장 실행을 시작할 수 있도록 실행 방법을 정리합니다. 자세한 명령과 실제 확인 결과는 연결된 안내에 있습니다.

## 컨테이너와 DB 파일

Compose는 DB·수집 서버·관제 서버·Python·Vue를 함께 켜는 도구입니다. 컨테이너는 실행 중인 프로그램이고, DB 볼륨은 기록을 저장하는 별도 공간입니다. 프로그램을 다시 시작해도 볼륨이 남아 있으면 기록이 남습니다.

처음 환경을 만들 때는 전용 DB와 계정을 한 번 생성합니다. 기존 환경에서는 이 초기화 명령을 다시 사용하지 않습니다. 실제로 기존 DB를 발견하면 초기화 도구가 덮어쓰기를 거부하는지 확인합니다.

## 마이그레이션

Flyway는 DB 구조 변경 파일의 적용 순서와 이력을 관리합니다. 이미 적용한 파일을 수정하는 대신 새 변경 파일을 추가합니다. 서버가 켜질 때 적용된 이력을 확인하고 필요한 새 변경만 수행합니다.

별도 검증 DB에서 기록을 만든 뒤 같은 데이터 디렉터리의 PostgreSQL과 두 Java 서버를 다시 시작합니다. 전후 행 수와 행 내용의 지문을 비교하고 마이그레이션 이력도 확인합니다. 이는 기존 DB를 지우고 새 DB를 만든 재실행과 다릅니다.

## 장애 복구의 책임

수집 ACK 이전의 원본은 Python이 재전송합니다. ACK 이후 관제 반영 전의 원본은 수집 DB의 outbox가 재전달합니다. 관제 서버는 같은 원본을 다시 받아도 업무 사실을 중복 생성하지 않습니다.

오래된 보고나 서버 재시작을 실제 공정 복구와 혼동하지 않습니다. 관제 창은 마지막 확인값을 보존하고 복원 중·보고 지연 등을 표시합니다. 셀 정상화는 시뮬레이터가 실제 정상화 상태를 보고한 뒤에 표시됩니다.

## 새 시연 세션

새 runId로 정상 등록한 차체 5대, 차체 AGV 2대와 부품 AMR 1대를 사용합니다. 예약 만석, 이동 중, 도착 만석, 셀 정지, 슬롯 반환과 복구, 최종 검사까지 진행합니다. 관제 화면에서 실제 단계의 슬롯 수·차체 위치·태그·알람·품질을 확인합니다.

S08의 장애 검증 전체를 불필요하게 반복하지 않습니다. 이번에는 초기화 거부, 기존 데이터 재시작, 새 시연이라는 변경 범위만 추가 확인합니다.

## 이번 실제 결과

새 검증 DB의 초기 DB/계정·Flyway 준비, 기존 DB 초기화 거부, 관제 재빌드/재기동, 양 서버/PG를 같은 data 폴더로 재시작하는 과정을 실제 확인했습니다. 선택한8개 표의 행 수와 내용 지문이 같았고 성공한 Flyway는 수집1/2·관제1입니다. 모든 표나 Python 메모리를 보장한다는 뜻은 아닙니다.

개발 Compose DB/볼륨은 유지했습니다. 검증용 프로세스와 임시 소켓은 종료하고 검증 DB·원본·로그는 보존했습니다. 처음 실행/기존 데이터 재실행/제조 데이터 전송/장애 책임별 복구/측정 재개 명령을 별도 안내에 정리했습니다. 일반 기동은 자동 생산하지 않습니다.
