# 작업 13. AGV 운송과 버퍼 슬롯 반환

## 이번 작업은 무엇인가

앞 작업은 다음 셀의 자리와 AGV를 확보하는 **배차 승인**이었다. 승인해도 차체는 앞 셀에 그대로 남았다. 이번에는 **차량이 차체를 픽업해 운반하고, Bay에 내려놓고, 차체가 셀에 들어갈 때 자리를 반환하는 과정**을 연결했다.

Python 공장 모델의 운송 기능이다. 실제 장비를 움직이거나 Java 서버에 보고서를 보내는 단계는 아니다. 일반 차체 등록부터 세 공정·검사·결과 구역 도착까지 시험용 위치 변경 없이 실행할 수 있다. 기존 기술 스택과 흰색·네이비 UI 기준을 유지한다.

## AGV는 어떤 순서로 움직이는가

| 차량 상태 | 역할 | 차체 위치 | 운송 상태 |
|---|---|---|---|
| TO_PICKUP | 빈 AGV가 픽업 장소로 이동 | INPUT 또는 출발 CELL | ASSIGNED |
| LOADING | 픽업 장소에서 차체를 싣기 전 대기 | 아직 출발지 | ASSIGNED |
| MOVING | 차체를 싣고 목적지로 운반 | VEHICLE / 해당 AGV | IN_TRANSIT |
| UNLOADING | 목적지에서 인계 완료 전 대기 | 아직 AGV | IN_TRANSIT |
| RETURNING | 차체를 내려놓고 빈 차 귀환 | BUFFER 또는 RESULT | 운송 COMPLETED |
| IDLE | 다음 배차를 받을 수 있음 | 차량에는 없음 | 활성 운송 없음 |

`start_transport(transport_id)`가 승인된 차량의 픽업 이동을 시작한다. 단순히 assign_transport만 호출한 앞 작업의 확인은 여전히 차체와 AGV를 움직이지 않는다.

LOADING이 끝나는 순간 출발지의 차체 소유를 AGV로 옮기고 운송을 IN_TRANSIT으로 바꾼다. 출발 셀은 이때 IDLE로 비워진다. 차체를 셀 목록과 AGV 목록에 각각 복사하지 않고 기존 차체의 단일 위치를 교체한다.

UNLOADING이 끝나는 순간 차체를 목적지 Bay/slotId 또는 GOOD/HOLD로 인계한다. 운송을 COMPLETED로 기록하고 차체의 활성 transportId/reservationId를 비운다. AGV도 적재와 활성 운송 참조를 비우고 귀환한다. **Bay에 차체를 둔 AGV가 셀 진입을 기다리며 계속 묶이지 않는다.**

귀환 중에는 새 배차를 받지 않는다. IDLE로 돌아온 뒤 가용 AGV로 사용한다. 실제 위치 좌표와 각 구간의 남은 시간을 로컬 진단에 표시한다.

## 만석인데 기존 예약 차량이 움직여도 되는가

**자기 슬롯을 이미 예약한 차량은 움직여야 한다.** A=0은 새로운 예약을 막는 조건이지 기존 예약을 취소하는 조건이 아니다.

픽업과 목적지 인계에서 자신의 transportId/reservationId/slotId와 차체·AGV 참조가 맞는지 검사한다. 자기 예약이 온전하면 W+R=C여도 진행한다. 이 단계에서 남은 슬롯을 다시 요구하지 않는다.

| 장면 | W | R | A | 무엇이 바뀌는가 |
|---|---|---|---|---|
| C=3, 예약 완료 | 2 | 1 | 0 | 차체는 앞 셀에 있음 |
| 적재/이동/인계 전 | 2 | 1 | 0 | 예약을 계속 보유 |
| Bay 인계 완료 | 3 | 0 | 0 | RESERVED 하나가 OCCUPIED로 바뀜 |
| 대기 차체가 셀 진입 | 2 | 0 | 1 | 작업 자리로 옮겨 Bay 슬롯 반환 |
| 새 배차 한 건 승인 | 2 | 1 | 0 | 반환된 슬롯을 다음 운송이 확보 |

**Bay에 도착하는 것만으로 빈자리가 늘지 않는다.** 예약이 실제 점유로 바뀌었기 때문이다. 대기 차체가 셀에 들어가야 Bay 자리가 비워진다.

OCCUPIED 슬롯에는 도착했던 완료 운송과 예약의 이력 번호를 보존한다. 활성 예약 수 R에는 포함하지 않는다. 초기 시험 배치 차체는 과거 운송이 없으므로 두 이력 번호가 null이다.

## 셀 진입과 슬롯 반환은 어떻게 연결되는가

`enter_cell(body_id)`는 다음 조건을 확인한다.

- 일시정지가 아니고 차체가 자신의 다음 공정 Bay에 실제로 있어야 한다.
- 해당 슬롯을 그 차체가 OCCUPIED로 소유하고 있어야 한다.
- 차체는 미검사 WAITING이고 활성 운송이 없어야 한다.
- 목적지 셀은 IDLE이고 다른 차체를 보유하지 않아야 한다.

통과하면 **Bay→CELL 위치 변경, PROCESSING 상태, 새 작업 번호, 셀 RUNNING, Bay 슬롯 반환**을 함께 처리한다. 별도 AGV 없이 수행하는 단순 내부 인계다. 실제 받침대나 이송 기구 동작은 계산하지 않는다.

CellEntry라는 변경 불가능한 로컬 기록을 남긴다. 차체·셀·반환 슬롯·선행 운송/예약·새 작업 번호와 진입 시각이 연결된다. availableSlotsAfterRelease는 **반환 직후, 재배차 전의 A**다.

곧바로 재배차하면 최종 조회의 A는 다시 0일 수 있다. 빈자리가 생기지 않은 것이 아니라 생긴 한 자리를 새 운송이 즉시 확보한 것이다. 이번 데모에서 반환 기록은 A=1, 재배차 후 조회는 W=2/R=1/A=0으로 확인했다.

## 재배차는 언제 하는가

`redispatch()`는 완료된 후공정 셀부터 검사하고 신규 INPUT 차체를 이어 검사한다. 슬롯과 AGV를 확보할 수 있는 요청만 배차하고 픽업 이동을 시작한다. 입력은 등록 순서를 유지한다. 복잡한 최적화 스케줄러는 아니다.

운송 흐름을 시작하면 각 tick 끝과 셀 진입 직후 재배차한다. 셀이 작업을 마쳤거나 빈 AGV가 귀환했을 때도 다음 tick의 흐름에서 자원을 다시 확인한다. 같은 자원에 두 배정을 만들지 않는 규칙은 S02-03의 함수를 그대로 사용한다.

Bay→셀 진입 자체는 **명시적인 enter_cell 호출**이다. 데모와 테스트가 이 호출을 실행한다. 셀이 바쁜데 도착한 차체는 Bay에 남아 자리를 계속 차지한다. 향후 실시간 생산 구동기가 이 명령들을 호출하도록 연결해야 한다. 일반 서비스 기동은 아직 기본 heartbeat 루프다.

## 시간과 좌표는 어떻게 계산하는가

적재 운반은 실행 설정의 경로 점들을 따라 이동하고 travelDurationMs를 사용한다. 진행 시간에 맞춰 경로 거리의 같은 비율로 차량 좌표를 계산한다.

빈 차의 픽업과 귀환은 해당 적재 경로의 거리/시간에서 얻은 속도로 직선 이동한다. 걸리는 시간은 tick 단위로 올림한다. 처음부터 픽업 장소에 있어도 한 tick을 쓰고, LOADING/UNLOADING도 각각 한 tick으로 단순화했다. 기본 tick은 100ms다. 동선 충돌 방지·교차로 제어·실제 적재 기구는 이번 범위가 아니다.

일시정지 중에는 차량 좌표·구간 시간·차체 인계·셀 작업·재배차가 모두 진행하지 않는다. UTC 기록 시각과 모델 작업/운송 시간의 구분은 기존 규칙을 유지한다.

한 tick이나 셀 진입/재배차 도중 오류가 나면 해당 전환의 차체·작업·예약·차량·번호·난수 상태를 복구한다. 예를 들어 픽업 시각이 잘못돼 실패한 tick에서 다른 셀의 작업 시간만 먼저 줄어든 채 남지 않는다. 여러 tick을 한꺼번에 advance한 경우 앞서 성공한 tick까지 되돌리는 일괄 취소는 아니다.

## 서버 없이 직접 확인하기

프로젝트 루트에서 기존 Python 3.12 환경으로 실행한다.

```sh
scripts/simulator.sh run --demo-transport
```

첫 번째 run은 일반 INPUT 등록 차체 한 대를 사용한다. ASM-01→ASM-02→QC-01→GOOD으로 운송하고 빈 AGV의 귀환까지 계산한다. 고정 PASS 결과를 사용한다.

| 항목 | 기본 실행 결과 |
|---|---|
| 차체 | body-00001 / tag-00001, COMPLETED, RESULT/GOOD |
| 셀 작업 | 3건 |
| 검사 | PASS 1건 |
| 운송 기록 | COMPLETED 4건 |
| 셀 진입/반환 기록 | 3건, 선행 운송/예약과 새 작업 연결 |
| 활성 운송 | 없음 |
| AGV | 빈 차로 귀환, 모두 IDLE |
| 각 Bay | W=0/R=0/A=3 |

두 번째 run은 초기 Bay 대기 2대와 셀의 차체를 명시적으로 시험 배치한다. 이후 픽업·운반·Bay 인계·셀 진입·반환·재배차는 **실제 Python 모델 동작**으로 진행한다. 시험용 위치 이동 함수나 자리 삭제로 반환을 대신하지 않는다. 앞 표의 W/R 변화를 단계별로 출력한다.

출력은 physicalTransportImplemented=true, initialFixturesOnly=true, networkConnected=false다. 실제 물리 장비가 아니라 **모델의 물리 규칙**을 구현했다는 뜻이다. 모델의 runState는 RUNNING이며 전체 실행 FINISHED 전환을 구현했다고 주장하지 않는다.

기본 결과는 `.build-cache/s02-04-transport-preview.json`에 남겼다. maxBodies는 ASM-02 Bay 용량+1 이상이어야 한다. --initial-bodies와 동시에 사용할 수 없다. 확인 명령은 구간별/전체 진행을 5000 tick으로 제한하므로 작업/경로 시간을 아주 길게 바꾼 설정에서는 한도 오류로 끝날 수 있다. 실제 1배속으로 기다리는 데모가 아니라 tick을 빠르게 계산한 결과다.

## 꼭 필요한 검증과 실제 결과

**새 테스트는 3개만 추가했다.** 기존 공통 모델 검증을 포함한 Python 테스트 **13개가 통과**했다.

| 새 테스트 | 필요한 확인 |
|---|---|
| 만석 예약 수명 | 픽업 전 차체 보유, A=0에서 자신의 예약 운송 진행, 실제 픽업 때 셀→AGV 소유 변경, 이동 좌표, 인계 전 R 유지, 도착 W=3/R=0, 반환 직후 A=1과 재배차 1건 |
| 일반 차체 전체 흐름 | 시험용 위치 변경 없이 INPUT→세 셀→GOOD/HOLD, 검사 1건·작업 3건·운송 4건·진입 3건, 태그 매핑 유지, AGV 비움/귀환, Bay/셀 비움 |
| 정지·실패 경계 | 적재 전/운반 중/귀환 중 시간과 위치 유지, 반복 이동 시작이 시간 초기화하지 않음, 잘못된 셀 진입·점유 셀·완료 운송 시작 거절, 시각 오류 때 작업/위치/번호와 다른 셀의 tick 진행 복구 |

```sh
scripts/simulator.sh test
scripts/simulator.sh run --demo-transport
scripts/dev-stack.sh compose up -d --build --wait factory-simulator
```

상태 전환의 오류 복구를 보완한 뒤 전체 Python 13개가 통과했고, 최종 재배차/진단 보완에는 새 운송 테스트 3개만 재확인했다. 시뮬레이터 컨테이너만 갱신해 healthy와 MODEL_INITIALIZED / registeredBodyCount=0 / factoryRunStarted=false를 확인했다.

DB/Java/GUI/기존 계약 전체 테스트는 반복하지 않았다. 이번 변경은 Python 모델과 로컬 확인 명령에 한정했다. 현재 Vue 화면의 준비 상태를 운송 데이터 LIVE로 바꾸지 않는다.
