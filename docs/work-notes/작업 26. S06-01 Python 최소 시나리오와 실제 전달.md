# 작업 26. S06-01 Python 최소 시나리오와 실제 전달

> 작업 ID: S06-01 · 완료일: 2026-10-05 · 상태: 완료

## 이번 작업은 무엇인가

앞 단계에서 준비한 모델·TCP 수집·자동 HTTP 전달을 **사람이 실행할 수 있는 시나리오 한 개**로 연결했다. `--connected-demo`를 명시하면 차체 한 대를 BODY-IN에 등록하고, 실제 모델의 AGV 운송·셀 작업·Bay 진입·검사를 진행해 GOOD으로 보낸다. 빈 AGV 귀환과 셀 정리까지 끝나면 모델이 최종 스냅샷과 RUN_FINISHED를 생성한다.

최소 관측의 중심은 차체 1대와 ASM-01이다. 사건 v1이 고정한 3셀/차량/Bay 구성은 유지하고 그 차체가 최종 검사까지 가는 기존 모델 흐름을 사용한다. 서로 다른 단계의 예제를 억지로 붙이거나 시험 위치 변경으로 공정 사이를 건너뛰지 않는다.

## 기술의 역할

| 구성 | 이번에 하는 일 |
|---|---|
| Python FactoryModel | 물리 상태·슬롯·차체 위치·공정/검사 결정 |
| SourceSession | 모델의 보고를 송신 대기 목록에 넣고 ACK 뒤 해제 |
| TCP/NDJSON | 한 번 직렬화한 원본을 수집기로 보내 저장 확인 |
| 수집 outbox / REST | 저장한 동일 원본을 관제에 자동 전달 |
| 관제 DB | 원본과 업무 사실·최신 상태 보관 |
| 실행 산출물 | run/body/tag 번호와 실제 보낸 NDJSON 기록 |

S05의 정상 60건 자동 전달 증거를 재사용했다. 이번에는 새 실행 진입점과 실제 시간에 따라 바뀌는 보고를 화면까지 보내는 경계만 추가 확인했다. 기존 공장 모델/수집/전달 테스트를 모두 다시 실행하지 않았다.

## 실행 방법

프로젝트 루트에서 기존 Compose를 기동한 뒤 실행한다.

```sh
scripts/dev-stack.sh up
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run --connected-demo
```

새 runId/body-00001/tag-00001과 산출물 경로가 처음에 출력된다. Vue `http://127.0.0.1:5173`에서 목록을 새로 읽고 해당 실행을 선택한다. `?run=실제runId`로 직접 열 수도 있다. 일반 Python/Compose 기동은 계속 초기화/heartbeat만 수행하며, 생산을 시작하려면 위 옵션을 명시한다.

tick은 기본100ms, 전체 상태 보고는 기본500ms다. 송신·저장이 늦으면 무리하게 밀린 tick을 한꺼번에 확정하지 않는다. 검사 결과는 이 단일 시연에서 고정 PASS이며 실제 공장의 불량 분포나 성능 측정이 아니다. 실행 설정은 `--config /absolute/path/run.json`으로 변경할 수 있다.

`.build-cache/connected-demo/{runId}/`에 run.json·originals.ndjson·result.json·필요한 오류 로그를 남긴다. CLI의 INGESTION_CONFIRMED는 수집 ACK까지의 확인이다. 관제/브라우저 반영을 확인하지 않은 CLI가 operationsApplied/guiConfirmed를 true로 만들지 않는다. 성공한 일반 시연의 DB 자료는 자동 삭제하지 않는다.

Ctrl+C는 새 계산/송신을 멈추고 연결을 정리한다. 실패/중단 시 원본 파일을 남기지만, Python 모델을 종료 후 복원하는 기능은 아니다. 데이터 파일 재송신과 물리 공장 재개를 혼동하지 않는다.

## 필요한 검증과 시간 제한 수정

공유 S06 검증은 Java3개·브라우저 공급부 Node2개와 실제 전체 시나리오다. 새 시연 명령은 실제 Python/TCP/두 DB 연결에서 검증했다. DB 원본/해시/순번, 태그1:1, 작업3/검사1을 최종 결과와 비교했다. 자세한 최종 결과는 [공유 검증 기록](<../validation/최소 검증 시나리오와 도구.md>)에 있다.

첫 실제 실행은 검사/GOOD 도착 뒤 빈 AGV 귀환 중 120초 제한에 걸렸다. 검증용 프로세스를 잠시 정지한 시간도 실제 경과 시간에 포함됐기 때문이다. 종료를 성공으로 꾸미지 않고 이미 수집한 기록을 보존했다. 제한을300초로 조정해 새 UUID 실행의 실제 연결 검증만 다시 수행했다. 검증 설정에서는 화면 관측 시간을 위해 ASM-01 작업 시간을20초로 두었고 기본 설정의4초는 바꾸지 않았다.
