## 이번 작업은 무엇인가

앞 작업에서 수집 서버와 관제 서버를 각각 만들고 저장 공간을 준비했다. 이번에는 프로그램들을 정해진 설정으로 함께 켜고, 준비됐는지 확인하고, 종료하는 방법을 만들었다.

공장에 비유하면 각 부서의 사무실과 기록장은 준비돼 있었다. 이번 작업은 “어떤 부서를 어떤 순서로 열고, 업무를 시작할 준비가 됐는지 어떻게 확인할 것인가”를 정한다. 아직 차체를 운송하거나 사건을 처리하는 단계는 아니다.

사용자가 요청한 1-3은 계획의 **S01-03**이다. Python/Vue 실행 단위를 완성하는 **S01-04**까지 이어서 검증했고, 설명은 [작업 8](<작업 8. Python과 Vue 기본 앱.md>)에 분리했다.

## 기술과 파일의 역할

| 요소 | 쉬운 설명 | 이번 파일 |
|---|---|---|
| Docker 이미지 | 한 프로그램과 실행 도구를 담은 실행 꾸러미 | Spring/Python/Vue Dockerfile |
| 컨테이너 | 그 꾸러미로 켠 실제 프로그램 | Compose의 5개 service |
| Compose | 어떤 프로그램을 어떤 설정으로 함께 켤지 적은 실행 목록 | compose.yaml |
| 환경 변수 | 코드 밖에서 전달하는 주소·계정·암호·포트 | .env, .env.example |
| healthcheck | 각 프로그램이 정한 준비 조건을 주기적으로 확인 | Compose, /readyz, heartbeat |
| 볼륨 | 컨테이너가 종료돼도 DB 파일을 남기는 저장 공간 | postgres-data |
| 로그 | 프로그램이 남기는 기동/오류/종료 기록 | 표준 출력, dev-stack.sh logs |

Spring 이미지는 빌드 단계에서 Maven Wrapper로 JAR를 만들고, 실행 단계에는 JRE와 JAR만 옮긴다. 두 서비스는 서로의 코드를 빌드하지 않는다. 빌드에 필요한 unzip을 빌드 이미지에 넣어 기존 Maven ZIP 체크섬 검증을 유지했다. 컨테이너 healthcheck는 작은 Java HTTP 확인 프로그램으로 자기 서버의 준비 상태를 검사한다.

## “살아 있음”과 “준비됨”을 구별한다

서버 창이 열렸어도 기록장에 접속하지 못하면 저장 업무를 시작할 수 없다. 그래서 두 질문을 분리한다.

| 질문 | 주소 | 정상 일반 실행 | DB 중단 | DB 없는 bootstrap |
|---|---|---|---|---|
| 프로세스가 기본적으로 살아 있는가 | /livez | 200 | 200 | 200 |
| 앱과 자기 DB가 준비됐는가 | /readyz | 200 | 503 | 503 |

HTTP의 200은 정상 응답, 503은 현재 준비되지 않았다는 뜻이다. Spring Actuator가 이 응답을 만든다. 기본 준비 검사에는 실제 앱 DataSource의 DB 연결을 포함한다. DB를 쓰지 않는 bootstrap 모드는 항상 준비되지 않았다고 답한다. health 외의 설정/환경 정보 공개 endpoint는 켜지 않았다.

**이 준비 상태는 공장 실시간 데이터의 LIVE 상태가 아니다.** 현재는 서버와 DB 실행 기반까지만 준비됐다. TCP 사건 수집, 업무 처리, REST/SSE 데이터 연결은 후속 단계다. 화면에서도 서버 준비 상태와 공장 데이터 연결 전을 구별한다.

## 실제 기동과 서비스 독립성

Compose는 PostgreSQL의 기본 준비 상태를 기다린 뒤 두 Spring 앱을 켠다. 각 앱은 자기 Flyway 계정으로 자기 DB의 V1을 확인하고, 일반 계정으로 연결 풀을 준비한다.

수집 앱과 관제 앱 사이에 기동 의존성을 두지 않았다. 수집 앱을 멈춰도 관제 앱·화면·Python 프로세스는 유지된다. 공통 DB 인스턴스가 멈추면 두 앱의 준비 상태는 함께 내려간다. 이것이 “프로그램 분리”와 “공유 기반 시설”의 차이다.

Vue는 서버가 없어도 화면 파일을 제공할 수 있다. Python의 현재 기본 루프도 다른 서버가 없어도 기동한다. 다만 어느 것도 실제 공장 사건이 연결됐다고 표시하지 않는다.

## 암호와 DB 기록은 어떻게 다루는가

`scripts/dev-stack.sh env`는 로컬 암호를 무작위 생성해 .env에 보관한다. 파일 권한은 0600이고 암호 값을 화면에 출력하지 않는다. 기존 파일이 있으면 덮어쓰지 않는다. 필수 암호가 누락되면 Compose 구성부터 실패한다.

`down`은 프로그램을 종료하지만 postgres-data 볼륨을 남긴다. 다음 `up`은 기존 기록과 Flyway 이력을 사용한다. 초기 계정/DB 준비 SQL은 빈 데이터 폴더에서만 실행된다. 볼륨 삭제나 DB reset을 helper의 기본 동작으로 넣지 않았다.

첫 컨테이너 초기화에서 SQL이 읽는 환경 변수 이름과 Compose 설정 이름이 달라 실패했다. 이름을 맞춘 뒤 기존 볼륨의 프로젝트 역할/DB가 아직 없음을 초기 SQL의 거절 검사로 확인해 준비를 이어 갔다. 이어서 **별도 새 검증 볼륨**에서 최초 자동 초기화까지 다시 확인했다. V1 마이그레이션은 수정하지 않았다.

## 실제 수행한 최소 검증

1. 두 앱의 기존 기동 테스트 1개씩에 bootstrap의 `/readyz` 503, `/livez` 200 확인을 포함했다. 각각 1개 통과했다.
2. 실제 Compose 통합 검증 1개로 아래 실행 경계를 확인했다. 기존 DB 권한 테스트 전체나 계약 예제 전체를 다시 돌리지 않았다.

```sh
scripts/service-maven.sh ingestion-service -o -B -Dtest='*ApplicationTests' test
scripts/service-maven.sh operations-service -o -B -Dtest='*ApplicationTests' test
FACTORY_COMPOSE_PROJECT=factory-foundation-check python3 scripts/verify-stack.py
```

| 통합 시나리오 | 실제 결과 |
|---|---|
| 필수 설정이 없는 Compose 구성 | 실패 — 정상적인 거절 |
| 새 프로젝트의 최초 DB 준비와 5개 프로그램 기동 | 모두 healthy |
| 수집 앱 중단 | 나머지 4개 프로세스 유지, 관제/화면 준비 응답 정상 |
| DB 중단 | 두 Spring 앱 readyz 503 / livez 200 |
| down → up | 두 DB의 검증용 행과 V1 적용 이력 유지 |
| 종료 정리 | 생성한 고유 검증 행 2개만 삭제, 검증 컨테이너 종료, 볼륨 보존 |

검증 DB는 PostgreSQL 17.11, Docker Engine 29.8.2 / Compose 5.6.0 / Buildx 0.37.2이며 macOS arm64의 Lima 2.2.1 VM에서 실행했다. Java 컨테이너는 Temurin 21.0.12.1+1이다. 로컬 JDK 21.0.7+6으로 수행한 기동 테스트와 구별한다.

결과 파일은 `.build-cache/stack-verification/stack-probe-bb974d661b5748b285235c8f67d9a5f9/result.json`이다. 모든 기록은 PASS다. 일반 빌드/기동 및 도구 보완 로그는 `.build-cache/`에 있으며 테스트용 계약/업무 사례를 새로 만든 것은 아니다.

## 실행할 때 알아둘 것

자세한 명령은 [전체 실행 안내](../../infrastructure/README.md)에 있다. 이번 컴퓨터에는 Docker가 없어 선택적인 로컬 CLI·Lima VM을 준비했다. VM의 DB 파일은 짧은 `/tmp/factory-lima-s01` 경로에 있다. Compose 재기동에는 유지되지만 OS 임시 폴더 삭제까지 보장하는 장기 저장 방식은 아니다. 상시 데이터는 지속 저장소와 백업이 필요하다.

검증용 프로젝트는 종료했고, 확인용 기본 `factory-dev` 환경은 기동해 뒀다. `http://127.0.0.1:5173`에서 실제 Vue 기본 화면을 볼 수 있다. 사용 후 `scripts/dev-stack.sh down`, `scripts/local-docker.sh stop`으로 종료할 수 있다.

이번 완료는 **프로그램 실행 기반의 완료**다. 버퍼 예약·Unload 차단·태그 상태 갱신·사건 전달과 실시간 관제는 아직 구현하지 않았다. 다음 단계는 S02의 Python 공장 모델이다.
