# 작업 25. S05-03 재시작 복구와 전달 진단·재개

> 작업 ID: S05-03 · 완료일: 2026-10-05 · 상태: 완료

## 이번 작업은 무엇인가

프로그램을 다시 켜도 DB에 남은 전달 책임을 이어받게 했다. 또한 “얼마나 밀렸고 어디서 멈췄는가”를 조회하고, 원인을 해결한 뒤 같은 보고서의 발송을 명시적으로 재개할 수 있게 했다.

worker는 재시작할 때 메모리의 송신 목록을 새로 만드는 대신 delivery_stream의 책갈피와 event_outbox의 상태·횟수·다음 시도 시각을 읽는다. 관제 성공이 아직 수집 DB에 기록되지 않았다면 같은 원본을 다시 보내 중복 성공으로 확인한다. PAUSED/BLOCKED를 프로그램 재시작만으로 풀지 않는다.

## 진단과 재개 API

| API | 역할 |
|---|---|
| GET /internal/v1/runs/{runId}/delivery-status | 책갈피·미전달 수/바이트·최초 대기 시각·중단 원인·누적 횟수·생산자 TCP 연결 표본 |
| GET /internal/v1/runs/{runId}/outbox | 보고서별 상태·해시·시도/대기 시각·거절 답장의 제한 페이지 |
| POST /internal/v1/runs/{runId}/delivery-resume | 원인 해결 후 현재 보류 head의 동일 원본 재시도 |

diagnostic은 v1의 16필드다. pending에는 격리 원본도 포함한다. 가장 오래된 receivedAt과 sampledAt을 함께 보고 대기 시간을 판단한다. 관제 서비스는 이 정보를 HTTP로 조회하며 수집 DB를 직접 읽지 않는다.

sourceConnected는 지금 열려 있고 해당 run의 저장 성공을 확인한 TCP 연결을 뜻한다. 과거 ACK나 DB 행만으로 true로 만들지 않는다. 수집기 재시작 후 새 TCP 수신이 없으면 false다. 진단을 못 얻으면 관제는 마지막 표본을 현재 정상으로 추정하지 않고 UNAVAILABLE/UNKNOWN으로 표현한다.

누적 retryCount는 최초 시도 이후 **DB에 예약한 추가 시도** 수다. HTTP 직전 종료는 실제 전송 여부가 불명확할 수 있지만 횟수는 남는다. 명시적 재개는 이번 시도 묶음만 0으로 시작하며 totalAttemptCount와 누적 진단값을 지우지 않는다. TCP 영구 거절은 이미 수집에 등록된 run에만 집계하며, 아직 정상 등록되지 않은 잘못된 입력은 제한 로그로 남긴다.

재개에는 현재 sourceSeq·operatorId·이유가 필수다. PAUSED_RETRY/PAUSED_DEPENDENCY/PAUSED_CONFIG만 허용하고, 다른 순번·QUARANTINED/BLOCKED는 거절한다. DB에 이전 상태·운영자·이유·시각을 같은 트랜잭션으로 남긴다. PAUSED_GAP은 누락 원본이 들어오면 자동으로 그 번호부터 진행한다. operatorId는 이 학습용 내부 도구의 입력이며 사용자 인증 시스템을 구현했다는 뜻은 아니다.

## 사용 예시

프로젝트 루트에서 실제 runId와 현재 보류 번호로 바꿔 사용한다.

```sh
python3 scripts/delivery-control.py status run-20261005-00000000000000000000000000000000
python3 scripts/delivery-control.py outbox run-20261005-00000000000000000000000000000000 --status QUARANTINED
python3 scripts/delivery-control.py resume run-20261005-00000000000000000000000000000000 --source-seq 8 --operator local-user --reason '관제 접속 복구 확인'
```

위 번호는 형식 예시이며 존재하는 실행을 조회한다는 뜻은 아니다. 성공한 이번 검증 run은 정리했으므로 그대로 조회하면 404다. 내부 API 응답은 no-store로 캐시하지 않는다. 페이지 기본 50/최대 200건, 응답 최대 512KiB이며 원본 전체는 목록에 노출하지 않는다.

## 꼭 필요한 검증 결과

공유 DB 검증에서 동일 원본 재전달·완료 저장 rollback 뒤 새 worker 복구, 20회 보류 유지, 명시적 재개 기록과 누적 횟수 유지, 실제 TCP 연결 종료 진단을 확인했다.

Compose에서는 관제를 중단한 상태에서 뒤 보고서의 수집 ACK를 받았다. 미전달 기록을 남긴 채 수집 컨테이너를 재시작했고 pending 수와 책갈피가 유지됐으며 head 시도 횟수도 1→1로 초기화되지 않았다. 원본 1번 재송신은 DUPLICATE_RECEIVED였다. 관제를 복원하자 원본 60건이 정확한 바이트/해시로 반영되고 **pending=0, nextSourceSeq=61, LIVE→FINISHED/ARCHIVED**가 확인됐다. 태그 조회는 HOLD/FAIL, 검사 수1/FAIL1이었다.

증거는 `.build-cache/database-verification/20261005T090132Z-4d0587ad/`와 `.build-cache/delivery-verification/f02af2cde1134e5298da715c1a80257d/`에 있다. 기존 행0건을 확인한 새 UUID만 사용했고, 다른 실행의 미전달이 없을 때만 서비스를 잠시 중단했다. 관제는 복원했으며 성공한 검증 실행만 정리했다. 실패한 검증 실행은 진단을 위해 보존하도록 도구를 구성했다. DB/볼륨 초기화는 하지 않았다.
