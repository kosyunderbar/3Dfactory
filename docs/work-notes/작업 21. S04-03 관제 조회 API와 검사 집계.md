# 작업 21. S04-03 관제 조회 API와 검사 집계

> 작업 ID: S04-03 · 완료일: 2026-10-05 · 상태: 완료  
> 실제 PostgreSQL SQL · REST DTO · 기간/페이지 상한

관제 DB에 쌓인 상태와 이력을 화면이 조회할 수 있는 REST API를 구현했다. 이번에는 화면에 필요한 데이터를 제공하는 서버를 만들었다. 실제 Vue 지도와 태그 창 연결은 S06/S07이다.

## REST, SQL, DTO를 쉽게 이해하기

REST는 “태그 1번의 차체를 알려 줘”, “최근 5분 검사를 알려 줘”처럼 HTTP 주소로 요청하는 방식이다. SQL은 서버가 DB에서 필요한 기록을 찾고 세는 언어다. DTO는 화면으로 보내기로 정한 데이터의 모양이다. DB의 모든 컬럼·암호·내부 주소를 그대로 보내지 않는다.

[OperationsController.java](../../services/operations-service/src/main/java/dev/factory/operations/api/OperationsController.java)가 요청을 받고, [HistoryQueries.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/HistoryQueries.java)가 실제 조회 SQL과 기간·페이지 규칙을 처리한다. [ReadSupport.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/ReadSupport.java)가 집계와 사건/알람 DTO를 만든다.

| 경로 | 조회 목적 |
|---|---|
| GET /api/v1/runs | 실행 목록 |
| GET /api/v1/factory/layout?runId=… | 해당 실행의 등록 공장 구성 |
| GET /api/v1/runs/{runId}/snapshot | 전체 현재 관제 묶음 |
| …/equipment/{id}, …/buffers/{id}, …/vehicles/{id} | 셀·Bay·차량 상세 |
| …/bodies/{bodyId}, …/tags/{tagId}/body | 차체 상세·태그로 차체 찾기 |
| …/events | 차체·셀·차량·사건 종류·기간별 이력 |
| …/quality, …/trends | 검사 수/불량률과 시간 구간별 검사 추이 |
| …/alarms | 활성·확인 여부·심각도·기간별 알람 |
| GET /api/v1/system/status?runId=… | 관제 처리 상태와 수집 전달 진단 |

알람 확인 POST는 작업 22에서 설명한다. 상세 경로·응답 필드는 [v1 화면 계약](../../contracts/v1/monitoring.md), 실행 예시는 [관제 안내](../../services/operations-service/README.md)에 있다. 잘못된 쿼리·없는 대상·변경된 cursor·DB 장애는 명시적인 오류 봉투로 응답한다. API에는 Cache-Control=no-store를 적용했다.

## 지도와 상세가 서로 다른 현재 값을 보이지 않도록

[ViewPublisher.java](../../services/operations-service/src/main/java/dev/factory/operations/domain/ViewPublisher.java)는 run별 전체 묶음을 한 번에 만든다. DB의 REPEATABLE READ 읽기를 사용하여 생성 중 다른 사건이 커밋되어도 하나의 DB 읽기 기준으로 구성한다. 물리 배열은 한 factory_snapshot에서만 가져온다.

500ms 게시 간격을 두고 상세 조회도 해당 묶음의 serverEpoch/revision을 사용한다. revision은 같은 서버 실행에서 늘어나는 게시 번호다. 두 HTTP 요청 사이에 다음 게시가 일어날 수 있으므로, 동시에 요청했다고 항상 같은 revision을 보장하는 것은 아니다. 화면은 같은 epoch에서 더 큰 revision의 전체 묶음을 우선하게 된다. 이 Vue 수신 규칙은 후속 작업이다.

등록된 차체가 아직 관측되지 않았으면 data=null이며, 등록 자체가 없는 차체/태그는 404다. “아직 모름”과 “대상이 없음”을 구분한다.

## 검사 집계와 시간 경계

검사 완료 차체 수를 스냅샷에서 세지 않고 고유 inspection_result를 SQL로 집계한다. 검사 100건 중 FAIL 20건이면 inspected=100, pass=80, fail=20, failRate=0.2다. 화면은 비율에 100을 곱해 20%로 표시한다. 표본이 0이면 failRate=null이며 0%라고 단정하지 않는다.

기간은 [from,to)이다. from의 검사는 포함하고 to와 같은 시각은 제외한다. 기본은 조회 시각까지 최근 5분이고 최대 24시간이다. 추이는 1초/5초/60초 버킷, 최대 300개로 제한하며 요청 시작/끝에 걸친 버킷을 잘라 집계한다. 지연 검사는 원래 검사 발생 구간의 값을 정정할 수 있다.

## 이력 페이지가 흔들리지 않도록

limit은 기본 50, 최대 200이다. 서버는 첫 조회 시각과 커밋된 기록의 경계 번호를 고정하고 다음 페이지 위치를 HMAC 서명한 cursor로 전달한다. HMAC은 cursor 내용이 바뀌지 않았는지 확인하는 서명이다. 사건을 날짜·순번·사건 ID로 정렬해 동률도 확정한다.

첫 페이지 뒤에 늦은 검사 보고가 새로 저장되더라도 이미 시작한 페이지 조회에 끼어들지 않는다. 새 조회에서는 볼 수 있다. cursor는 10분 만료, 최대 2KiB이며 필터나 limit을 바꿔 이어 읽으면 409다. 프로세스를 재시작하면 서명 키가 바뀌므로 새 조회를 시작해야 한다. 페이지는 최대 512KiB, 완전한 항목 단위로 제한한다.

## 필요한 최소 검증

S04 공통 7개에서 실제 PostgreSQL의 100/20/.2 집계, 0건 null, 반열린 시각 경계, 늦은 검사 반영, cursor 기간 유지·변조/필터 불일치·지연 사건 제외를 확인했다. 실제 HTTP와 Compose에서도 태그가 HOLD 차체를 찾고 검사 FAIL 한 건과 사건 60건을 조회하는 결과를 확인했다.

```sh
python3 scripts/verify-databases.py --suite operations
python3 scripts/verify-operations.py
```
