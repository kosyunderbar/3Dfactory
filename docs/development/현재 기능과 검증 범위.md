# 현재 기능과 검증 범위

> 2026-10-11 · 작업 59까지의 저장소 소스 기준. GitHub에 최신 변경이 올라갔다는 뜻은 아니다.

## 현재 실행과 화면

일반 웹 선택지는 **1대 정상 / 3대 정상 / 5대 장애·수동 복구**다. 기본 선택은 5대다. 5대는 차체 수이며 설비는 ASM 2·QC 1, 차량은 AGV 2·AMR 1이다. 현재 세 시나리오는 PASS 검사 패턴을 사용한다. 설비 정지와 품질 불합격은 별개다.

Three.js 0.186.1을 Vue 3에 직접 연결한다. 기본 공장 3D와 2D SVG 대체 보기, 실제 설비 상태·차량 목적지·적재, 차체/태그 조회, 품질·알람, 기록 탭을 제공한다. 모델은 코드 형상이며 외부 GLB 파일을 내려받아야 실행되는 구성이 아니다. AGV·AMR의 3인칭 추적은 차량 뒤쪽 위에서 따라가고 드래그로 상대 시점·휠로 거리를 바꾼다. AGV 전면 1인칭은 별도 선택이다. 카메라는 관측 위치를 표현하며 차량 주행 규칙을 바꾸지 않는다.

## 화면 연속 재생 개선 — 작업 61

3D는 수신 시각 기준 600ms 버퍼에서 공장 전체를 같은 시점으로 재생한다. 동일한 물리 스냅샷의 재발행은 애니메이션을 재시작하지 않는다. 정지 위치에서 적재·상태가 바뀌어도 다른 차량의 보간을 끊지 않으며 로봇팔도 관측 사이의 시간을 사용한다. 3D의 상태·적재·경로는 함께 전환하고, 상세 패널은 최신 보고를 사용하므로 짧은 표시 시차가 있을 수 있다. 미수신 미래 위치를 추측하지 않고 실제 경로 변경·양보·정지와 연결 단절은 유지한다.

3인칭 카메라의 가림 검사는 정적 설비 경계 상자를 사용한다. 이는 카메라 렌즈 위치 계산의 최적화이며 AGV 물리 충돌 규칙이나 상세 외형을 바꾸지 않는다. [작업 61](<../work-notes/작업 61. 3D 관측 재생 끊김과 추적 카메라 부하 개선.md>)에 코드·브라우저 검증과 한계를 기록한다.

## 물류와 부품

교통 정책 4의 설정된 통로를 A*로 계획하고 구간별 통행 예약과 양보를 적용한다. 가감속·정지 회전·적재물 포함 충돌 여유를 모델과 화면에서 같은 시간 곡선으로 표현한다. 적재 중에는 전진하며, 빈 차량의 제한적인 접안 출발 후진만 허용한다. 빈 설비에는 직접 인계하고 대기가 필요한 경우 Bay에 보관한다. Bay에서 설비로도 AGV가 옮긴다. Bay 슬롯은 AGV 픽업 완료 시 반환하고 설비 작업은 셀 인계 완료 후 시작한다. 짧은 공정은 현장에서 완료를 기다리고, 모든 생산·출고 이후 외곽 통로로 초기 위치에 복귀한다.

AMR은 ASM 뒤쪽의 전용 통로에서 PARTS-STORE → PARTS-ASM-01/02로 키트를 나른다. 공정마다 초기 2키트를 두고 용량도 2다. 1대 실행도 기본 설정의 초기 2키트를 사용하므로 추가 보급이 필요하지 않을 수 있다. 설정의 maxBodies가 1일 때만 초기 1키트다. ASM 작업 시작 때 실제 키트 1개를 소비하고, 도착 완료한 배송만 재고로 센다. 재고+운송 중 수량과 남은 차체 수요를 비교해 보충하며 보급할 일이 없으면 후면 대기점으로 돌아간다. 재고가 없으면 조립을 시작할 수 없다.

`available + consumed = initialStock + delivered`, `available + inbound <= capacity`를 유지한다. 부품 재고는 차체 Bay의 W/R과 별개다. 개별 BOM, 공급 창고의 유한 총재고·외부 입고는 포함하지 않는다.

## 수동 장애와 제어 경계

5대 실행의 첫 ASM-01 작업에서 1초 진행 후 위치 센서 불일치를 주입한다. DETECTED → 사용자 **현장 점검 시작** → INSPECTING → 사용자 **조치 완료 · 재가동** → VERIFYING 2초 → RESOLVED 순서다. 사용자 조작 없이 자동 복구하지 않는다. 해당 설비의 차체·작업 진행량과 이미 소비한 부품을 보존하고 복구 후 남은 작업을 이어간다. 다른 설비·차량은 가능한 작업을 계속한다.

로컬 Vite `/__simulation` 실행기가 해당 Python 자식 프로세스의 표준입력으로 명령을 보내고, runId·faultId·현재 단계가 맞는 응답을 확인한다. 일반 관제 알람의 **알람 확인**은 확인 기록이며 설비를 복구하지 않는다. 장애 조치 이력은 로컬 실행 상태와 `.build-cache/connected-demo/<runId>/maintenance.json`에 저장된다. 이 이력이 모두 별도 영속 정비 DB/API로 구현된 것은 아니다. 설비 상태 사건과 관측 스냅샷은 기존 TCP→수집→관제→SSE로 전달된다.

시작·중단·수동 복구는 해당 실행기를 켠 Vite에서 사용한다. CLI나 다른 실행기가 만든 run을 선택하는 것만으로 그 프로세스의 복구 권한·제어 연결이 생기지 않는다. 정적 Docker/Nginx 또는 `vite preview`는 이 실행기를 제공하지 않는다. 중단은 일시정지·이어하기가 아니며 다음 시작은 새 run이다. Vite 재시작도 관리 중인 Python을 중단시킨다.

## Windows 소스 전달 — 작업 62

GitHub 전체 소스를 받은 Windows x64 PC는 [처음 실행 안내](../../WINDOWS-START.md)의 `01-prepare-windows.cmd` → `02-start-windows.cmd`를 사용한다. 최초 준비에는 인터넷이 필요하며 Git/Docker 사전 설치는 필요하지 않다. macOS의 Git 없는 별도 소스 폴더에서 Python 설정 검사·Vue·Java 2개 서버 빌드를 확인했다. Windows CMD/PowerShell 자체 실행 및 새 Windows의 전체 시연은 이번에 재검증하지 않았다. [작업 62](<../work-notes/작업 62. GitHub 소스의 Windows 더블클릭 실행 준비.md>)에 범위를 기록했다.
