# 초기 실행·재실행·복구·시연

> S09-03 · 프로젝트 루트에서 실행 · 기존 Java/Python/Vue/PostgreSQL/Compose 스택 유지

새 컴퓨터의 도구 설치·clone·첫 환경 준비와 기존 저장소의 pull 후 개발은 [다른 컴퓨터 실행·개발 안내](<../../가상 제조공장 실시간 통합 관제 시스템 - 다른 컴퓨터 실행·개발 안내.md>)를 먼저 따릅니다. 이 문서는 복구·측정 도구의 상세까지 설명하는 후속 안내입니다.

처음 보는 사람에게 설명하며 시연하려면 [기능 설명 및 시연 시나리오](<../../가상 제조공장 실시간 통합 관제 시스템 - 기능 설명 및 시연 시나리오.md>)를 따릅니다. 기능 소개, 발표 멘트, 화면 조작과 장면별 진행 방법을 제공합니다.

## 처음 준비하는 환경

Docker Engine·Compose가 준비된 환경에서 다음을 실행합니다. 이 프로젝트에 이미 `.env`와 DB가 있다면 아래의 **기존 환경 다시 켜기**를 사용합니다.

```sh
scripts/dev-stack.sh env
scripts/dev-stack.sh check
scripts/dev-stack.sh up
scripts/dev-stack.sh status
```

`env`는 로컬 암호 파일을 만들며 기존 파일을 덮어쓰지 않습니다. PostgreSQL 초기화는 빈 데이터 디렉터리에서만 수행합니다. 두 Spring 서버는 각자의 DB에 Flyway 변경을 적용합니다. `/readyz` 성공은 서비스·DB 준비를 뜻하며 실제 제조 보고가 LIVE라는 뜻은 아닙니다.

이 macOS에서 프로젝트 전용 Lima Engine을 사용하는 경우 먼저 `scripts/local-docker.sh start`를 실행합니다. 최초 도구 준비와 다른 환경의 설치 기준은 [전체 실행 안내](../../infrastructure/README.md)와 [버전·빌드 기준](<실행 버전과 빌드 기준.md>)을 따릅니다. 임시 VM 저장 위치의 장기 보관 범위도 해당 안내에 있습니다.

## 기존 환경 다시 켜기

```sh
scripts/dev-stack.sh up
scripts/dev-stack.sh status
```

기존 `.env`와 DB 볼륨을 사용합니다. 초기 계정 생성 SQL을 다시 실행하거나 `.env`만 새로 만들어 DB의 기존 암호가 바뀌었다고 가정하지 않습니다.

일부 서비스의 코드만 반영하려면 다음과 같이 실행합니다.

```sh
scripts/dev-stack.sh compose up -d --build --wait ingestion-service operations-service factory-console
```

종료는 `scripts/dev-stack.sh down`입니다. DB 볼륨과 수집 거절 로그 볼륨을 보존합니다. 다시 `up`하면 같은 DB를 사용합니다. 적용된 마이그레이션을 수정하지 않고 새 변경 파일을 추가합니다. DB를 지우는 것을 장애 해결의 기본 절차로 사용하지 않습니다.

## 현재 수동 복구 시연 · 2026-10-11

일반 시나리오는 1대 정상 / 3대 정상 / 5대 장애·수동 복구다. 서버 기동 후 호스트 Python 3.12와 Node를 준비한다.

```sh
sh scripts/console.sh install
FACTORY_SIMULATOR_PYTHON="$PWD/.build-cache/simulator-venv/bin/python" sh scripts/console.sh dev --port 5174
```

이 Vite에서 5대 시나리오를 시작하고 점검/조치 버튼을 사용한다. 정적 Docker 5173은 관측용이다. 아래 `--connected-p0-demo`와 marker는 **과거 자동 P0 검증용**이며 현재 5대 수동 실행과 다르다. [현재 시연 순서](<../../가상 제조공장 실시간 통합 관제 시스템 - 기능 설명 및 시연 시나리오.md>)를 따른다.

## 정상 CLI와 과거 P0 검증 데이터를 보내기

Windows 로컬 실행은 [Docker 없는 실행 안내](<Windows Docker 없이 실행.md>)의 웹 시작 버튼이나 PowerShell 명령을 사용한다. 웹 버튼은 새 runId로 1대/3대 정상 생산 또는 5대 시나리오를 시작하고 자동으로 관측 연결한다. 정적 배포/Compose 화면에는 해당 로컬 실행 기능이 없다.

과거 `--connected-p0-demo` 5대 검증의 BUFFER_FULL은 버퍼의 대기+예약 용량을 초과하지 않도록 신규 배차를 막는 정상 상태다. 예약된 차체의 도착은 허용하고, Bay에서 셀로 진입해 슬롯을 반환하면 재배차한다. ASM-01 DOWN/복구는 별도의 장애 주입이고, 관찰 단계의 PAUSED는 설명을 위한 일시정지다. 지정 FAIL 1건도 버퍼로 인한 오류가 아니다. 현재 일반 5대 시나리오에는 이 자동 P0 관찰 단계가 없으며 사용자 점검·조치 후 복구한다. 현재 시연은 [시연 안내](<../../가상 제조공장 실시간 통합 관제 시스템 - 기능 설명 및 시연 시나리오.md>)를 따른다.

일반 Python 컨테이너 기동은 생산을 자동으로 시작하지 않습니다. 준비된 환경에서 다음 중 필요한 시연 **하나**를 명시적으로 실행합니다.

```sh
# 차체 1대의 정상 공정·검사·결과 구역
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run --connected-demo --traffic

# 차체 3대의 정상 공정·PASS/GOOD 완료
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run --connected-three-demo --traffic

# 과거 자동 P0 검증 전용: 예약 만석·셀 정지/복구·4 PASS/1 FAIL
INGESTION_TCP_HOST=127.0.0.1 INGESTION_TCP_PORT=9090 scripts/simulator.sh run --connected-p0-demo
```

출력한 새 runId를 [실제 Vue 관제](http://127.0.0.1:5173)의 **실행 ID**에 넣고 **관측 연결**을 선택합니다. `factory-gui/`의 독립 샘플은 실제 제조 데이터 화면이 아닙니다. 공장 지도와 스마트태그 상세, 목적지 슬롯의 W/R/A/C, 품질·알람, 기록 조회를 관측합니다.

각 명령은 새 runId를 만듭니다. 같은 tagId라도 run이 다르면 별도 차체입니다. 이미 종료한 run은 FINISHED/보관값이며 현재 LIVE 생산으로 설명하지 않습니다. 원본·실행 자료는 `.build-cache/connected-demo/`에 남습니다.

## 서버·전달 장애 진단과 복구

이 절은 서버/DB/통신 복구다. 현재 5대 시나리오의 설비 정지는 위의 사용자 점검·조치 버튼으로 복구한다.

```sh
scripts/dev-stack.sh status
scripts/dev-stack.sh logs ingestion-service
scripts/dev-stack.sh logs operations-service
```

1. 프로세스·DB 준비 상태와 공장 보고 신선도를 구분합니다. `/livez` 200이어도 DB가 준비되지 않으면 `/readyz`는 503일 수 있습니다.
2. 관제 서버가 멈추면 수집 ACK와 outbox 대기는 유지됩니다. 관제 서버·DB를 복구한 뒤 전달 대기가 줄고 최신 전체 보고가 반영되는지 확인합니다.
3. 수집 서버·DB가 멈추면 Python의 미확인 head를 유지합니다. ACK가 없던 원본은 같은 바이트·eventId·sourceSeq로 재전송합니다. 새 원본으로 바꾸어 순서를 뛰어넘지 않습니다.
4. 반복 거절·설정 오류·수동 정지 상태는 자동 재시작만으로 해결됐다고 판단하지 않습니다. [전달 진단/재개 안내](../../services/ingestion-service/README.md)와 [delivery-control.py](../../scripts/delivery-control.py)의 해당 실행 진단을 확인합니다. 원인을 해결한 후 필요한 run만 명시적으로 재개합니다.
5. 관제 서버 재시작 직후의 RESTORING·오래된 위치는 마지막 확인값입니다. 새 전체 보고가 도착해야 LIVE로 복원됩니다. 알람 확인 버튼은 셀·차체를 정상화하지 않습니다.

실제 장애 재현은 사용자 환경에서 무작정 서버를 끊지 않고 전용 도구를 사용합니다. 기존 S08 증거를 참고하며, 장애 경계가 바뀐 경우에만 다시 실행합니다.

```sh
.build-cache/simulator-venv/bin/python scripts/verify-recovery.py
```

Python의 미확인 목록과 물리 상태는 메모리 기반입니다. Python 프로세스 자체의 비정상 종료 후 물리 상태 자동 복원을 구현한 것은 아닙니다. ACK 이후의 원본/outbox는 DB의 영속 기록입니다.

## 측정을 다시 하는 경우

캐시된 PostgreSQL 17.11·Java 21·Node 도구와 Python 환경이 준비돼 있어야 합니다. 이 명령들은 임의 loopback 포트의 **새 검증 DB**를 사용하며 개발 Compose DB를 초기화하지 않습니다.

```sh
# 정상 5분×3, 스트레스 2분×3×3단계. 예열·배출 대기는 별도
.build-cache/simulator-venv/bin/python scripts/measure-performance.py

# 실제 Chrome 연결도 함께 기록. 각 normal 단계의 phase.json URL을 열어 확인
.build-cache/simulator-venv/bin/python scripts/measure-performance.py --browser

# SQL 비교 → 기존 데이터 재시작 → 새 P0 실제 브라우저 시연
.build-cache/simulator-venv/bin/python scripts/measure-sql-demo.py --browser
```

`--browser`의 정상 측정에서는 실제 화면 연결을 확인한 뒤 증거 폴더에 `UI.normal-1.continue`, `UI.normal-2.continue`, `UI.normal-3.continue`를 각 단계마다 만듭니다. 각 5분 동안 해당 실행 화면을 유지합니다. 실제 전경 여부와 크기는 표본마다 기록됩니다. 브라우저를 연결하지 않은 실행은 GUI 성능 결과로 간주하지 않습니다.

SQL 도구는 `SQL_REVIEW`에서 멈춥니다. `sql-result.json`과 실행 계획·동일 조건 API 비교를 확인한 뒤 필요한 마이그레이션을 결정하고 `review.continue`를 만듭니다. 권고값만으로 자동 최적화하지 않습니다. 재빌드·적용 후 같은 DB의 지문과 이력을 확인합니다.

새 시연에서는 `phase.json`에 표시한 `FULL_RESERVED`, `FULL_IN_TRANSIT`, `FULL_ARRIVED`, `CELL_DOWN`, `SLOT_RELEASED`, `FINISHED`의 실제 화면과 JSON을 확인하고 단계별 `UI.<단계>.continue`를 만듭니다. 마지막 단계에서는 같은 runId·전체 stages 목록·실제 저장한 screenshots 목록의 `browser-proof.json`을 **먼저** 저장한 뒤 마지막 gate를 만듭니다. gate 파일 자체를 브라우저 검증 증거로 사용하지 않습니다.

기능만 확인하는 SQL·시연 실행은 브라우저 플래그를 생략할 수 있습니다. SQL 검토 gate는 그대로 필요합니다. 100대 검사 재생에는 이미 검증한 S08 원본 파일이 필요하며, 없으면 임의 사실을 만들지 않고 명시적으로 실패합니다.

성공·실패 모두 `.build-cache/performance-verification/<UUID>/`에 DB·원본·로그·측정 파일을 남깁니다. 도구는 자기 프로세스와 임시 소켓을 종료합니다. 0600 자격 정보와 DB 디렉터리 전체를 공유하지 않습니다. 제출 가능한 선택 자료와 실제 실행 결과는 [S09 측정·완료 기록](<S09 측정·완료 기록.md>)에 연결합니다.

## 측정 도구가 준비 단계에서 중단된 경우

실패 폴더의 DB·로그·원본을 보존합니다. 완료한 반복의 바이트 대조와 종료 상태를 먼저 확인하고, 필요한 나머지 반복만 새 검증 환경에서 진행할 수 있습니다. `--first-repeat`은 첫 번째로 선택한 목표에만 적용됩니다. `--skip-regression`은 같은 변경의 관련 Java 검증이 이미 통과했을 때만 사용합니다.

```sh
# 이번 실행에서는 정상/100과 300의 1~2회가 이미 완료되어 나머지만 수행
.build-cache/simulator-venv/bin/python scripts/measure-performance.py --rates 300 500 --first-repeat 3 --skip-regression

# 종료가 확인된 부모 폴더만 합쳐 12개의 완료 반복을 분석
.build-cache/simulator-venv/bin/python scripts/merge-performance-evidence.py <첫8회폴더> <나머지4회폴더>
.build-cache/simulator-venv/bin/python scripts/report-performance.py <분석합본폴더> docs/development/s09-results

# 실제 캡처가 있는 browser-proof.json의 captures 목록을 단계 재생으로 묶기
.build-cache/simulator-venv/bin/python scripts/package-demo-captures.py <SQL시연증거폴더> docs/development/s09-demo

# macOS 내장 avconvert가 있는 경우에만 MP4 추가
.build-cache/simulator-venv/bin/python scripts/package-demo-captures.py <SQL시연증거폴더> docs/development/s09-demo --mp4
```

새 JVM/PG의 캐시와 uptime은 이전 프로세스와 동일하지 않습니다. 실패한 부모 전체를 성공으로 바꾸지 않고 결과에 원본 부모·실패 단계·완료한 개별 반복을 표시합니다. 제출 자료에는 비밀 계정 파일과 DB 전체를 넣지 않습니다. 영상은 실제 캡처를 각3초씩 보여 주는 단계 재생입니다.
