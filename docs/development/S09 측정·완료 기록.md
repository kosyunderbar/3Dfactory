## 측정 범위와 조건

Java 21·Spring Boot 4.1.1·JdbcTemplate·Flyway·PostgreSQL 17.11·Python 3.12·Vue 3·Vite·ECharts·TCP NDJSON·REST/SSE를 유지한다. UI는 흰 바탕·네이비 글씨·파랑 계열 그대로다. 새 의존성과 서비스는 추가하지 않는다.

별도 PostgreSQL 클러스터와 두 Java 서버, 측정용 Vue 개발 서버를 loopback 임의 포트에서 실행한다. 개발용 Compose DB/볼륨을 초기화하거나 재시작하지 않는다. 하드웨어는 Apple M3 Pro, 논리 코어 12개, 메모리 36GiB다. 네이티브 측정은 Compose 검증 VM의 2CPU/4GiB 제한 안에서 실행한 결과가 아니다. 기존 사용자 작업을 중단하지 않으므로 이 환경의 관측 결과로 해석한다.

정상은 초당 전체 보고 25건 목표로 300초×3, 스트레스는 100·300·500건 목표로 각각 120초×3이다. 기본 3셀·AGV 2대·AMR 1대, seed42, work4/6/3초, route4초를 사용한다. 정상 등록 간격은 40초이며 정상 8대, 스트레스 3대의 실제 공정을 진행한다. 검사 패턴은 FAIL/PASS/PASS/PASS/PASS다. 입력 부하와 최종 검사 수를 별도로 센다.

각 반복은 새 runId와 5초 예열을 사용한다. 브라우저 gate 대기는 활성 시간에 포함하지 않는다. 활성 부하가 끝나면 신규 투입을 멈추고 잔여 공정·미확인·outbox를 소진한다. 성공한 자기 run은 원본 바이트·해시 대조 후 DB 행만 정리한다. 원본·측정·결과는 남긴다. 동일한 설정과 시작 행 수를 사용하며, 매번 물리 DB 캐시를 초기화한 실험은 아니다.

## 수치의 의미

- 고유 commit/s는 활성 구간의 성공 ACK를 실제 원본·양 DB와 대조한 수/monotonic 실행 시간이다. 예열·배출 기록은 활성 처리량에 더하지 않는다.
- ACK 왕복은 송신기의 같은 monotonic clock이다. Java 수집 처리·입력 대기·HTTP 왕복·관제 업무 반영은 각각 해당 JVM의 monotonic 구간이다. 수집/업무 처리는 검증과 commit을 포함한다.
- 서버 간 HTTP 왕복에는 관제 처리 시간이 포함된다. 구간별 p95를 더하지 않는다. outbox 대기는 1초마다 관측한 건수·바이트로 기록하며 정확한 매 순간의 최고 큐 길이로 부르지 않는다.
- 발생→수신, 수신→업무 commit/SSE/렌더 프레임은 같은 호스트의 wall clock 차이를 포함한 추정치다. 밀리초 해상도와 호스트 시계 조정을 포함한다.
- SSE는 최신 전체 상태를 묶는다. 실제 관측한 sourceSeq만 원본 수신 시각에 대응시킨다. 관측하지 않은 이벤트에 0ms 화면 지연을 부여하지 않는다.
- Vue `nextTick` 후 렌더 프레임과 `requestAnimationFrame` 간격을 관측한다. 실제 디스플레이 표시 완료·GPU FPS를 직접 측정하지 않는다. 숨겨진 탭과 비활성 창을 전경 결과에서 제외한다.
- Java CSV와 개발 모드 브라우저 기록의 비용이 포함된다. Java 파일은 유한한 행 수, 브라우저 기록은 유한한 배치/파일 크기로 제한한다. 누락·상한 도달은 결과에서 드러나야 한다.

## SQL·화면 비용과 최적화 판단

10만 합성 TELEMETRY 로그의 실행/기간/설비 조건과 첫 페이지20건을 고정한다. 첫 관측 실행 계획과 예열 후 계획을 구분한다. 각 실제 API는 5회 예열 후 50회 측정한다. OS 캐시를 비우지 않으므로 warm 결과이며 cold 성능을 주장하지 않는다.

품질은 검증된 100대 원본의 재생으로 얻은 검사 사실100건·PASS80/FAIL20이다. 이 결과를 10만 건 검사 집계라고 표현하지 않는다. 검증 전용 임시 인덱스의 동일 조건 비교, 인덱스 크기, 동일한 1,000행 rollback 삽입 비용을 확인한 뒤 채택 여부를 남긴다.

로그 기간5분·limit20·run/설비와 첫 페이지의 eventId/sourceSeq를 고정했고 양쪽 조회 결과가 일치했다. SQL의 계획 시간은 단일 관측이며 API50회 분포와 다르다. DB cache/JIT가 순차 진행된 전후 실험이므로 API 감소를 전부 인덱스의 인과 효과라고 주장하지 않는다. 품질 재생은 S08 원본3,533건의 동일 바이트를 새 DB에 전달한 것이다.

**인덱스 채택 안 함.** 기존 계획은 최신 인덱스 조회와 incremental sort를 사용했고 로그 SQL은0.1ms 안팎이다. 임시 `(run_id, record_ordinal DESC)` fence 색인의 개선은0.016ms뿐이다. 추가 공간7,774,208바이트(약7.41MiB), 같은1,000행 rollback 삽입의 p50은34.276→35.130ms, p95는35.974→36.113ms였다(각 최초1회 제외3회). 기존 조회는500ms 목표보다 충분히 작고 의미 있는 SQL 병목을 확인하지 못해 임시 index를 삭제했다. 관제 Flyway V1, 수집 V1/V2를 유지하고 새 DDL을 추가하지 않았다.

## 초기·기존 데이터 재실행과 새 시연

초기 실행은 새 검증 DB에서 DB/계정 준비와 Flyway를 적용했다. 같은 DB에 초기화 스크립트를 다시 실행하면 `Refusing to reset or overwrite`로 거부했고 선택 표의 지문은 유지됐다. 관제 재빌드·기동 뒤에도 같은 내용이었다. 두 Java와 PostgreSQL을 종료하고 **같은 data 디렉터리**로 다시 시작한 뒤 다음 선택 표의 행 수/내용 MD5 지문이 모두 같았다.

| DB | 확인한 표 | 재시작 전/후 행 수 |
|---|---|---|
| 수집 | raw_event / event_outbox / delivery_stream | 3,535 / 3,535 / 2 |
| 관제 | processed_event / event_projection | 103,535 / 103,535 |
| 관제 | inspection_result / body / factory_snapshot | 100 / 100 / 2 |

선택 표8개의 정렬한 row JSON 지문 비교이며 모든 DB 표나 Python 메모리를 검증한 것은 아니다. Flyway 성공 이력은 수집1,2·관제1 그대로다. [재시작 원본 지문](s09-results/restart-result.json) · [재빌드/기동 보존](s09-results/migration-preservation.json). 실행 명령과 장애 책임별 절차는 [초기 실행·재실행·복구·시연](<초기 실행·재실행·복구·시연.md>)에 있다.

### 제출용 캡처·영상

[단계별 캡처 재생 HTML](s09-demo/index.html) · [MP4 단계 영상](s09-demo/s09-stage-playback.mp4) · [원본 JPEG 프레임 AVI](s09-demo/s09-stage-playback.avi) · [순서/촬영 시각](s09-demo/manifest.json) · [실제 재생 확인](s09-demo/video-verification.json).

실제 JPEG7장을 각3초씩 보여 주는21초 단계 재생이다. AVI 프레임/색인/길이 구조를 확인했고 macOS 내장 avconvert로 MP4를 만들었다. QuickTime에서 재생 시작·00:21 길이·마지막 태그 화면과21초 끝을 실제 확인하고 검증 창을 닫았다. 원본 JPEG/AVI는 그대로 남겼고 MP4는 인코딩한 파생 영상이다. HTML의 로컬 브라우저 열기는 도구의 file: URL 허용 정책에 막혀 실제 버튼 재생을 확인하지 못했다. 우회하지 않고 [HTML/JS 문법·미디어 링크/원본 일치 정적 확인](s09-demo/html-static-verification.json)으로 구분해 남겼다. MP4의 실제 재생 확인과 다르다. 기획서의3~5분 해설 포함 연속 촬영 구성은 참고안이며 이번21초 자료를 그 연속 녹화라고 부르지 않는다.

SQL/재시작/시연 증거는 `.build-cache/performance-verification/6980434eae66421cbdbdaaf547efb641`에 보존했다. 성공 후 검증용 Java/PG/Vue와 임시 소켓을 종료했고 DB/원본은 남겼다. 공유용 자료에는 선택 JSON/CSV·계획·이미지·영상만 복사했다. 0600 계정 파일과 DB 전체는 제외했다.


새 시연은 정상 모델 등록과 명령만 사용한다. 관측 gate에서는 물리 진행을 일시정지하고 실제 보고를 계속 보낸다. 물리 진행은 일시정지하며 GUI는 같은 보고와 전달 진단에 따라 공장 일시정지 또는 잠깐의 업무 반영 대기를 표시한다. 캡처 기반 단계 영상은 같은 실제 run의 이미지를 각3초씩 재생하며, 연속 실시간 화면 녹화의 FPS·소요시간으로 해석하지 않는다.

## 완료 범위와 한계

P0의 차량은 AGV2/AMR1이다. S08의100대는 차체이며 수백 대 차량의 처리 성능이 아니다. 무선 태그·현장 장비·경로 교통 충돌·복잡한 자원 순환 전체의 교착 상태 부재 증명·Python 비정상 종료 후 물리 상태 영속 복원·고가용성/운영 인증은 후속 범위다.

`W+R≥C`의 예약 규칙은 예약 없는 배출·초과 진입을 막는다. 모든 종류의 교착 상태를 증명한 것으로 확대하지 않는다. [ADR-002](<../decisions/ADR-002-측정 근거와 P0 완료 범위.md>)에 유지한 규칙·측정 해석·재검토 조건을 남겼다.

성능 목표를 못 맞췄거나 해당 입력량/화면 조건을 만들지 못한 결과도 남긴다. 기능 검증 완료와 특정 성능 목표의 달성 여부를 구분한다. 전체 테스트를 다시 돌리지 않고 변경과 관련한 기존 Java2개·Node2개, 실제 측정·원본 대조·기존 데이터 재시작·새 시연만 수행한다.
